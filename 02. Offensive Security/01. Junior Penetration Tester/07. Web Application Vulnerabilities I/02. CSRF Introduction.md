## Task 1: Introduction
Overview
**Cross-Site Request Forgery (CSRF)** attacks. CSRF exploits the trust a web application has in a user's browser by tricking it into making unauthorized requests on an authenticated site. Unlike credential theft, CSRF leverages the browser's automatic inclusion of session cookies to perform actions without the user's consent.

Imagine we're logged into your bank account. A hacker sends us a link to a funny cat video. We click it — but hidden in that page is a request to transfer $100 to the hacker. Since our browser still has your bank's login cookie, the bank thinks we made the transfer. That's CSRF.

> **Note**: A token that web applications use to track authenticated users. MLflow API calls without a session cookie indicate scripted access rather than someone using the web interface, which is a sign of automated enumeration.

> **Note**: Cross-site request forgery (also known as CSRF) is a web security vulnerability that allows an attacker to induce users to perform actions that they do not intend to perform. It allows an attacker to partly circumvent the same origin policy, which is designed to prevent different websites from interfering with each other.

## Task 2: What is CSRF

### What is CSRF?
**Cross-Site Request Forgery (CSRF)** is a web vulnerability where an attacker tricks a user's browser into sending an unauthorized request to a website where the user is already logged in. Because browsers automatically attach session cookies to every request, the web application has no way of knowing that the user didn't actually intend to make that request.


The attacker doesn't steal the user's password or login details. Instead, they abuse the trust between the browser and the website. If the request does something sensitive — like changing an email address, updating account settings, or transferring money — the attacker can quietly modify the victim's account without them ever realizing it.


#### Example:
Imagine you're logged into our company's internal portal in one browser tab. In another tab, we visit a malicious website. That website contains hidden code that sends a request to your company portal — like "change my email to hacker@evil.com". our browser automatically includes our session cookie with that request. The portal sees a valid cookie and processes the change, thinking it came from us. we never clicked anything on the portal, but our account is now compromised.



### How CSRF Attacks Work

<img width="1200" height="400" alt="image" src="https://github.com/user-attachments/assets/fa870964-0f7b-4169-89f9-4b1a02284d04" />


A typical CSRF attack follows three simple steps:
- **The victim logs in** to a legitimate website (like StaffHub). The browser stores a session cookie to remember they're authenticated.
- **The attacker tricks the victim** into visiting a malicious webpage. This page contains a hidden or automatically submitted request (like a form or image tag) that targets the legitimate site.
- **The victim's browser sends the request** to the target website, automatically including the stored session cookie. The server receives the request, sees a valid cookie, and processes it as if the victim intentionally made it.

Because the request looks completely legitimate to the server, the action is carried out without any warning or confirmation.



### Why This Is Dangerous
CSRF attacks can be used to perform a wide range of harmful actions, depending on what the target application allows:

- **Changing a user's email address**: allowing the attacker to reset the password later.
- **Updating account settings**: like turning off security notifications.
- **Performing financial transactions**: transferring money or making purchases.
- **Modifying security preferences**: like changing recovery questions or 2FA settings.

The victim never intended to perform these actions, and they may not even notice anything happened. The web application processes everything as a legitimate request because it trusts the session cookie.

## Task 3: Why CSRF Works

The browser is doing exactly what it was designed to do. The problem is that the web application trusts the request too much.

> **Note**: **Session Cookies** is a token that web applications use to track authenticated users. MLflow API calls without a session cookie indicate scripted access rather than someone using the web interface, which is a sign of automated enumeration.

### What is happening?

When we log in to a website such as ``StaffHub``, the server creates a ``session`` and gives your browser a ``session cookie``.

<img width="600" height="200" alt="image" src="https://github.com/user-attachments/assets/8aa79abc-ca7f-4a9d-bd7a-b0e282c9188d" />


Think of the cookie like an ID card:
````
Us
 ↓
Login to StaffHub
 ↓
StaffHub creates a session
 ↓
Browser receives session cookie
 ↓
Browser stores the cookie
````


For example:
````
session = ABC123
````
Every time our browser sends a request to ``StaffHub``, it automatically includes that cookie.

````
Browser
   ↓
Request + Cookie
   ↓
StaffHub
````


StaffHub sees:
````
session = ABC123
````
and thinks: ``This request belongs to a logged-in user``.



#### Why can this become CSRF?

The browser does not know whether the request was intentionally made by us.

Example:
````
We are logged in to StaffHub
          ↓
We visit another website
          ↓
That website causes a request to StaffHub
          ↓
Browser includes your StaffHub cookie
          ↓
StaffHub receives an authenticated request
          ↓
StaffHub may trust it
````

The browser sends the cookie automatically, and the application may trust the request too much.




### Key Conditions for a CSRF Attack

#### 1. Victim is authenticated

The victim must already be logged in: ``Login -> Valid session -> Authenticated``


#### 2. Application has a state-changing action

The application must have an action that changes something.

Examples:
````
Change email
Change password
Update profile
Change account settings
````


#### 3. Application doesn't properly verify the request

The application must fail to properly check whether the request was legitimate.

For example: ``Is the user logged in? ->  YES -> Allow request``

It may fail to ask:

``Did this request actually come from the legitimate application?``.

## Task 4: Finding CSRF Vulnerabilities

Before testing for CSRF, a pentester first needs to find **which features might be vulnerable**.

Not every feature is a good CSRF target.

The most interesting features are actions that **change data or account settings**.

> **Note**: Cross-site request forgery (also known as CSRF) is a web security vulnerability that allows an attacker to induce users to perform actions that they do not intend to perform. It allows an attacker to partly circumvent the same origin policy, which is designed to prevent different websites from interfering with each other.

> **Note**: Hypertext Transfer Protocol (HTTP) is the protocol that specifies how a web browser and a web server communicate. Your web browser requests content from the TryHackMe web server using the HTTP protocol as we go through this room.


#### What should we look for?

Whenever we perform an action on a website, our browser sends an HTTP request to the server.

There are two general types:
````
GET
 ↓
Usually retrieves information


POST
 ↓
Often changes information
````
For CSRF testing, we mainly pay attention to ``state-changing`` requests.

For example:
````
Change Email
      ↓
HTTP Request
      ↓
Server
      ↓
Email changed
````
The important question for a pentester is:

> Can this action be triggered without verifying that the request actually came from the user?

If yes, the feature might be vulnerable to CSRF.




### Common Features Vulnerable to CSRF

<img width="800" height="1200" alt="image" src="https://github.com/user-attachments/assets/0f855f5f-de68-41d8-b0fe-2ba31e248b8d" />


#### GET vs POST: A Common Misconception

A very important point:

> **POST does NOT automatically protect against CSRF**.

Some developers think:
````
POST = Safe
````
But that is incorrect.

Both **GET** and **POST** can potentially be involved in CSRF if the application does not properly verify the request.

#### GET
````
GET /change-email?email=test@example.com
````

If this request changes the email, it could potentially be abused.

#### POST

Another application might use:
````
POST /change-email

email=test@example.com
````
This can also potentially be vulnerable if proper CSRF protection is missing.

So don't simply look at:
````
GET = vulnerable
POST = safe
````
Instead, look at: ``HTTP Request -> Does it change something? -> Does it have proper CSRF protection? -> Can the request be triggered by another origin?``
