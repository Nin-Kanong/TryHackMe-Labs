## Task 1: What is an IDOR?

### What is IDOR?

**IDOR = Insecure Direct Object Reference**

**IDOR (Insecure Direct Object Reference)** is a type of Broken Access Control vulnerability.

It happens when an application uses an ID or reference to retrieve an object, but does not check whether the logged-in user is allowed to access that object.


For example:
````
https://website.thm/profile?id=100
````
If id=100 belongs to us, everything is normal.

But if we change it to:
````
https://website.thm/profile?id=101
````
and the server shows another user's profile without checking authorization, that is an IDOR.



#### How IDOR works
<img width="1536" height="1024" alt="image" src="https://github.com/user-attachments/assets/3ea90eb3-c4d0-4f59-9bfb-82471b6d70f3" />



### IDOR in the Security Landscape

#### Where it fits:
**IDOR** is classified as an access control vulnerability. It falls under Broken Access Control - which is #1 in the OWASP Top 10 (the most critical web security risks).

In the API security world, the same flaw is called Broken Object Level Authorization (BOLA). The terminology changes depending on context, but the root cause is exactly the same: **the server doesn't verify permissions for the specific object being requested**.


### Learning Objectives

By the end of this room, you will be able to:
- Explain what an IDOR vulnerability is and how it relates to broken access control
- Identify the different forms object references can take, including plaintext, encoded, and hashed identifiers
- Recognise the locations in a web application where IDOR vectors commonly appear
- Exploit an IDOR vulnerability in a practical scenario to access another user's data

## Task 3: Finding IDORs in Encoded IDs

**The ID is hidden by encoding, but it is not encrypted.**

Not every application exposes object references as plaintext values. Developers frequently ``encode`` identifiers before including them in query strings, POST data, or cookies. Encoding converts raw data into an ASCII-safe string using the characters ``a-z``, ``A-Z``, ``0-9``, and ``=`` for padding. The purpose is to ensure the receiving server can process the value without misinterpreting special characters.

The most common encoding scheme on the web is ``base64``. Base64 strings tend to be noticeably longer than the value they represent and often end with one or two ``=`` padding characters. For example, the integer ``123`` becomes ``MTIz`` when base64-encoded. A small JSON structure like ``{"user_id": 5}`` might appear as ``eyJ1c2VyX2lkIjogNX0=``.

### 1. Find the encoded ID

We may see something like:
````
/user?id=eyJ1c2VyX2lkIjo1fQ==
````
The value after ``id=`` is Base64-encoded.

Go to: https://www.base64decode.org/

Then past this:
````
eyJ1c2VyX2lkIjogNX0=
````
<img width="1346" height="977" alt="image" src="https://github.com/user-attachments/assets/35fa5fd9-aeb9-4340-bda6-20fb6705ef91" />



### 2. Decode it

Use a Base64 decoder.

Example:
````
eyJ1c2VyX2lkIjo1fQ==
        ↓ decode
{"user_id":5}
````
Now we can see the real ID:
````
user_id = 5
````


### 3. Change the ID

Modify the decoded value:
````
{"user_id":5}
        ↓
{"user_id":1}
````
This is the IDOR test.

Go to: https://www.base64encode.org/

## Task 4: Finding IDORs in Hashed IDs

The application may **hash an ID** before putting it in a request.

Example:
````
User ID: 123
     ↓ MD5
202cb962ac59075b964b07152d234b70
````

The hash looks random, but if the original IDs are predictable (``1, 2, 3, 4...``), an attacker can calculate hashes for those IDs and compare them with the hash in the request.


Important
| Hash Algorithm         |        Length | Character Set              | Important Point                                                      |
| ---------------------- | ------------: | -------------------------- | -------------------------------------------------------------------- |
| **MD5**                | 32 characters | Hexadecimal (`0-9`, `a-f`) | Fast but considered weak for security                                |
| **SHA-1**              | 40 characters | Hexadecimal (`0-9`, `a-f`) | Weak for collision resistance                                        |
| **SHA-256**            | 64 characters | Hexadecimal (`0-9`, `a-f`) | Stronger and commonly used                                           |
| **Hashing**            |             — | —                          | **One-way** — normally cannot be reversed directly                   |
| **Predictable inputs** |             — | —                          | Hashes of predictable values can still be **guessed/brute-forced**   |
| **Hashed ID**          |             — | —                          | **Does not prevent IDOR** if the server does not check authorization |

````
Hashed ID
   ↓
Identify algorithm
   ↓
Test predictable IDs
   ↓
Compare hashes
   ↓
Match?
   ↓
Possible IDOR
````

> **Note**: Hashing hides the ID, but **server-side authorization is what actually prevents IDOR**.

## Task 5: Finding IDORs in Unpredictable IDs


### What Are Unpredictable IDs?

Some applications use randomly generated strings, UUIDs, or other identifier formats that can't be guessed or enumerated.


Example UUID:
````
d3b07384-d9a0-4e9b-8b3c-2f1a6c7e4a90
````

> **Note**: **UUID** is an Universal Unique Identifier is a 128-bit value used to uniquely identify an object, entity or information within a particular system or knowledge database.

> **Note**: **IDOR** is an Insecure direct object references (IDOR) are a type of access control vulnerability that arises when an application uses user-supplied input to access objects directly. The term IDOR was popularized by its appearance in the OWASP 2007 Top Ten.

This identifier has no relationship to other users' IDs. We can't increment it (like ``1`` → ``2``) or hash sequential values to get valid references. It's designed to be unpredictable.


### Does Unpredictable Mean Secure?
No! An unpredictable identifier removes one attack path: enumeration (guessing other IDs). But it does not eliminate the IDOR risk.

#### The real question:
If the server still fails to verify that the requesting user is authorized to access the referenced object, the vulnerability exists. The attacker just needs to obtain a valid identifier through a different channel.


### The Standard Test: Two-Account Technique
This is the most reliable way to test for IDOR when IDs are unpredictable.

#### Step-by-step:

1. ``Create two accounts`` on the application — **Account A and Account B**.

2. ``Log into Account A`` and record the identifiers associated with its resources:
- Profile IDs
- Order references
- Document paths
- Any other object IDs

3. ``Log into Account B`` and substitute Account A's identifiers into Account B's requests.
4. Observe the response:
- If the server returns Account A's data to Account B → Vulnerable!
- If the server says "access denied" or returns nothing → Protected!


### Why This Technique Works
This technique separates two important questions:

| **Question**                           | **What it means**                                           |
| -------------------------------------- | ----------------------------------------------------------- |
| **Can an attacker get a valid ID?**    | This depends on how predictable the IDs are and what leaks. |
| **Will the server serve that object?** | This depends on whether proper authorization checks exist.  |



### Where Unpredictable IDs Can Leak
In practice, unpredictable identifiers often leak through various channels. Once we find a valid ID from any of these sources, exploiting the IDOR is no different from the plaintext case.

Common leak channels:
| **Channel**             | **Example**                                                      |
| ----------------------- | ---------------------------------------------------------------- |
| **Shared URLs**         | A user shares a direct link to a document or resource.           |
| **API responses**       | The API returns references to other users' resources.            |
| **HTML source code**    | IDs embedded in the page HTML.                                   |
| **JavaScript files**    | Hardcoded references in client-side code.                        |
| **Notification emails** | Links in password reset, order confirmation, or activity emails. |
| **Exported data**       | CSV reports, PDFs, or other generated documents.                 |

## Task 6: Where are IDORs Located?


### Where to Find IDOR Vulnerabilities

#### The Big Mistake
**IDOR** vectors are not confined to URL parameters visible in the browser's address bar. Vulnerable endpoints can exist anywhere the application processes a user-supplied object reference. If we only test what we see in the address bar, we'll miss a significant proportion of IDOR flaws.



### 1. Background Requests

Websites often send ``API requests in the background`` that we don't see in the URL bar.

Example: ``Our Account page -> Background API request -> /api/v1/customer?id=15``

If we change ``id=15`` to another user's ID and can access their data, it may be **IDOR**.

Check these requests in **Developer Tools** → **Network** or Burp Suite.




### 2. JavaScript Files

JavaScript files can contain hidden API endpoints and parameter names.

Example:
````
fetch("/api/user/details?id=15")
````
This can reveal an endpoint that isn't visible on the webpage.



### 3. Parameter Mining

Sometimes an endpoint accepts parameters that the normal website doesn't use.

Example:
````
/user/details
````
Normally uses your session.

But testing may reveal:
````
/user/details?user_id=123
````
If changing the parameter lets you access another user's data, it may be **IDOR**.



### 4. Common Locations

Look for IDORs in:

| Location                | Example                 |
| ----------------------- | ----------------------- |
| **URL parameters**      | `?id=123`               |
| **POST body**           | `user_id=123`           |
| **Cookies**             | `user_id=123`           |
| **HTTP headers**        | `X-User-ID: 123`        |
| **API paths**           | `/api/users/123/orders` |
| **Background requests** | AJAX/API requests       |


> **Note**: Don't only check the browser URL. ``Inspect the requests the application sends``.
