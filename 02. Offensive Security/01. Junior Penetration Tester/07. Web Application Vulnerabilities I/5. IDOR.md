## Task 1: What is an IDOR?

### What is IDOR?

**IDOR = Insecure Direct Object Reference**

**IDOR (Insecure Direct Object Reference)** is a type of Broken Access Control vulnerability.

It happens when an application uses an ID or reference to retrieve an object, but does not check whether the logged-in user is allowed to access that object.


For example:
````
https://website.thm/profile?id=100
````
If id=100 belongs to us, everything is normal.

But if we change it to:
````
https://website.thm/profile?id=101
````
and the server shows another user's profile without checking authorization, that is an IDOR.

### IDOR in the Security Landscape

#### Where it fits:
**IDOR** is classified as an access control vulnerability. It falls under Broken Access Control - which is #1 in the OWASP Top 10 (the most critical web security risks).

In the API security world, the same flaw is called Broken Object Level Authorization (BOLA). The terminology changes depending on context, but the root cause is exactly the same: **the server doesn't verify permissions for the specific object being requested**.


### Learning Objectives

By the end of this room, you will be able to:

- Identify the different forms object references can take, including plaintext, encoded, and hashed identifiers
- Recognise the locations in a web application where IDOR vectors commonly appear
- Exploit an IDOR vulnerability in a practical scenario to access another user's data

## Task 2: An IDOR Example

The simplest form of **IDOR** occurs when an application places an object identifier directly in a URL parameter and uses it to query a back-end database without any authorisation check.

Suppose we sign up for an online service and navigate to our profile page. The URL reads:
````
http://online-service.thm/profile?user_id=1305
````
The ``user_id`` parameter tells the server which record to retrieve from its database. In this case, record 1305 corresponds to your account, and the page displays your name, email address, and other personal details as expected.


Now suppose you change the parameter value to 1000:
````
http://online-service.thm/profile?user_id=1000
````

## Task 3: Finding IDORs in Encoded IDs

**The ID is hidden by encoding, but it is not encrypted.**

Not every application exposes object references as plaintext values. Developers frequently ``encode`` identifiers before including them in query strings, POST data, or cookies. Encoding converts raw data into an ASCII-safe string using the characters ``a-z``, ``A-Z``, ``0-9``, and ``=`` for padding. The purpose is to ensure the receiving server can process the value without misinterpreting special characters.

The most common encoding scheme on the web is ``base64``. Base64 strings tend to be noticeably longer than the value they represent and often end with one or two ``=`` padding characters. For example, the integer ``123`` becomes ``MTIz`` when base64-encoded. A small JSON structure like ``{"user_id": 5}`` might appear as ``eyJ1c2VyX2lkIjogNX0=``.

### 1. Find the encoded ID

We may see something like:
````
/user?id=eyJ1c2VyX2lkIjo1fQ==
````
The value after ``id=`` is Base64-encoded.

Go to: https://www.base64decode.org/

Then past this:
````
eyJ1c2VyX2lkIjogNX0=
````
<img width="1346" height="977" alt="image" src="https://github.com/user-attachments/assets/35fa5fd9-aeb9-4340-bda6-20fb6705ef91" />



### 2. Decode it

Use a Base64 decoder.

Example:
````
eyJ1c2VyX2lkIjo1fQ==
        ↓ decode
{"user_id":5}
````
Now we can see the real ID:
````
user_id = 5
````


### 3. Change the ID

Modify the decoded value:
````
{"user_id":5}
        ↓
{"user_id":1}
````
This is the IDOR test.

Go to: https://www.base64encode.org/

### 4. Encode it again

Encode the modified value with Base64:
````
{"user_id":1}
        ↓ encode
eyJ1c2VyX2lkIjoxfQ==
````


### 5. Put it back into the request
````
/user?id=eyJ1c2VyX2lkIjoxfQ==
````
Then submit the request.

## Task 4: Finding IDORs in Hashed IDs

The application may **hash an ID** before putting it in a request.

Example:
````
User ID: 123
     ↓ MD5
202cb962ac59075b964b07152d234b70
````

The hash looks random, but if the original IDs are predictable (``1, 2, 3, 4...``), an attacker can calculate hashes for those IDs and compare them with the hash in the request.


Important
| Hash Algorithm         |        Length | Character Set              | Important Point                                                      |
| ---------------------- | ------------: | -------------------------- | -------------------------------------------------------------------- |
| **MD5**                | 32 characters | Hexadecimal (`0-9`, `a-f`) | Fast but considered weak for security                                |
| **SHA-1**              | 40 characters | Hexadecimal (`0-9`, `a-f`) | Weak for collision resistance                                        |
| **SHA-256**            | 64 characters | Hexadecimal (`0-9`, `a-f`) | Stronger and commonly used                                           |
| **Hashing**            |             — | —                          | **One-way** — normally cannot be reversed directly                   |
| **Predictable inputs** |             — | —                          | Hashes of predictable values can still be **guessed/brute-forced**   |
| **Hashed ID**          |             — | —                          | **Does not prevent IDOR** if the server does not check authorization |

````
Hashed ID
   ↓
Identify algorithm
   ↓
Test predictable IDs
   ↓
Compare hashes
   ↓
Match?
   ↓
Possible IDOR
````

> **Note**: Hashing hides the ID, but **server-side authorization is what actually prevents IDOR**.
