## Task 1: SSRF Introduction

### What is SSRF?

**SSRF (Server-Side Request Forgery)** is a vulnerability where an attacker tricks a web server into making an HTTP request to a destination chosen by the attacker.

<img width="1024" height="1536" alt="image" src="https://github.com/user-attachments/assets/cf5b8535-a688-40b4-8c7c-56e865cd5cfb" />



The important point is that **the request comes from the server**, not directly from the attacker's browser.


#### Example

Imagine an application has:
````
/image?url=https://example.com/image.jpg
````
The server fetches whatever URL is supplied.

An attacker might try to make the server request an internal service:
````
/image?url=http://internal-service/
````
The server may be able to access something that the attacker cannot access directly.


### Types of SSRF
| Type             | Response Visible? | Description                                                                                                                             |
| ---------------- | ----------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| **Regular SSRF** | **Yes**           | The server makes the request and returns the response to the attacker. The attacker can directly read the result.                       |
| **Blind SSRF**   | **No**            | The server makes the request, but the response isn't returned. The attacker needs an indirect way to confirm that the request happened. |



#### Regular SSRF

<img width="600" height="700" alt="image" src="https://github.com/user-attachments/assets/6f332b78-4f50-4502-b0b6-6fea463cf287" />

We can directly inspect the returned content.


#### Blind SSRF

<img width="1536" height="1024" alt="image" src="https://github.com/user-attachments/assets/40c928de-58af-4b65-9a6e-52d467e63bb2" />


The response isn't shown to us.

We therefore need an indirect signal, such as a callback to a server we control, to determine whether the request happened.


### SSRF Impact
| Impact                              | Short explanation                                                                                                                 |
| ----------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| **Access to internal endpoints**    | The server may reach internal admin panels, configuration pages, and monitoring systems that aren't publicly accessible.          |
| **Sensitive data exposure**         | Internal APIs, databases, or services may return private company or customer information.                                         |
| **Internal network reconnaissance** | An attacker may discover internal hosts and services by observing responses, errors, or timing.                                   |
| **Cloud metadata theft**            | SSRF may allow access to cloud metadata such as `169.254.169.254`, potentially exposing temporary credentials or IAM information. |
| **Credential/token leakage**        | Internal requests may expose authentication tokens or secrets, especially when internal communication is poorly protected.        |

### 1. Full URL in a parameter

````
https://website.thm/item/2?server=api
````

The application internally creates:
````
https://server.website.thm/api/item?id=2
````
The important point is:
````
server=api
      ↑
user-controlled
````
If you can control this value, you can try changing the destination.


##### Example from the lesson
````
server=server.website.thm/flag?id=9&x=
````

The application may construct something like:
````
https://server.website.thm/flag?id=9&x=/api/item?id=2
````
The ``&x=`` is used so the application's original parameters are treated as another query parameter rather than changing our intended ``id=9``.






### 2. Partial URL / hostname

Sometimes the application does not accept a complete URL.

For example:
````
https://website.thm/stock?server=api.internal
````
The backend builds:
````
https://api.internal/stock/item
````
We can test whether the hostname is actually controlled:
````
https://website.thm/stock?server=attacker.com
````
If our server receives a request, we have evidence that the backend is making the request to our supplied host.



### 3. Path traversal in the URL

The application might normally request:
````
https://website.thm/stock?url=/item/123/details
````
The backend expects:
````
/item/123/details
````
But if the application doesn't properly normalize the path,:
````
../admin
````
can change the requested location.

Conceptually:
````
/item/123/../admin
          ↓
/admin
````
So the server may request:
````
https://website.thm/admin
````




### 4. Hidden form fields

SSRF input isn't always visible in the URL.

The HTML might contain:
````
<input type="hidden"
       name="avatar"
       value="/images/avatars/default.png">
````
The browser hides this field from the normal page, but the server still receives it.

We can inspect it with by just press `F12` or we can `View Source`.


We can also intercept the request with Burp Suite and change the value.

For example:
````
avatar=/images/avatars/default.png
````
could potentially be changed to another URL/path if the server doesn't validate it.

### Summary:

| Technique          | What you control     | Main idea                                                            |
| ------------------ | -------------------- | -------------------------------------------------------------------- |
| Full URL           | Complete destination | Change where the server requests                                     |
| Partial URL        | Host/path            | Control part of the destination                                      |
| Path traversal     | URL path             | Use `../` to reach another path                                      |
| Hidden field       | HTML form value      | Modify an invisible server-side request input                        |
| Query manipulation | Parameters           | Use `&`/query parameters to control how the final URL is constructed |

## Task 3: Finding an SSRF

### Common Indicators


#### What is SSRF?
**Server-Side Request Forgery (SSRF)** happens when a web application makes requests to other servers based on user-supplied input. If the application doesn't properly validate that input, attackers can trick the server into making requests to internal systems, cloud metadata endpoints, or other unintended destinations.


#### Common Patterns That Signal SSRF
These patterns are strong indicators that an application might be vulnerable to SSRF. When you see them during testing, it's worth investigating further.


#### 1. Full URL in a parameter

When a complete URL appears as a query parameter in the address bar, the application is almost certainly using it to make a server-side request.

Example:
````
https://website.thm/form?server=http://server.website.thm/store
````
Here, the server parameter contains a full URL. The application likely fetches something from that URL. If you change it to a different URL (like ``http://localhost`` or ``http://169.254.169.254/``), the server might fetch from that location instead — potentially exposing internal resources.



#### 2. Hidden form fields

Hidden form fields aren't visible on the rendered page, but they exist in the HTML source code. Their values control what the server fetches.

Example:

````html
<form method="post" action="/form">
    <input type="hidden" name="server" value="http://server.website.thm/store">
</form>
````
We can find these by:

Viewing the page source (Ctrl+U or right-click → View Page Source)

Intercepting requests with a proxy (like Burp Suite)




#### 3. Partial URL (hostname only)

The application accepts just a hostname and constructs the full URL on the server side.

Example:
````
https://website.thm/form?server=api
````
The server might take this value and build something like:
````
http://api.website.thm/data
````
By changing the hostname to something else (like ``localhost`` or ``internal-server``), we might be able to redirect the server's request.



#### 4. Path only

Only the path portion of the URL is user-controlled. The application prepends the scheme and hostname automatically.

Example:
````
https://website.thm/form?ds=/forms/contact
````

The server might construct:
````
https://api.website.thm/forms/contact
````
Changing the path might let you access other endpoints on the same server — like ``/admin`` or ``/internal/status`` — that aren't normally accessible from the outside.


#### Common Application Features That Contain SSRF Vectors

| Feature                   | Why It's Relevant                                                |
| ------------------------- | ---------------------------------------------------------------- |
| **Webhook configuration** | The application sends a request to a URL provided by the user.   |
| **PDF/report generation** | The server fetches content from a supplied URL.                  |
| **URL preview/unfurling** | The application retrieves information from a user-provided link. |
| **File import by URL**    | The server downloads a file from a user-specified location.      |
| **Integration settings**  | The server connects to third-party service URLs.                 |
