## Task 2: Sniffing Attack


### What is a Sniffing Attack?

A **sniffing attack** means capturing network packets to see information traveling across a network.

````
Client
  │
  │ USER frank
  │ PASS ********
  ▼
Network ──────► Server
  │
  └──► 👀 Packet Sniffer
       captures traffic
````

#### Where Sniffing Still Matters
- Internal networks without encryption
- Legacy systems using HTTP, FTP, POP3, Telnet, etc.
- Misconfigured services where TLS is available but not used
- IoT devices using insecure protocols
- Wireless networks
- Traffic exposed after a successful MITM/redirection attack

#### Common Packet-Capture Tools
| Tool             | Purpose                       |
| ---------------- | ----------------------------- |
| **tcpdump**      | CLI packet capture            |
| **Wireshark**    | GUI packet capture & analysis |
| **TShark**       | CLI version of Wireshark      |
| **tcpflow**      | Reconstruct TCP streams       |
| **ngrep**        | Search network traffic        |
| **NetworkMiner** | Network forensic analysis     |

### Tcpdump Usefull Filter

### Mitigation
| Mitigation                          | Easy Explanation                                                  |
| ----------------------------------- | ----------------------------------------------------------------- |
| 🔐 **TLS Encryption**               | Encrypt network traffic so captured data is unreadable            |
| 🔑 **Use SSH instead of Telnet**    | SSH encrypts remote login credentials and commands                |
| 🌐 **Use HTTPS instead of HTTP**    | Protects web traffic with TLS                                     |
| 📁 **Use SFTP/FTPS instead of FTP** | Encrypts file transfers and credentials                           |
| 📧 **Use POP3S / IMAPS**            | Encrypts email login and message traffic                          |
| 🧱 **Network Segmentation**         | Separates networks/VLANs to limit who can see traffic             |
| 🔒 **Encrypted VLANs / Tunnels**    | Protects sensitive internal network traffic                       |
| 🪪 **802.1X Authentication**        | Requires devices/users to authenticate before network access      |
| 🛡️ **Zero Trust**                  | Treats network connections as untrusted and requires verification |
| 👁️ **Monitor ARP Spoofing**        | Detects attempts to redirect/intercept local network traffic      |

## Task 3: Man-in-the-Middle (MITM) Attack

A **MITM attack** happens when an attacker secretly positions themselves between two communicating systems.

<img width="1200" height="800" alt="image" src="https://github.com/user-attachments/assets/0dd6c0d0-3d6b-41b9-94a8-81e04bbdf1fd" />



### Common MITM techniques
| Technique              | Simple meaning                                         |
| ---------------------- | ------------------------------------------------------ |
| **ARP Spoofing**       | Redirects LAN traffic through the attacker             |
| **DNS Spoofing**       | Gives a false DNS response to redirect the victim      |
| **Rogue Access Point** | Fake Wi-Fi that routes victim traffic through attacker |
| **BGP Hijacking**      | Redirects internet routes                              |
| **SSL Stripping**      | Attempts to downgrade HTTPS → HTTP                     |
| **Fake Certificate**   | Attempts to impersonate a trusted HTTPS endpoint       |


### Common tools mentioned
| Tool          | Purpose                                                        |
| ------------- | -------------------------------------------------------------- |
| **Bettercap** | MITM/network testing framework                                 |
| **Ettercap**  | Classic LAN MITM testing tool                                  |
| **mitmproxy** | Inspect/test HTTP and HTTPS traffic in controlled environments |
| **Responder** | Tests Windows name-resolution/authentication weaknesses        |

<img width="889" height="150" alt="image" src="https://github.com/user-attachments/assets/4001ca67-c24f-4b79-8dea-635d122b9070" />

### MITM vs Sniffing
````
SNIFFING
Victim ─────────────► Server
         👀
      Attacker
   watches traffic

MITM
Victim ──► Attacker ──► Server
             👀 ✏️
         intercepts traffic
````

**Sniffing** mainly observes/captures traffic. **MITM** actively places the attacker in the communication path and may capture or modify it.


### Modern MITM Defenses
| Defense                      | Purpose                                              |
| ---------------------------- | ---------------------------------------------------- |
| **HTTPS / TLS**              | Encrypts and authenticates connections               |
| **HSTS**                     | Forces browsers to use HTTPS                         |
| **Certificate validation**   | Helps detect impersonated servers                    |
| **Certificate Transparency** | Helps detect improperly issued certificates          |
| **Certificate pinning**      | Apps can restrict which certificates/keys they trust |
| **DNSSEC / DANE**            | Adds cryptographic protections to DNS-related trust  |
| **Network segmentation**     | Limits exposure between systems                      |

## Task 4: Transport Layer Security (TLS)

### 1. What is TLS?

**TLS (Transport Layer Security)** encrypts network communication.
````
Without TLS
Client ─── Cleartext ───> Server
         👀 Can be read

With TLS
Client ─── 🔒 Encrypted ───> Server
           Protected
````
TLS mainly protects:
- **Confidentiality** → others cannot read the data.
- **Integrity** → others cannot secretly modify the data.
- **Authentication** → certificates help verify the server.


#### SSL vs TLS
| Version       | Status                            |
| ------------- | --------------------------------- |
| SSL 2.0 / 3.0 | Insecure/deprecated             |
| TLS 1.0 / 1.1 | Deprecated                      |
| TLS 1.2       | Secure when properly configured |
| TLS 1.3       | Modern/current standard         |

Although people still say “SSL certificate,” modern systems actually use TLS.


### Where TLS fits in the Network Model

<img width="1200" height="800" alt="image" src="https://github.com/user-attachments/assets/d73794fa-3c58-4d41-98bf-b28907c36ba8" />


#### TLS
| Cleartext | Port | Secure |    Port |
| --------- | ---: | ------ | ------: |
| HTTP      |   80 | HTTPS  | **443** |
| FTP       |   21 | FTPS   | **990** |
| SMTP      |   25 | SMTPS  | **465** |
| POP3      |  110 | POP3S  | **995** |
| IMAP      |  143 | IMAPS  | **993** |


#### Implicit TLS vs STARTTLS
**Implicit TLS**: encryption starts immediately.
````
Client
  │
  │ 🔒 TLS immediately
  ▼
Server

HTTPS → 443
IMAPS → 993
POP3S → 995
````

**STARTTLS**: starts as a normal connection and then upgrades to TLS.
````
Client ── Cleartext ──> Server
           │
        STARTTLS
           ↓
Client ══ 🔒 TLS ══> Server
````
SMTP commonly uses this approach, especially submission on ``587``.


### HTTP vs HTTPS
| HTTP                                     | HTTPS                                                |
| ---------------------------------------- | ---------------------------------------------------- |
| 1. TCP connection                        | 1. TCP connection                                    |
| 2. HTTP request                          | 2. TLS handshake                                     |
| 3. HTTP response                         | 3. Encrypted HTTP request                            |
| No encryption                            | 4. Encrypted HTTP response                           |
| Traffic contents can be read if captured | Traffic contents cannot normally be read if captured |
| Uses `http://`                           | Uses `https://`                                      |

Therefore, someone capturing normal HTTPS traffic cannot simply read the HTTP contents like they can with cleartext HTTP.


### TLS Handshake
<img width="1200" height="645" alt="image" src="https://github.com/user-attachments/assets/8f0118f5-3f51-4ac4-81fc-a5634379308a" />

Way:

> **Hello → Certificate → Keys → Encrypted**

The client and server establish shared cryptographic keys without simply sending the resulting secret key across the network.


### TLS 1.3 Improvements

| Improvement                          | Explanation                                                                 |
| ------------------------------------ | --------------------------------------------------------------------------- |
| Faster handshake                     | Requires fewer steps to establish a secure connection                       |
| Forward secrecy                      | Past sessions remain protected even if a long-term key is later compromised |
| Removes old/weak algorithms          | Removes outdated cryptographic algorithms and options                       |
| More handshake information encrypted | Encrypts more of the TLS handshake, improving privacy                       |


### Certificates

<img width="1086" height="1448" alt="image" src="https://github.com/user-attachments/assets/873f2618-c691-4a37-b2dd-559f321ea403" />


Important certificate information includes:
| Field         | Meaning                                          |
| ------------- | ------------------------------------------------ |
| Issued To     | Who owns/uses the certificate                    |
| Issued By     | Certificate Authority (CA)                       |
| Valid From/To | Certificate lifetime                             |
| Public Key    | Used in the cryptographic authentication process |
| Fingerprint   | Hash identifying the certificate                 |

## Task 5: SSH (Secure Shell)

### 1. What is SSH?

**SSH** is used to securely access and control another computer remotely.

````
Your PC                         Server
   │                              │
   │──── 🔐 SSH Port 22 ─────────>│
   │                              │
   │<══ Encrypted Connection ════>│
   │                              │
   └──── Remote Terminal ─────────┘
````

SSH replaced insecure Telnet for most remote administration.
| Protocol | Port | Security    |
| -------- | ---: | ----------- |
| Telnet   |   23 | ❌ Cleartext |
| SSH      |   22 | ✅ Encrypted |


SSH provides **authentication**, **confidentiality**, and **integrity**.




### SSH Authentication Methods
| Method      | Meaning                       |
| ----------- | ----------------------------- |
| Password    | Username + password           |
| Public Key  | 🔑 Public/private key pair    |
| Certificate | CA-signed SSH keys            |
| MFA         | Key/password + another factor |

## SSH Config

Open the configuration:

```bash
nano ~/.ssh/config
```

| Setting        | Value               | Purpose               |
| -------------- | ------------------- | --------------------- |
| `Host`         | `webserver`         | Easy alias for server |
| `HostName`     | `10.48.145.111`     | Server IP address     |
| `User`         | `mark`              | Login username        |
| `Port`         | `22`                | SSH port              |
| `IdentityFile` | `~/.ssh/id_ed25519` | Private key to use    |

```text
Host webserver
    HostName 10.48.145.111
    User mark
    Port 22
    IdentityFile ~/.ssh/id_ed25519
```

```bash

```

instead of:


## Task 6: Password Attack

### 1. Authentication Factors
| Factor                 | Meaning                    | Example                         |
| ---------------------- | -------------------------- | ------------------------------- |
| Something you **know** | Secret knowledge           | Password, PIN                   |
| Something you **have** | Physical/device possession | Phone, security key, smart card |
| Something you **are**  | Biometrics                 | Fingerprint, face               |




### 2. Why Weak Passwords Persist

Common weak passwords are predictable:
````
123456
password
qwerty
qwerty123
Summer2024
Welcome1
````
A major problem is password reuse:
````
Website A breached
       ↓
Username + Password leaked
       ↓
Same password used elsewhere
       ↓
⚠️ Other accounts may be compromised
````


### 3. Types of Password Attacks
| Attack                     | Simple meaning                           |
| -------------------------- | ---------------------------------------- |
| 🎯 **Password Guessing**   | Guess based on information about a user  |
| 📖 **Dictionary Attack**   | Try passwords from a wordlist            |
| 🔨 **Brute Force**         | Try many/all possible combinations       |
| ♻️ **Credential Stuffing** | Try leaked credentials on other services |
| 💦 **Password Spraying**   | Few common passwords → many users        |
| 🔀 **Hybrid Attack**       | Wordlist + numbers/patterns              |

Example hybrid patterns:
````
Summer
   ↓
Summer2023
Summer2024
Summer2025
````



### 4. Wordlists & Breach Data
A wordlist is a file containing possible passwords used during password auditing.
````
/usr/share/wordlists/rockyou.txt
````

### 5. THC Hydra

Hydra automates login testing against supported network services in an authorized lab.

General syntax from your TryHackMe lesson:
````
hydra -l username -P wordlist.txt server service
````
Think of it as:
````
Hydra
 │
 ├── Username
 ├── Password Wordlist
 ├── Target
 └── Service
        ↓
   Test Logins
        ↓
   Valid credential?
````


#### Hydra Parameters
| Option            | Meaning                               |
| ----------------- | ------------------------------------- |
| `-l username`     | One username                          |
| `-L users.txt`    | Username list                         |
| `-p password`     | One password                          |
| `-P wordlist.txt` | Password list                         |
| `-s PORT`         | Custom port                           |
| `-V` / `-vV`      | Show attempts/details                 |
| `-t n`            | Number of parallel tasks              |
| `-d`              | Debug output                          |
| `-f`              | Stop after finding a valid credential |
| `-w n`            | Connection wait/timeout setting       |


More command Hydra:
| Service               | Command                                                                 |

| SSH                   | `hydra -l frank -P /usr/share/wordlists/rockyou.txt 10.48.145.111 ssh`  |

### 7. Mitigating Password Attacks

| Defense                            | What it does                                                |
| ---------------------------------- | ----------------------------------------------------------- |
| 🔑 **Strong Password Policy**      | Encourages long passwords and blocks known compromised ones |
| 🔒 **Account Lockout**             | Locks account after repeated failed attempts                |
| 🐢 **Rate Limiting**               | Slows repeated login attempts                               |
| 🤖 **CAPTCHA**                     | Makes automated login attempts harder                       |
| 📱 **MFA**                         | Requires another authentication factor                      |
| 🔐 **Passkeys**                    | Replaces passwords with cryptographic authentication        |
| 🚨 **Breached Password Detection** | Rejects passwords known from breaches                       |
| 👁️ **Behavior Analysis**          | Detects abnormal login behavior                             |
| 🌐 **IP-based Controls**           | Blocks or challenges suspicious locations/IPs               |
