3 categories from the OWASP Top 10 2025 that are related to failures in how an application manages users and their actions.



### 1. Broken Access Control

Access control determines what a user is allowed to access or do.

``User`` -> ``Application`` -> ``Check permission`` -> ``Allowed / Denied``

A vulnerability happens when the application fails to properly check permissions.

Example: ``Normal User`` -> ``/admin`` -> ``Application fails to check permission`` -> ``Admin page accessible``

This is **Broken Access Control (A01)**.




### 2. Authentication Failures

Authentication checks who the user is.
````
 Username + Password
        ↓
   Authentication
         ↓
      Correct?
    ↓          ↓
  Yes          No
   ↓            ↓
 Login       Denied
````


Authentication failures can involve problems with:
- Login mechanisms
- Password handling
- Sessions
- Account authentication

This is A07: Authentication Failures.



### Logging & Alerting Failures

Applications should record important security events.

``Login attempt`` -> ``Application`` -> ``Log event`` -> ``Monitor / Alert``

If important security events are not properly logged or monitored, attacks can happen without being noticed.

This is **A09: Logging & Alerting Failures**.

## Task 2: What is IAAA?

**IAAA** is a way to understand how an application identifies users, verifies them, controls what they can do, and records their actions.

The four steps happen in order:
````
Identity
   ↓
Authentication
   ↓
Authorization
   ↓
Accountability
````



### 1. Identity - "Who are you?"

**Identity** identifies the user or service.

Examples:
````
Username
Email
User ID
````
Example: ``User ID: 1001``

This tells the application **which account** is being used.


### 2. Authentication - "Can you prove it?"

**Authentication** verifies that the person really owns that identity.

Examples:
- Password
- OTP
- Passkey
- MFA

````
Username + Password
        ↓
   Authentication
        ↓
     Correct?
     /     \
   Yes      No
   ↓        ↓
 Login    Denied
````


### 3. Authorization - "What can you do?"

After authentication, the application checks what the user is allowed to access.

Example:
````
Normal User
    ↓
Can view profile
Can edit own profile
Cannot access admin panel
````
So authorization controls **permissions and privileges**.


### 4. Accountability - "What did you do?"

The application records user actions so activity can be investigated.

It can record:

| Element   | Meaning       | Example           |
| --------- | ------------- | ----------------- |
| **Who**   | User          | `admin`           |
| **What**  | Action        | `Deleted account` |
| **When**  | Time          | `10:30`           |
| **Where** | IP / Location | `192.168.1.10`    |


This helps security teams detect and investigate suspicious activity.

---


### Summary

| IAAA               | Simple Meaning              | Example                  |
| ------------------ | --------------------------- | ------------------------ |
| **Identity**       | Who are you?                | User ID / Email          |
| **Authentication** | Prove who you are           | Password / OTP           |
| **Authorization**  | What are you allowed to do? | Admin / User permissions |
| **Accountability** | What did you do?            | Logs / Alerts            |



> **Note**: **Identity identifies you → Authentication verifies you → Authorization controls your permissions → Accountability records your actions.**

## Task 3: A01: Broken Access Control

**Broken Access Control** happens when a server does not properly check who is allowed to access what.


### IDOR - Insecure Direct Object Reference

A common example is **IDOR**.

If a URL contains: ``?id=7``

and we change it to: ``?id=6``

and suddenly see another user's information, the application has failed to check authorization.

``Our Account`` -> ``?id=7`` -> ``Change ID`` -> ``?id=6`` -> ``Other User's Data``



### Types of Privilege Escalation
| Type           | Meaning                                              | Example                   |
| -------------- | ---------------------------------------------------- | ------------------------- |
| **Horizontal** | Same privilege level, but access another user's data | User A → User B's account |
| **Vertical**   | Gain a higher privilege level                        | Normal User → Admin       |
| **IDOR**       | Manipulate an object ID to access another object     | `?id=7` → `?id=6`         |

## Task 4: A07: Authentication Failures

**Authentication failures** happen when an application does not correctly verify a user's identity.

Common Problems
| Problem                         | Easy Meaning                                  |
| ------------------------------- | --------------------------------------------- |
| **Username Enumeration**        | Application reveals whether a username exists |
| **Weak Passwords**              | Passwords are easy to guess                   |
| **No Rate Limiting**            | Attacker can repeatedly try passwords         |
| **Login Logic Flaws**           | Bugs allow authentication to be bypassed      |
| **Bad Session/Cookie Handling** | Sessions can be linked to the wrong account   |


#### What Can Happen?

``Authentication Failure`` -> ``Application doesn't properly verify identity`` -> ``Attacker bypasses authentication`` -> ``Access another user's account``

## Task 5: A09: Logging & Alerting Failures

**Logging & Alerting Failures** happen when an application does not properly record or alert on important security events.

| Concept            | Easy Meaning                                        |
| ------------------ | --------------------------------------------------- |
| **Logging**        | Recording what happened                             |
| **Alerting**       | Warning defenders when something suspicious happens |
| **Accountability** | Knowing **who did what, when, and from where**      |
| **Investigation**  | Using logs to understand an attack                  |


Common Problems

| Failure                  | What happens                              |
| ------------------------ | ----------------------------------------- |
| Missing login logs       | Hard to know who logged in                |
| Vague error logs         | Difficult to understand the attack        |
| No brute-force alerts    | Repeated login attempts may go unnoticed  |
| No privilege-change logs | Important account changes aren't recorded |
| Short log retention      | Old attack evidence disappears            |
| Logs can be modified     | Attacker can hide their activity          |

## Task 6: Conclusion


| OWASP Category                       | Main Lesson                                                          | Key Protection                                                                                              |
| ------------------------------------ | -------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| **A01: Broken Access Control**       | Users must only access what they are authorized to access            | Check authorization **server-side on every request**                                                        |
| **A07: Authentication Failures**     | Weak authentication can allow account takeover                       | Use unique canonical usernames, rate limiting/lockout, and rotate sessions after password/privilege changes |
| **A09: Logging & Alerting Failures** | Without proper logs, attacks are difficult to detect and investigate | Log authentication and admin activity, centralize logs, retain them, and alert on suspicious behavior       |
