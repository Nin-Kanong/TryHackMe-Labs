## Task 2: AS02: Security Misconfigurations


### Security Misconfigurations

#### What is Security misconfiguration?

**Security misconfiguration** means a system is set up with unsafe or incorrect security settings.

Security misconfigurations happen when a system, server, application, or network is configured insecurely.


Example: A server is installed with a default password and the administrator never changes it.


#### Why It Matters

A small configuration mistake can give an attacker access to:
- Sensitive data
- User accounts
- Internal services
- Administrative functions
- Other systems on the network

For example: ``Insecure Configuration`` -> ``Attacker discovers it`` -> ``Unauthorized Access`` -> ``Data Theft / Privilege Escalation``

##### Example

https://www.huntress.com/threat-library/data-breach/uber-data-breach

A cloud storage bucket is accidentally configured as public.

``Private Storage`` -> ``Misconfigured as Public`` -> ``Anyone can access it`` -> ``Sensitive data exposed``

This demonstrates how a simple deployment/configuration mistake can become a major security breach.



### Common Patterns
- **Default credentials**: Default username/password is still being used.
- **Weak passwords**: Passwords are easy to guess.
- **Exposed services**: Unnecessary services are accessible from the Internet.
- **Public cloud storage**: S3, Azure Blob, or GCP buckets are accidentally public.
- **Missing authentication**: An API can be accessed without proper login.
- **Excessive permissions**: Users or services have more access than necessary.
- **Verbose error messages**: Errors reveal stack traces or system information.
- **Outdated software** Old software contains known vulnerabilities.
- **Unprotected AI/ML endpoints**: AI services are exposed without proper access control.


### How To Prevent It
- Change all **default passwords and credentials**.
- Disable **unused services and features**.
- Apply **least privilege**.
- Restrict unnecessary **Internet/network exposure**.
- Keep software and containers **patched and updated**.
- Hide sensitive information from **error messages**.
- Regularly review **cloud permissions**.
- Protect APIs and AI services with **authentication and authorization**.
- Perform **configuration reviews and security checks** before deployment.

> **AS02 = The software may be fine, but the way it is configured makes it vulnerable.**

## Software Supply Chain Failures

### Software Supply Chain Failures

#### What It Is

Software Supply Chain Failures happen when an application **depends on third-party software, libraries, APIs, packages, or AI models that are compromised, outdated, malicious, or not properly verified**.

The problem may not be in our own code. Instead, an attacker compromises something our application **trusts and uses**.

**Simple example:**

> Our application uses a malicious or compromised library → the library runs inside our application → the attacker can affect our system.

---

#### Why It Matters

Modern applications use many external components:

```text
Your Application
       ↓
Third-Party Library
       ↓
API / Package / AI Model
       ↓
Compromised Component
       ↓
Your Application becomes vulnerable
```

So, **one compromised dependency can affect many applications at once**.

---

#### Example

The **SolarWinds Orion** incident demonstrated this type of attack.

```text
Trusted Software
      ↓
Attacker compromises update/build process
      ↓
Malicious code added to update
      ↓
Customers install the trusted update
      ↓
Customers become compromised
```

The important point is that the customers **trusted the software update**.

---

#### Common Patterns

* Using **untrusted or outdated libraries**
* Installing packages without verifying them
* Automatically accepting software updates
* Using third-party AI models without checking them
* Weak or insecure **CI/CD pipelines**
* Not tracking where software components came from
* Not monitoring dependencies for vulnerabilities

---

#### How To Protect The Supply Chain

* Verify third-party libraries and packages before using them.
* Keep dependencies **updated and monitored**.
* Verify and sign software releases.
* Secure **CI/CD pipelines**.
* Track the **source/provenance** of dependencies.
* Monitor dependencies after deployment.
* Check third-party AI models before using them.
* Include supply-chain security in the **SDLC**.

---

### Easy Summary

| Section             | Meaning                                                      |
| ------------------- | ------------------------------------------------------------ |
| **What It Is**      | A trusted third-party component becomes unsafe               |
| **Why It Matters**  | One compromised dependency can affect your whole application |
| **Example**         | SolarWinds malicious software update                         |
| **Common Patterns** | Untrusted packages, outdated libraries, insecure CI/CD       |
| **Protection**      | Verify, monitor, update, and secure dependencies             |

**Key idea:**

> **AS03 = Don't blindly trust the software components your application depends on.**

## Task 4: Cryptographic Failures

### Cryptographic Failures

#### What It Is

Cryptographic Failures happen when **encryption is missing or used incorrectly**.

In simple words:

> **Sensitive data is not protected properly, so an attacker may be able to see it.**

Examples:

* Weak encryption
* Hard-coded encryption keys
* Poor key management
* Sensitive data sent without encryption

---

#### Why It Matters

Encryption protects things like:

* Passwords
* Tokens
* Personal information
* Network traffic
* Secrets

If encryption fails:

```text
Sensitive Data
      ↓
Weak / No Encryption
      ↓
Attacker accesses data
```

---

#### Common Patterns

| Problem                 | Easy meaning                                   |
| ----------------------- | ---------------------------------------------- |
| Weak algorithms         | Using old/weak encryption                      |
| Hard-coded keys         | Secret key is written directly in code         |
| Poor key management     | Keys are not protected or rotated              |
| No encryption           | Sensitive data is sent/stored openly           |
| Invalid TLS certificate | HTTPS protection is not properly configured    |
| Exposed AI secrets      | Sensitive data/keys are not properly protected |

---

#### How To Prevent It

| Protection             | Easy meaning                            |
| ---------------------- | --------------------------------------- |
| Use strong algorithms  | Use modern encryption                   |
| Secure key management  | Store keys safely                       |
| Rotate keys            | Change keys regularly                   |
| Manage certificates    | Keep TLS certificates valid             |
| Encrypt sensitive data | Protect data **at rest and in transit** |

> **Cryptographic Failure = Sensitive data is not properly protected by encryption.**
