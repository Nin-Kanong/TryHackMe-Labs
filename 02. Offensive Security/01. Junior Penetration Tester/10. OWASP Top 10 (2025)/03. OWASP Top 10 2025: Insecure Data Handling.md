### What are Cryptographic Failures?

Cryptographic failures happen when **sensitive data is not properly protected** because encryption is missing, weak, or incorrectly implemented.

Common examples include:

- Storing passwords without proper hashing.
- Using weak or outdated algorithms such as ``MD5``, ``SHA1``, or ``DES``.
- Exposing encryption keys.
- Sending sensitive data without encryption.
- Creating your own encryption instead of using trusted algorithms.


| Hash Algorithm | Full Name                  |                            Typical Length |
| -------------- | -------------------------- | ----------------------------------------: |
| **MD5**        | Message-Digest Algorithm 5 |               128-bit (32 hex characters) |
| **SHA-1**      | Secure Hash Algorithm 1    |               160-bit (40 hex characters) |
| **DES**        | Data Encryption Standard   | 64-bit block cipher (not a hash function) |





### How to Prevent Cryptographic Failures
- Use **strong**, **modern cryptographic algorithms**.
- Use **bcryptU**, **scrypt**, or **Argon2** for password hashing.
- Use trusted cryptographic libraries instead of creating our own encryption.
- Do not put passwords or access credentials in source code or repositories.
- Use secure key-management systems to protect encryption keys.
- Encrypt sensitive data both at rest and in transit.

## Task 3: A05: Injection 


<img width="600" height="500" alt="image" src="https://github.com/user-attachments/assets/3219eb3e-fc98-447b-9a62-d5502960dd9f" />


### What is Injection?
Injection happens when an application takes user input and sends it directly to another system without handling it safely.


For example, an attacker may insert malicious input into:
- SQL queries
- Operating system commands
- AI prompts
- Server-side templates
- APIs


#### Common Types
| Type                  | Meaning                                                          |
| --------------------- | ---------------------------------------------------------------- |
| **SQL Injection**     | Malicious input is inserted into a database query.               |
| **Command Injection** | Malicious input is used to execute system commands.              |
| **AI Prompts**        | User input manipulates an AI system's instructions or behaviour. |
| **SSTI**              | Malicious input is processed by a server-side template.          |


### How to Prevent Injection
- Treat **all user input as untrusted**.
- Use **prepared statements and parameterised queries** for SQL.
- Do not build SQL queries using string concatenation.
- Avoid passing user input directly to the system shell.
- Use safe APIs that do not invoke the shell.
- Validate and sanitise user input.
- Escape dangerous characters.
- Enforce strict data types.
- Filter input before the application processes it.

## Task 4: A08: Software or Data Integrity Failures



<img width="303" height="303" alt="image" src="https://github.com/user-attachments/assets/73ea9451-655a-4ada-953c-171b86957817" />



### What Are Software or Data Integrity Failures?

**Software** or **Data Integrity Failures** occur when an application trusts code, updates, or data without verifying that they are authentic, trustworthy, or unchanged.


Examples include:
- Installing software updates without verification.
- Loading scripts or configuration files from untrusted sources.
- Failing to validate data that affects application logic.
- Accepting binaries, templates, or JSON files without checking whether they have been modified.



### How to Avoid Software & Data Integrity Failures
- Establish clear trust boundaries.
- Verify the integrity of code, updates, and important data before trusting them.
- Use cryptographic checks, such as checksums, for update packages.
- Allow only trusted sources to modify critical files and artifacts.
- Apply integrity and trust controls throughout CI/CD build processes.


> **CI**: Continuous  Integration is a software development practice that involves automatically building, testing and implementing changes to an application's source code
>
> **CD**: Continuous Deployment is a software development term for deploying code to production environments automatically without any interaction from a human. For example, the automation of tests and then deployment of the code.
