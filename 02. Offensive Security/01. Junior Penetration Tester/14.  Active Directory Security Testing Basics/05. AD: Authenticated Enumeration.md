## Task 2: AS-REP Roasting

This section teaches how to find **Active Directory accounts that have Kerberos pre-authentication disabled** and retrieve their **AS-REP** hashes for offline password cracking.



#### What is AS-REP Roasting?

Normally, Kerberos uses **pre-authentication** to verify that a user is legitimate before the KDC returns an authentication response.

If an account has:
````
UF_DONT_REQUIRE_PREAUTH
````
enabled, Kerberos pre-authentication is disabled for that account.

That allows an attacker to request an **AS-REP** for the account without first authenticating as that user.

The returned AS-REP contains encrypted material that can be captured and potentially cracked offline.


Flow: ``AD User`` -> ``Pre-authentication disabled`` -> ``Request AS-REP`` -> ``Receive encrypted AS-REP`` -> ``Save hash`` -> ``Offline password cracking``



### AS-REP Roasting in Two Phases

| Phase                     | Goal                                                                            |
| ------------------------- | ------------------------------------------------------------------------------- |
| **Phase 1: Enumeration** | Find accounts with pre-authentication disabled and retrieve their AS-REP hashes |
| **Phase 2: Cracking**    | Crack the retrieved hashes offline                                              |




#### Phase 1: Enumeration – Identifying Vulnerable Accounts

**Find AD accounts that have Kerberos pre-authentication disabled and obtain their AS-REP hashes.**

In this phase, we are looking for Active Directory user accounts that have Kerberos pre-authentication disabled.


> Kerberos requires the user to prove their identity before the KDC returns an authentication response. If pre-authentication is disabled, an attacker can request an **AS-REP** for that account without knowing the user's password.

> The returned AS-REP contains encrypted information that can potentially be **cracked offline**.

**Flow**: ``Username`` -> ``Kerberos pre-authentication disabled?`` -> ``Request AS-REP`` -> ``Receive encrypted AS-REP`` -> ``Save hash`` -> ``Offline cracking``

#### After Cracking

Once an AS-REP hash has been successfully cracked, we have the user's plaintext password, that credential can then be used to authenticate as that account and continue AD enumeration.


#### Mitigations
| Mitigation                             | Purpose                                                         |
| -------------------------------------- | --------------------------------------------------------------- |
| **Enable Kerberos pre-authentication** | Prevent accounts from being vulnerable to AS-REP Roasting       |
| **Use strong passwords**               | Makes offline password cracking more difficult                  |
| **Monitor AS-REP requests**            | Helps detect unusual Kerberos activity                          |
| **Review vulnerable accounts**         | Ensure no unnecessary accounts have pre-authentication disabled |



#### Key Takeaways
- AS-REP Roasting is a low-noise, unauthenticated Kerberos attack
- Rubeus simplifies discovery on Windows; GetNPUsers.py offers manual control
- Success depends on password strength and proper pre-auth enforcement

### Identifying Service Accounts
**Service accounts** are accounts used by applications or services, not people.

Examples:
- ``svc_backup`` → backup service
- ``svc_sql`` → SQL service
- ``svc_web`` → web application

They can be important because they may have higher privileges and often use long-term passwords that don't expire frequently.

## Task 4: Enumeration With BloodHound


### A Brief History

**BloodHound** is a tool used for Active Directory enumeration and analysis.

Before BloodHound, security teams often looked at separate lists:
````
Users
Groups
Computers
Permissions
````

**BloodHound** changed this by showing the **relationships between them as a graph**.

Example like: ``User`` -> ``Group`` -> ``Computer`` -> ``Administrator``.

This makes hidden relationships and possible attack paths easier to understand.


> Traditional enumeration = lists
>
> BloodHound = graph of relationships



### The Two-Stage Attack Model

BloodHound's approach can be divided into **two stages**.


#### Stage 1: Enumeration

First, collect information from the Active Directory environment.

Tools such as:
- SharpHound
- BloodHound.py


can collect information about:
| Information | Example                  |
| ----------- | ------------------------ |
| Users       | `asrepuser1`             |
| Groups      | `Domain Admins`          |
| Computers   | `WRK`, `DC`              |
| Sessions    | Who is logged in         |
| ACLs        | Who has permissions      |
| Delegation  | Delegation relationships |

> The collected information is then loaded into BloodHound.



#### Stage 2: Targeted Attack

Once the data has been collected, BloodHound can analyze the relationships.

For example: ``User`` -> ``MemberOf`` -> ``IT Group`` -> ``AdminTo`` -> ``Computer``.

This helps identify **possible paths to a security goal**, such as reaching a highly privileged account.

The important point is that the analysis can be performed **offline using the collected data**.



### Evolution and Modern Capabilities

BloodHound has also expanded beyond traditional on-premises Active Directory.

#### Azure Support
**AzureHound** can collect information from **Microsoft Entra ID/Azure environments** as well as traditional AD environments.

````mermaid
flowchart TD
    A[On-Prem AD] --> C[BloodHound analysis]
    B[Azure / Entra ID] --> C
````


#### New Attack Primitives

Modern BloodHound can represent newer AD relationships, including **Resource-Based Constrained Delegation (RBCD)**.

Important concepts mentioned in the lesson include:
- ``AddAllowedToAct``
- ``AllowedToAct``

These describe relationships involving delegation permissions.

#### Advanced Analysis
**BloodHound** also provides more advanced ways to analyze AD relationships.

The **Butterfly algorithm**, which helps with analyzing and prioritizing relationships and potential risks.




### Defender’s Perspective

**BloodHound** is not only useful for attackers.

Defenders can use it to find:
- Misconfigurations
- Excessive privileges
- Risky access paths
- Dangerous AD relationships

The goal is to find and fix problems before attackers exploit them.



### Data Collection

**BloodHound** needs AD data before it can create its graph.

There are two important collectors:
- ``SharpHound``
- ``BloodHound.py``

> They collect information from the AD environment, which BloodHound then visualizes.

Idea flow: ``Collector`` -> ``Collect AD information`` -> ``BloodHound`` -> ``Create attack/relationship graph``.



### Understanding SharpHound

**SharpHound** is the official BloodHound data collector.

It is written in ``C#`` and can collect information such as:
| Data                     | Meaning                              |
| ------------------------ | ------------------------------------ |
| Group memberships        | Who belongs to which groups          |
| Session data             | Who is logged in where               |
| ACLs                     | Who has permissions over objects     |
| Domain trusts            | Relationships between domains        |
| Privileged relationships | Administrative access and privileges |


> SharpHound's job is mainly: ``Collect the data``.
> 
> BloodHound's job is: ``Analyze and visualize the data``.



### Types of SharpHound Collectors

| Collector        | Purpose                                |
| ---------------- | -------------------------------------- |
| `SharpHound.exe` | Main Windows collector                 |
| `AzureHound.ps1` | Collects Azure/Entra ID information    |
| `SharpHound.ps1` | Older PowerShell collector; deprecated |



- ``SharpHound.exe``: Designed for Windows machines joined to a domain and is the recommended standard method.
- ``AzureHound.ps1``: Used for collecting information from **Azure/Entra ID** environments.
- ``SharpHound.ps1``: An older PowerShell-based collector, it as **deprecated**, meaning newer approaches are preferred.



### BloodHound.py

**BloodHound.py** is a Python-based collector.

It is particularly useful when working from: ``Linux``

instead of a Windows machine.

It can collect AD information using credentials and can output data that BloodHound can import.

| Tool              | Main use                             |
| ----------------- | ------------------------------------ |
| **SharpHound**    | Windows AD data collection           |
| **AzureHound**    | Azure/Entra ID collection            |
| **BloodHound.py** | Python/Linux-based AD collection     |
| **BloodHound**    | Visualize and analyze collected data |

### Benefits and Limitations

**BloodHound Community Edition (BloodHound-CE)** is used to visualize relationships in Active Directory and identify potential attack paths.

| Benefit                       | Explanation                                                                    |
| ----------------------------- | ------------------------------------------------------------------------------ |
| Web-based interface           | Access BloodHound through a browser-based interface                            |
| Attack path visualization     | Shows relationships between users, groups, computers, and permissions          |
| AD relationship analysis      | Helps understand complex AD permissions and trust relationships                |

| Limitation              | Explanation                                                     |
| ----------------------- | --------------------------------------------------------------- |

| Large environments      | Large AD environments can produce very large and complex graphs |

## Task 6: Conclusion


| Term                                  | Definition                                                                                                                                                           |
| ------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Authenticated Enumeration**         | Collecting information from an Active Directory environment **using valid credentials**.                                                                             |
| **Active Directory (AD)**             | Microsoft's directory service used to manage **users, computers, groups, permissions, and other resources** in a Windows domain.                                     |
| **AS-REP Roasting**                   | An attack that targets AD accounts where **Kerberos pre-authentication is disabled**, allowing an attacker to obtain an AS-REP response that can be cracked offline. |
| **Kerberos Pre-Authentication**       | A Kerberos security mechanism that requires a user to prove knowledge of their password before the KDC issues an authentication response.                            |
| **Manual Enumeration**                | Using Windows commands to manually discover information about **users, groups, computers, sessions, services, and policies**.                                        |
| **PowerShell ActiveDirectory Module** | Microsoft's PowerShell module that provides commands for querying and managing Active Directory.                                                                     |
| **PowerView**                         | A PowerShell tool used for **domain and Active Directory reconnaissance/enumeration**.                                                                               |
| **BloodHound**                        | A tool that represents Active Directory relationships as a **graph**, making relationships and potential attack paths easier to analyze.                             |
| **SharpHound**                        | BloodHound's Windows data collector that gathers information from an AD environment.                                                                                 |
| **BloodHound.py**                     | A Python-based BloodHound collector that can be used from Linux.                                                                                                     |
| **Domain User**                       | A user account managed by the Active Directory domain.                                                                                                               |
| **Domain Group**                      | A group managed by Active Directory that can contain users, computers, or other groups.                                                                              |
| **Domain Computer**                   | A computer account registered in the Active Directory domain.                                                                                                        |
| **Service Account**                   | An account used by a service or application rather than normally being used by a person.                                                                             |
| **Password Policy**                   | Domain rules controlling passwords, such as **minimum length, complexity, expiration, and lockout settings**.                                                        |
| **SPN (Service Principal Name)**      | An identifier that associates a service with an account in Active Directory; accounts with SPNs can be relevant to **Kerberoasting**.                                |
| **AdminCount**                        | An AD attribute associated with accounts that have been protected as members of privileged groups.                                                                   |
| **Attack Path**                       | A sequence of relationships or permissions that can potentially connect one account/resource to a more privileged target.                                            |
