## Task 1: Introduction 

### What is lateral movement?

For example:
````mermaid
flowchart TD
    A[Compromised Workstation] -->|stolen/valid credentials| B[Server 1]
    B --> C[Server 2]
    C --> D[Domain Controller]
````


#### Why do we move laterally?

Important resources are usually spread across different machines:

| Machine                    | Possible importance                      |
| -------------------------- | ---------------------------------------- |
| **Workstation**            | Initial compromised machine              |
| **File Server**            | Sensitive documents/data                 |
| **Application Server**     | Business applications                    |
| **Server**                 | Services and privileged accounts         |
| **Domain Controller (DC)** | Active Directory / domain authentication |

So compromising one workstation doesn't necessarily give access to everything.


### What can be used for lateral movement?
| Material              | Simple meaning                           |
| --------------------- | ---------------------------------------- |
| **Valid credentials** | Username + password                      |
| **Hashes**            | Password-derived authentication material |
| **Tickets**           | Kerberos authentication tickets          |

These can potentially allow an attacker to authenticate to another machine without exploiting a vulnerability on that machine.


### Learning Objectives

In this room, we will cover the following lateral movement techniques:
- Executing commands on remote hosts using PsExec and Evil-WinRM
- Performing Pass-the-Hash attacks to authenticate with NTLM hashes directly - no plaintext password needed
- Understanding how Kerberos ticket reuse and Overpass-the-Hash extend lateral movement options
- Tunnelling through compromised hosts to reach otherwise inaccessible network segments using SSH SOCKS proxies
- Defensive measures that detect and prevent lateral movement

This is by no means an exhaustive list of lateral movement techniques, but it covers the foundational skills you'll use on every engagement. More advanced techniques — including Kerberos ticket abuse, advanced pivoting with Chisel and Ligolo-ng, and multi-host pivot chains — will be explored in later rooms.


> **Windows New Technology LAN Manager (NTLM)** is a suite of security protocols offered by Microsoft to authenticate users’ identity and protect the integrity and confidentiality of their activity.

> **Secure Shell (SSH)** refers to a cryptographic network protocol used in secure communication between devices. SSH encrypts data using cryptographic algorithms, such as Advanced Encryption System (AES) and is often used when logging in remotely to a computer or server.

> **Kerberos** is a computer network authentication protocol that operates based on tickets, allowing nodes to securely prove their identity to one another over a non-secure network.

## Task 2: What is Lateral Movement?


#### What Is Lateral Movement?
**Lateral movement** means moving from one compromised computer to another using valid credentials, hashes, or Kerberos tickets.

How it differs from initial access:
| Phase            | Explain                                                           |
| ---------------- | ----------------------------------------------------------------- |
| Initial access   | Get into the environment                                          |
| Lateral movement | Move from one compromised host to another                         |
| Authentication   | Use legitimate mechanisms such as credentials, hashes, or tickets |

Common authentication material mentioned:
| Material    | Description                                           |
| ----------- | ----------------------------------------------------- |
| Credentials | Valid username + password                             |
| Hashes      | Credential hashes that may be used for authentication |
| Tickets     | Kerberos authentication tickets                       |



### Why Does Lateral Movement Matter?

After compromising one computer, we usually **don't control the entire network**.

Important resources may be located on other machines:
- Domain Controller
- File servers
- Application servers
- Backup servers
- Privileged accounts

Example: ``We compromise WRK`` -> ``Find credentials`` -> ``Use them on SERVER1`` -> ``Find more credentials`` -> ``Reach ROOTDC``

This creates a cycle:

> **Move → Harvest → Move again**

Each new machine may provide additional credentials or access that lets we move further.



### The Three Pillars of Lateral Movement
three main categories:
| Pillar               | Simple meaning                                            |
| -------------------- | --------------------------------------------------------- |
| **Remote Execution** | Run commands on another computer                          |
| **Credential Reuse** | Use a password, hash, or ticket to authenticate elsewhere |
| **Pivoting**         | Use a compromised computer as a bridge to another network |


#### 1. Remote Execution

**Remote execution** means running commands on another Windows machine remotely.

Windows has legitimate administration protocols that can be used for this.

Example:
- **PsExec** → SMB
- **WinRM**  → PowerShell
- **WMI**    → Windows Management Instrumentation
- **DCOM**   → Windows component communication

Tools use with it:
| Tool       | Purpose                                       |
| ---------- | --------------------------------------------- |
| **PsExec** | Remote command execution through SMB/services |
| **WinRM**  | Remote PowerShell                             |
| **WMI**    | Remote Windows management/execution           |
| **DCOM**   | Another Windows remote execution mechanism    |

> **Remote Execution = ``I have access to another machine, so I can execute something there``.**


#### 2. Credential Reuse

This is where the credentials you previously harvested become useful.

Normally:
````mermaid
flowchart TD
    A[Username + Password] --> B[Authentication]
````

But Windows also supports authentication mechanisms involving **hashes and Kerberos tickets**.

##### Pass-the-Hash

If we have an NTLM hash:

``Username`` + ``NTLM Hash`` -> ``Authentication``


We may not need to know the plaintext password.

> This is called: **Pass-the-Hash (PtH)**

##### Pass-the-Ticket

Kerberos uses tickets for authentication.

If an attacker obtains a valid Kerberos ticket, it may potentially be reused to authenticate as that account.

> **Pass-the-Ticket = reuse a stolen Kerberos ticket**.

##### Overpass-the-Hash

An NTLM hash can also be used in certain techniques to obtain Kerberos authentication material.

> **Overpass-the-Hash = use an NTLM hash to obtain Kerberos-based authentication**.

So:
````
Credential Reuse
      │
      ├── Password
      ├── NTLM Hash → Pass-the-Hash
      └── Kerberos Ticket → Pass-the-Ticket
````



#### 3. Pivoting
Real networks are often **segmented**.


Our attacker may be able to reach the WebServer but **not directly reach the Domain Controller**.

Example like: 
````mermaid
flowchart TD
    A[AttackBox] --> B[WebServer]
    B -->|Internal network| C[ROOTDC]
````


The attacker might not have a direct route to ROOTDC.

The compromised WebServer can act as a **bridge**.

> This is called: **Pivoting**

Example: 
````mermaid
flowchart LR
    A[Attacker] --> B[WebServer]
    B --> C[ROOTDC]
    B --> D[SERVER1]

    subgraph Internal["Internal Network"]
        B
        C
        D
    end
````

Common tools mentioned in the room include:
- SSH tunneling
- SOCKS proxy
- Chisel
- Ligolo-ng

> **Pivoting = use a compromised machine to reach systems that your machine cannot directly reach.**



### What Do we Need for Lateral Movement?

Before any of these techniques will work, we need two things:

| Requirement                         | Meaning                                                                                                            |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| **Valid credentials**               | We need authentication material such as a plaintext password, NTLM hash, or Kerberos ticket                       |
| **Administrative access on target** | The account generally needs local administrator privileges on the target machine for many remote-execution methods |


#### 1. Valid credentials

We need something that allows you to authenticate:

````mermaid
flowchart TD
    A{OR} --> B[Username + Password]
    A --> C[NTLM Hash]
    A --> D[Kerberos Ticket]
    B --> E[Authentication]
    C --> E
    D --> E
````

Without valid authentication material, you cannot authenticate to the target.



#### 2. Administrative access

Many remote execution techniques require membership in the target machine's: ``Local Administrators``

For example, **PsExec** requires administrative access because it needs to interact with:
- ``ADMIN$`` administrative share
- Service Control Manager

**WinRM** is somewhat different because the lesson notes that members of: ``Remote Management Users``


#### Local Admin ≠ Domain Admin

``Local Administrator`` ≠ ``Domain Administrator``

A user can be an administrator on several workstations without being a Domain Admin.

#### What Is Remote Execution?

**Remote execution** means: We authenticate to another computer and run commands on that computer remotely.


Instead of:


We do:

These are legitimate Windows administration mechanisms. In a penetration test, the same mechanisms can be used when we have authorized credentials.

Most remote execution methods require the account to have the appropriate privileges on the target.

### PsExec (Impacket)

[PsExec](https://learn.microsoft.com/en-us/sysinternals/downloads/psexec) is arguably the most well-known lateral movement technique. Impacket's psexec.py (a [Python implementation](https://github.com/fortra/impacket/blob/master/examples/psexec.py) of PsExec) connects to a target over SMB, uploads a service binary, creates and starts a Windows service to execute it, and returns an interactive shell, all running as NT AUTHORITY\SYSTEM.

##### How it works
1. **Connect via SMB** → authenticates over port 445 and accesses IPC$.
2. **Access ADMIN$** → uploads a temporary service executable to ``C:\Windows\``.
3. **Create a service** → uses the Service Control Manager (``svcctl``) to create the service.
4. **Start the service** → the service runs as ``NT AUTHORITY\SYSTEM``, giving us a SYSTEM shell.
5. **Clean up** → stops/deletes the service and removes the uploaded file.

**Flow**: ``Credentials`` -> ``SMB : 445`` -> ``ADMIN$`` -> ``Upload service`` -> ``Create + Start service`` -> ``SYSTEM shell``.

##### Why is PsExec "noisy"?
Because it leaves several traces:
| Action                | Evidence          |
| --------------------- | ----------------- |
| Uploads executable    | File activity     |
| Creates service       | **Event ID 7045** |
| Starts service        | Service activity  |
| Removes files/service | Additional events |

> **PsExec = SMB → temporary service → SYSTEM shell.**

### Evil-WinRM

##### What is WinRM?

**WinRM (Windows Remote Management)** lets us remotely control a Windows computer using PowerShell.

- **5985** → **HTTP**
- **5986** → **HTTPS**

> **WinRM = Remote PowerShell**



##### What is Evil-WinRM?

[Evil-WinRM](https://github.com/Hackplayers/evil-winrm) is a tool that connects to a Windows machine through WinRM and gives us an interactive PowerShell shell.

There are two key differences between **Evil-WinRM** and **PsExec**:
| Difference         | Evil-WinRM                                                        | PsExec                                                                           |
| ------------------ | ----------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| **Shell context**  | Runs as the **authenticated user**                                | Typically provides a **SYSTEM** shell when executed with the required privileges |
| **Required group** | `BUILTIN\Administrators` **or** `BUILTIN\Remote Management Users` | Requires administrative access to the target, including access to `ADMIN$`       |
| **Protocol**       | WinRM                                                             | SMB + Service Control Manager                                                    |
| **Privilege**      | Depends on the authenticated account                              | Requires admin privileges and can result in SYSTEM execution                     |
| **Flexibility**    | More flexible because `Remote Management Users` can be sufficient | More restrictive because administrative access is required                       |

> Having access through WinRM does not automatically mean we have SYSTEM privileges. Our session runs with the privileges of the account we authenticated with.

### Other Remote Execution Methods

Besides **PsExec** and **Evil-WinRM**, there are several other ways to execute commands remotely on Windows.

The main difference is **which Windows protocol/mechanism they use**:
| Method      | Tool          | Simple meaning                   | Main use                        |
| ----------- | ------------- | -------------------------------- | ------------------------------- |
| **WMI**     | `wmiexec.py`  | Executes a process through WMI   | When PsExec doesn't work        |
| **DCOM**    | `dcomexec.py` | Executes through DCOM objects    | When Service Manager is blocked |
| **SMBExec** | `smbexec.py`  | Creates a temporary service      | Alternative to PsExec           |
| **AtExec**  | `atexec.py`   | Creates a scheduled task         | When other methods are blocked  |
| **RDP**     | `xfreerdp`    | Gives you a full Windows desktop | When you need GUI access        |
| **NetExec** | `nxc`         | Quickly runs commands remotely   | Quick one-off commands          |

Impacket tools usually use the same basic authentication methods:
| Method        | Meaning                         |
| ------------- | ------------------------------- |
| **Password**  | Log in with the user's password |
| **`-hashes`** | Authenticate using an NTLM hash |
| **`-k`**      | Authenticate using Kerberos     |

> So if we understand the authentication syntax for one Impacket tool, the others are very similar.


**NetExec** is useful when we want to run a command quickly without opening an interactive shell.

> **NetExec = authenticate → execute command → get result**

### Detection at a Glance

Each remote execution method leaves evidence in Windows Event Logs.

> **Different technique → different Event ID**

| Event ID        | Simple meaning                 | Usually related to            |
| --------------- | ------------------------------ | ----------------------------- |
| **4624 Type 3** | Network login                  | SMB, WinRM, WMI               |
| **4648**        | Explicit credentials were used | Direct credential-based login |
| **7045**        | New Windows service created    | PsExec, SMBExec               |
| **4697**        | Service installed              | PsExec, SMBExec               |
| **4698**        | Scheduled task created         | AtExec                        |
| **4688**        | New process started            | Command/process execution     |

## Task 4: Pass-the-Hash and Credential Reuse

using an NTLM hash instead of the actual password to authenticate.

Normally:
````mermaid
flowchart TD
    A[Username + Password] --> B[Authentication]
````
But sometimes we don't know the password. We only have the NT hash.


Pass-the-Hash allows:
````mermaid
flowchart TD
    A[Username + NT Hash] --> B[Authentication]
````


> We don't need to know the plaintext password. The NT hash can be enough.


### How Pass-the-Hash Works

NTLM authentication uses a **challenge-response** process.

````mermaid
sequenceDiagram
    participant C as Client
    participant S as Server

    C->>S: "I want to log in"
    S->>C: Random challenge
    Note over C: Uses NT hash to calculate<br/>authentication response
    C->>S: Response
    S->>C: Authentication OK
````

> **The plaintext password is not sent during this process.**

The NT hash is used to produce the response.

Therefore, if an attacker obtains the raw NT hash, they may be able to authenticate without knowing the password.



### The Hash Confusion Trap

There are two things people sometimes call ``NTLM hashes``:

| Type                | Where It Comes From                                                               | Format                                                     | Can You Pass-the-Hash?        |
| ------------------- | --------------------------------------------------------------------------------- | ---------------------------------------------------------- | ----------------------------- |
| **NT hash**         | SAM database, `NTDS.dit`, LSASS memory (via Mimikatz, secretsdump, etc.)          | 32 hex characters, e.g. `fa0af7f6a73316dd59f0be812dbf3c12` | **Yes**                       |
| **Net-NTLMv2 hash** | Captured from the network (via Responder, `.url` coercion, LLMNR poisoning, etc.) | Multi-field format: `user::DOMAIN:challenge:hmac:blob`     | **No** — crack it or relay it |


NT Hash `fa0af7f6a73316dd59f0be812dbf3c12` it is `32 hexadecimal characters` This is the type used for Pass-the-Hash.

**Net-NTLMv2* A captured network challenge-response looks more like: `user::DOMAIN:challenge:response:blob` It is not the user's stored NT hash.

We generally cannot simply take that captured value and use it with Pass-the-Hash.

### Other Credential Reuse Techniques
**Pass-the-Hash** is not the only way to reuse stolen authentication material. There are also techniques based on Kerberos tickets and Windows access tokens.


#### Pass-the-Ticket (PtT)
Instead of using an NT hash, we use a stolen Kerberos ticket.

``Stolen Kerberos Ticket`` -> ``Inject into session`` -> ``Authenticate as that ticket's identity``


Common tools:

Mimikatz
````
mimikatz # kerberos::ptt ticket.kirbi
````
Rubeus
````
Rubeus.exe ptt /ticket:ticket.kirbi
````


#### Overpass-the-Hash (Pass-the-Key)

This connects NTLM and Kerberos.

We start with an NT hash: ``NT Hash`` -> ``Request Kerberos TGT`` -> ``Get Kerberos ticket`` -> ``Use Kerberos authentication``


> **Overpass-the-Hash = use a hash to obtain a Kerberos ticket.**

Mimikatz can perform this with:
````
sekurlsa::pth
````
The important difference:
| Technique         | Starting material | Result                  |
| ----------------- | ----------------- | ----------------------- |
| Pass-the-Hash     | NT hash           | NTLM authentication     |
| Pass-the-Ticket   | Kerberos ticket   | Kerberos authentication |
| Overpass-the-Hash | NT hash           | Kerberos ticket         |



#### Token Impersonation 
We don't need a password, hash, or Kerberos ticket.

If we already have sufficient privileges such as SYSTEM, you may be able to access another logged-in user's Windows access token.

``SYSTEM`` -> ``Find logged-in user's token`` -> ``Impersonate token`` -> ``Act with that user's permissions``

For example, if a Domain Administrator is currently logged into the same machine, their token may exist on that machine.

> **Token Impersonation = borrow another user's existing Windows session identity.**

Tools like Incognito (available as a Meterpreter module) can list available tokens and impersonate them:
````
meterpreter > use incognito
meterpreter > list_tokens -u
meterpreter > impersonate_token "THM\\Administrator"
````



### Key Takeaway

**An NT hash can sometimes be used like a password.**

``NT Hash`` -> ``Pass-the-Hash`` -> ``Authenticate`` -> ``Remote host``

If the same local Administrator password is reused on several machines, the same NT hash may work on several machines.

``WRK`` -> ``Local Admin NT hash`` -> ``SERVER1`` -> ``Another credential`` -> ``Next host``

This is why credential reuse can create a lateral-movement chain.

#### NT Hash vs Net-NTLMv2
This distinction is very important:
|                   | NT Hash              | Net-NTLMv2                           |
| ----------------- | -------------------- | ------------------------------------ |
| Example           | `fa0af7...3c12`      | `user::DOMAIN:challenge:response...` |
| Source            | SAM, NTDS.dit, LSASS | Network capture                      |
| Pass-the-Hash?    | **Yes**              | **No**                               |
| Typical next step | Use for PtH          | Crack or potentially relay           |

## Task 6: Mitigation

Now we switch from attacker to defender.


> Every attack technique should have a security control that can stop or detect it.

| Attack                | Defense                                    |
| --------------------- | ------------------------------------------ |
| Credential harvesting | Protect LSASS, limit admin privileges      |
| Password reuse        | **LAPS** / unique local admin passwords    |
| Pass-the-Hash         | Restrict NTLM, use stronger authentication |
| PsExec                | Monitor/block unnecessary service creation |
| WinRM                 | Restrict WinRM access                      |
| Lateral movement      | Network segmentation + firewall rules      |
| Pivoting              | Segment internal networks                  |
| Credential theft      | MFA + credential protection                |
| Remote execution      | Monitor Windows security events            |



### Local Administrator Password Solution (LAPS)

**LAPS (Local Administrator Password Solution)** prevents the password-reuse problem we exploited.


Without LAPS:
````
WRK        → Administrator password A
SERVER1    → Administrator password A
             ↓
      Same NT hash
             ↓
   One stolen hash → multiple machines
````


With LAPS:
````
WRK        → Random password A
SERVER1    → Random password B
             ↓
      Different hashes
             ↓
Stolen WRK hash ≠ SERVER1 hash
````

#### What LAPS does
- Generates a unique random local Administrator password for each machine.
- Automatically rotates the password.
- Stores the password securely for authorized administrators.
- Prevents one stolen local-admin credential from being reused across many computers.

> **Windows LAPS is the modern built-in version for supported Windows systems and replaces the older Legacy LAPS.**


### Restricting Local Administrator Rights

The goal is to make lateral movement harder by giving users only the permissions they actually need.


##### Why we use it?

These techniques usually require local Administrator access:
````
PsExec
WMI
DCOM
SMBExec
````
So: ``No Local Admin`` -> ``Remote execution fails`` -> ``Lateral movement becomes harder``

| Control                 | Meaning                              |
| ----------------------- | ------------------------------------ |
| Least privilege         | Don't give normal users admin rights |
| Separate admin accounts | Daily account ≠ Admin account        |
| Tier 0                  | Domain Controllers / Domain Admins   |
| Tier 1                  | Servers / Server admins              |
| Tier 2                  | Workstations / Workstation admins    |




### Restricting NTLM Authentication

**Pass-the-Hash (PtH)** depends on NTLM. So reducing NTLM usage reduces the PtH attack surface.

#### Restrict NTLM

Group Policy can:
````mermaid
flowchart TD
````

#### Credential Guard

Credential Guard protects credentials stored in memory.

### Host Firewall Rules
Block unnecessary SMB (445), WinRM (5985), and RDP (3389) between workstations.

Allow access only from trusted management servers.

````mermaid
flowchart TD
    A[WebServer] -->|"WRK:445 ❌"| B[PsExec ❌]
````


### Network Segmentation


eparate the network into different zones:

````mermaid
flowchart TD
    A[Workstations] --X--> B[Workstations]
    C[Servers] --X--> D[Workstations]
    E[DC] --X--> F[Normal hosts]
````

- Put Workstations, Servers, and DCs in separate VLANs.
- Restrict traffic with firewalls.
- Protect DCs behind a dedicated subnet/jump hosts.
- Block unnecessary DC internet access.

Segmentation = limit where an attacker can move.



### Privileged Access Workstations (PAWs)

**PAW (Privileged Access Workstation)** is a dedicated, hardened computer used only for high-privilege administration.

````mermaid
flowchart TD
    subgraph Normal["Normal PC"]
        A[Normal PC] --> B[Daily work]
    end

    subgraph PAW["PAW"]
        C[PAW] --> D[Domain Admin / DC administration]
    end
````

> Don't put Domain Admin credentials on normal computers.

## Task 7: Conclusion


| Topic                     | What we learned                                | Key point                                        |
| ------------------------- | ---------------------------------------------- | ------------------------------------------------ |
| **Remote Execution**      | PsExec and Evil-WinRM                          | PsExec → SYSTEM; Evil-WinRM → authenticated user |
| **PsExec**                | Uses SMB and Windows services                  | `SMB → Service → SYSTEM`                         |
| **Evil-WinRM**            | Uses WinRM/PowerShell                          | `WinRM → PowerShell`                             |
| **Credential Harvesting** | Found NT hashes on compromised hosts           | NT hash can be reused                            |
| **Pass-the-Hash**         | Authenticate using NT hash without password    | `NT Hash → Authentication`                       |
| **Credential Reuse**      | Same local Admin hash worked on multiple hosts | LAPS helps prevent this                          |
| **Pivoting**              | Used WebServer to reach restricted network     | `AttackBox → WebServer → DC`                     |
| **SSH `-D`**              | Created SOCKS proxy                            | Dynamic pivot                                    |
| **ProxyChains**           | Sent TCP tools through the pivot               | `proxychains tool ...`                           |
| **Chisel**                | SOCKS tunnel over HTTP                         | Alternative to SSH                               |
| **Ligolo-ng**             | Creates a TUN interface                        | Tools work more naturally                        |
| **LAPS**                  | Unique local Admin password per machine        | Prevents password reuse                          |
| **Firewall**              | Blocks unnecessary lateral connections         | Restricts SMB/WinRM/RDP                          |
| **Network Segmentation**  | Separates workstations, servers, and DCs       | Limits attacker movement                         |
| **PAW**                   | Dedicated workstation for privileged accounts  | Protects high-value credentials                  |
| **Monitoring**            | Detects suspicious lateral movement            | Watch authentication, services, processes        |
