## Task 1: Introduction 
This room teaches us the fundamentals of password cracking and how security professionals recover passwords from password hashes during an authorized penetration test.

### What is Password Cracking?
**Password cracking** is the process of trying to recover a password from a password hash. In penetration testing, this can help assess whether users' passwords are weak or easily guessable.


#### How Password Hashing Works

A password is normally converted into a hash before being stored:
````
Password
   ↓
Hashing Algorithm
   ↓
Password Hash
````
A hash is designed to be one-way, so cracking tools try possible passwords and compare their hashes with the target hash.


#### Salting

A **salt** is a random value added to a password before hashing.
````
Password + Salt
      ↓
    Hashing
      ↓
     Hash
````
Salting makes identical passwords produce different hashes and makes precomputed cracking techniques less effective.



#### Identifying Hash Types

Different hashing algorithms produce hashes with different characteristics.
- **MD5** → commonly 32 hexadecimal characters
- **SHA-1** → commonly 40 hexadecimal characters
- **SHA-256** → commonly 64 hexadecimal characters
- **SHA-512** → commonly 128 hexadecimal characters

Tools such as ``hashid`` can help identify possible hash algorithms.

#### Password Cracking Techniques
- Dictionary attack: Tests passwords from a wordlist.
- Rule-based attack: Modifies words from a wordlist into different password variations.
- Mask attack: Generates passwords based on a known pattern.


#### Common Tools
- **Hashid**: identifies possible hash types.
- **Hashcat**: performs password recovery using several attack techniques.
- **John the Ripper**: performs password recovery using wordlists and rules.




### Learning objectives
- Explain how passwords are stored as hashes and what salting does
- Identify common hash types by their visual characteristics and with dedicated tools
- Use ``hashid`` to narrow down unknown hash formats
- Run dictionary attacks with ``Hashcat`` and ``John the Ripper``.
- Apply rule-based and mask attacks to extend coverage beyond a standard wordlist
- Choose the right tool and technique for a given hash and scenario

## Task 2: How Passwords Are Stored

**Passwords** should never be stored as plain text. Instead, systems normally store a hash of the password.

What Makes a Hash Useful?

A good cryptographic hash has four important properties:
- **One-way**: We cannot simply reverse the hash to get the original password.
- **Deterministic**: The same input produces the same hash.
- **Fixed-length**: The output has a fixed size regardless of the input length.
- **Collision-resistant**: It should be difficult for two different inputs to produce the same hash.



### Common Hashing Algorithms

| Algorithm   | Output Length           | Still Used for Passwords? | Notes                                          |
| ----------- | ----------------------- | ------------------------- | ---------------------------------------------- |
| **MD5**     | 128 bits (32 hex chars) | No                        | Fast, collision-prone, widely cracked          |
| **SHA-1**   | 160 bits (40 hex chars) | No                        | Faster than SHA-256, deprecated                |
| **SHA-256** | 256 bits (64 hex chars) | Sometimes                 | Better than MD5/SHA-1, but still fast          |
| **NTLM**    | 128 bits (32 hex chars) | Yes, legacy               | MD4-based; used for Windows authentication     |
| **bcrypt**  | ~60 chars, `$2*` prefix | Yes, recommended          | Deliberately slow and cost-configurable        |
| **Argon2**  | Variable                | Yes, recommended          | Modern, memory-hard password hashing algorithm |

MD5, SHA-1, and SHA-256 are designed mainly for general cryptographic purposes and are very fast. Password-specific algorithms such as ``bcrypt`` and ``Argon2`` are deliberately slower, making password guessing more expensive.



#### Salting

A salt is a unique random value added to each password before hashing.

``Password + Salt`` -> ``Hashing`` -> ``Stored Hash``

For example: ``stored_value = hash(password + salt)``

Each user gets a different salt, so even if two users have the same password, their stored hashes will be different.




#### Why Salting Matters

Without salt:
````
user1 → password123 → same hash
user2 → password123 → same hash
````
With different salts:
````
user1 → password123 + saltA → hash A
user2 → password123 + saltB → hash B
````
This makes pre-computed rainbow tables much less useful.


#### When Password Storage Fails

##### RockYou Breach
The **RockYou breach (2009)** exposed around ``32 million passwords`` that were stored in plain text.


ecause the passwords were already readable, attackers did not need to crack hashes.

The leaked passwords became the famous: ``rockyou.txt``

wordlist, which is commonly available on Kali Linux:
````
/usr/share/wordlists/rockyou.txt
````


##### Aptoide Breach

The ``Aptoide breach (2020)`` exposed more than 20 million accounts.

The passwords were stored using ``SHA-1 without salt``.

SHA-1 is a very fast hashing algorithm, so attackers can test a very large number of password guesses quickly.


#### Why No Salt Is Dangerous

Without a unique salt: ``Password`` -> ``SHA-1`` -> ``Same password`` → ``Same hash``

Attackers can use pre-computed rainbow tables to look for known password/hash combinations.

With a salt: ``Password + unique salt`` ->  ``SHA-1`` -> ``Different hash``

This makes pre-computed rainbow tables much less useful.

Before cracking a hash, we first need to determine which hashing algorithm created it. Using the wrong hash mode will usually produce no results.

Visual Characteristics

The easiest first check is the length and format of the hash.

| Hash Type | Length / Format   | Example                                                            |
| --------- | ----------------- | ------------------------------------------------------------------ |
| MD5       | 32 hex characters | `5f4dcc3b5aa765d61d8327deb882cf99`                                 |
| SHA-1     | 40 hex characters | `5baa61e4c9b93f3f0682250b6cf8331b7ee68fd8`                         |
| SHA-256   | 64 hex characters | `5e884898da28047151d0e56f8dc6292773603d0d6aabbdd62a11ef721d1542d8` |
| NTLM      | 32 hex characters | `8846f7eaee8fb117ad06bdd830b7586c`                                 |
| bcrypt    | ~60 characters    | `$2y$12$...`                                                       |


> MD5 and NTLM are both 32 characters, so the hash length alone cannot always identify the algorithm. Context helps.


### Using Hashid

``hashid`` analyzes a hash and gives possible algorithms.
````
hashid '5f4dcc3b5aa765d61d8327deb882cf99'
````
<img width="629" height="504" alt="image" src="https://github.com/user-attachments/assets/9a833328-1b7c-40c4-8dd1-264625329596" />


``hashid`` analyzes the hash format and lists algorithms that could potentially match its structure.

| Part                    | Meaning                                                                                               |
| ----------------------- | ----------------------------------------------------------------------------------------------------- |
| Hash                    | `5f4dcc3b5aa765d61d8327deb882cf99`                                                                    |
| Length                  | 32 hexadecimal characters                                                                             |
| `hashid` result         | Several possible hash types                                                                           |
| Most common possibility | **MD5**                                                                                               |
| Important               | The output is **not proof** that the hash is MD5; the same format can be used by multiple algorithms. |



For bcrypt, hashid gives an unambiguous result:
````
hashid '$2y$10$wJ/mZDURD4jQ0lrCEMheE.8FzMXNEBNjIkuZgEFm9VMn1m4ZP4eDG'
````
<img width="934" height="162" alt="image" src="https://github.com/user-attachments/assets/f5de9f54-e14f-4334-9723-c683234df264" />


The ``$2a$``, ``$2b$``, or ``$2y$`` prefix identifies bcrypt.

| Output                      | Meaning                                                            |
| --------------------------- | ------------------------------------------------------------------ |
| `Blowfish(OpenBSD)`         | The underlying cryptographic algorithm associated with this format |

Hashcat can also identify possible hash modes:

### Online Resources

For quick lookups, two sites are worth knowing:
- **crackstation.net**: Paste a hash, and it checks against a pre-computed lookup table of billions of entries. If the plaintext has been seen before, it comes back instantly.

https://crackstation.net/

- **hashes.com**: Identifies the hash type and attempts a lookup against a large database. Also accepts bulk hash submissions.

https://hashes.com/en/decrypt/hash

Both are useful in CTF and lab environments where speed matters.

> **Note**: On a real engagement, never submit client hashes to third-party sites. The hash may be sensitive, and any lookup creates a record of what you were cracking and when.


### Hashcat and John Formats

Once the algorithm is identified, we need the correct format or mode.

| Algorithm | Hashcat Mode | John Format  |
| --------- | -----------: | ------------ |
| MD5       |          `0` | `raw-md5`    |
| SHA-1     |        `100` | `raw-sha1`   |
| SHA-256   |       `1400` | `raw-sha256` |
| SHA-512   |       `1700` | `raw-sha512` |
| NTLM      |       `1000` | `nt`         |
| bcrypt    |       `3200` | `bcrypt`     |

Hashcat mode numbers are fixed.
- ``-m 1000`` = NTLM
- ``-m 0`` = MD5

Using the wrong mode can cause Hashcat to find no password, even if the password is in your wordlist.
