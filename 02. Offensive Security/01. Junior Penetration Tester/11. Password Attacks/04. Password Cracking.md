## Task 1: Introduction 
This room teaches us the fundamentals of password cracking and how security professionals recover passwords from password hashes during an authorized penetration test.

### What is Password Cracking?
**Password cracking** is the process of trying to recover a password from a password hash. In penetration testing, this can help assess whether users' passwords are weak or easily guessable.


#### How Password Hashing Works

A password is normally converted into a hash before being stored:
````
Password
   ↓
Hashing Algorithm
   ↓
Password Hash
````
A hash is designed to be one-way, so cracking tools try possible passwords and compare their hashes with the target hash.


#### Salting

A **salt** is a random value added to a password before hashing.
````
Password + Salt
      ↓
    Hashing
      ↓
     Hash
````
Salting makes identical passwords produce different hashes and makes precomputed cracking techniques less effective.



#### Identifying Hash Types

Different hashing algorithms produce hashes with different characteristics.
- **MD5** → commonly 32 hexadecimal characters
- **SHA-1** → commonly 40 hexadecimal characters
- **SHA-256** → commonly 64 hexadecimal characters
- **SHA-512** → commonly 128 hexadecimal characters

Tools such as ``hashid`` can help identify possible hash algorithms.

#### Password Cracking Techniques
- Dictionary attack: Tests passwords from a wordlist.
- Rule-based attack: Modifies words from a wordlist into different password variations.
- Mask attack: Generates passwords based on a known pattern.


#### Common Tools
- **Hashid**: identifies possible hash types.
- **Hashcat**: performs password recovery using several attack techniques.
- **John the Ripper**: performs password recovery using wordlists and rules.




### Learning objectives
- Explain how passwords are stored as hashes and what salting does
- Identify common hash types by their visual characteristics and with dedicated tools
- Use ``hashid`` to narrow down unknown hash formats
- Run dictionary attacks with ``Hashcat`` and ``John the Ripper``.
- Apply rule-based and mask attacks to extend coverage beyond a standard wordlist
- Choose the right tool and technique for a given hash and scenario

## Task 2: How Passwords Are Stored

**Passwords** should never be stored as plain text. Instead, systems normally store a hash of the password.

### What Makes a Hash Function Useful for This

When a user logs in:

<img width="1200" height="600" alt="image" src="https://github.com/user-attachments/assets/e358fb10-4736-466b-a1d6-153aa234a22c" />


What Makes a Hash Useful?

A good cryptographic hash has four important properties:
- **One-way**: We cannot simply reverse the hash to get the original password.
- **Deterministic**: The same input produces the same hash.
- **Fixed-length**: The output has a fixed size regardless of the input length.
- **Collision-resistant**: It should be difficult for two different inputs to produce the same hash.



### Common Hashing Algorithms

| Algorithm   | Output Length           | Still Used for Passwords? | Notes                                          |
| ----------- | ----------------------- | ------------------------- | ---------------------------------------------- |
| **MD5**     | 128 bits (32 hex chars) | No                        | Fast, collision-prone, widely cracked          |
| **SHA-1**   | 160 bits (40 hex chars) | No                        | Faster than SHA-256, deprecated                |
| **SHA-256** | 256 bits (64 hex chars) | Sometimes                 | Better than MD5/SHA-1, but still fast          |
| **NTLM**    | 128 bits (32 hex chars) | Yes, legacy               | MD4-based; used for Windows authentication     |
| **bcrypt**  | ~60 chars, `$2*` prefix | Yes, recommended          | Deliberately slow and cost-configurable        |
| **Argon2**  | Variable                | Yes, recommended          | Modern, memory-hard password hashing algorithm |

MD5, SHA-1, and SHA-256 are designed mainly for general cryptographic purposes and are very fast. Password-specific algorithms such as ``bcrypt`` and ``Argon2`` are deliberately slower, making password guessing more expensive.



#### Salting

A salt is a unique random value added to each password before hashing.

``Password + Salt`` -> ``Hashing`` -> ``Stored Hash``

For example: ``stored_value = hash(password + salt)``

Each user gets a different salt, so even if two users have the same password, their stored hashes will be different.




#### Why Salting Matters

Without salt:
````
user1 → password123 → same hash
user2 → password123 → same hash
````
With different salts:
````
user1 → password123 + saltA → hash A
user2 → password123 + saltB → hash B
````
This makes pre-computed rainbow tables much less useful.


#### When Password Storage Fails

##### RockYou Breach
The **RockYou breach (2009)** exposed around ``32 million passwords`` that were stored in plain text.


ecause the passwords were already readable, attackers did not need to crack hashes.

The leaked passwords became the famous: ``rockyou.txt``

wordlist, which is commonly available on Kali Linux:
````
/usr/share/wordlists/rockyou.txt
````


##### Aptoide Breach

The ``Aptoide breach (2020)`` exposed more than 20 million accounts.

The passwords were stored using ``SHA-1 without salt``.

SHA-1 is a very fast hashing algorithm, so attackers can test a very large number of password guesses quickly.


#### Why No Salt Is Dangerous

Without a unique salt: ``Password`` -> ``SHA-1`` -> ``Same password`` → ``Same hash``

Attackers can use pre-computed rainbow tables to look for known password/hash combinations.

With a salt: ``Password + unique salt`` ->  ``SHA-1`` -> ``Different hash``

This makes pre-computed rainbow tables much less useful.

### Hashcat and John Formats

Once the algorithm is identified, we need the correct format or mode.

| Algorithm | Hashcat Mode | John Format  |
| --------- | -----------: | ------------ |
| MD5       |          `0` | `raw-md5`    |
| SHA-1     |        `100` | `raw-sha1`   |
| SHA-256   |       `1400` | `raw-sha256` |
| SHA-512   |       `1700` | `raw-sha512` |
| NTLM      |       `1000` | `nt`         |
| bcrypt    |       `3200` | `bcrypt`     |

Hashcat mode numbers are fixed.
- ``-m 1000`` = NTLM
- ``-m 0`` = MD5

Using the wrong mode can cause Hashcat to find no password, even if the password is in your wordlist.

## Task 4: Wordlists and Attack Strategies

This section explains how to choose the right password attack method based on what we know about the target password.


### 1. Dictionary Attack

A **dictionary attack** tries passwords from a wordlist one by one against a password hash.

#### Common Wordlists
| Wordlist              | Purpose                     |
| --------------------- | --------------------------- |
| `rockyou.txt`         | Common real-world passwords |
| `SecLists`            | Targeted password lists     |
| `SecLists/Passwords/` | Password-focused wordlists  |


RockYou leak: https://cybernews.com/security/rockyou2024-largest-password-compilation-leak/

Path: ``/usr/share/wordlists/rockyou.txt``

Seclist: ``/usr/share/wordlists/SecLists/Passwords/``


How it works: ``Hash`` -> ``Wordlist`` -> ``Try password 1`` -> ``Try password 2`` -> ``Try password 3`` -> ``Match found → Password recovered``


> **RockYou2024** is a much larger collection containing billions of passwords from previous breaches.

> Dictionary attacks use passwords that people have actually used instead of generating every possible combination.



### 2. Brute-Force Attacks

A **brute-force attack** tries every possible combination of characters until the correct password is found.


How it works: ``Password Hash`` -> ``Generate candidates`` -> ``aaaa, aaab, aaac, ..., zzzz`` -> ``Match found`` → ``Password recovered``


Example: 

For a ``6-character lowercase`` password: `26⁶ = 308,915,776 combinations`.

For an ``8-character password`` using uppercase, lowercase, and digits: `62⁸ = 218,340,105,584,896 combinations`.

The search space becomes extremely large as the password gets longer.

> **Brute force = try every possible combination.**



### 3. Rule-Based Attacks

**Rule-based attacks** start with an existing wordlist and modify each word to create common password variations.

Example like:

| Rule / Change           | Original   | Result      |
| ----------------------- | ---------- | ----------- |
| Capitalise first letter | `password` | `Password`  |
| Add a number            | `password` | `password1` |
| Add special character   | `password` | `password!` |
| Substitute characters   | `password` | `p@ssw0rd`  |

Instead of trying **every possible password** like brute force, rules create realistic variations from words we already have.


#### Why Rules Are Useful

Many users make predictable changes to passwords:
````
password
Password
password1
password!
P@ssw0rd
````
So if ``password`` is already in the wordlist, rules can automatically generate these variations.

This gives **much more coverage** than a simple dictionary attack without the huge search space of full brute force.


#### Hashcat Rule Files

On the AttackBox, Hashcat rules are located here: ``/opt/hashcat/rules/``

| Rule File                   | Description                               |
| --------------------------- | ----------------------------------------- |
| `best64.rule`               | 64 effective mutations; good first choice |
| `rockyou-30000.rule`        | 30,000 rules based on RockYou analysis    |
| `d3ad0ne.rule`              | Large community rule set                  |
| `dive.rule`                 | Extensive mutation rule set               |
| `OneRuleToRuleThemAll.rule` | Popular large community rule set          |


#### John the Ripper

John has its own rules: ``/usr/local/john/run/rules/``

Common options: ``--rules=wordlist``

Applies default wordlist mutations.

````
--rules=single
````

Uses the Single rule set, which creates mutations based on usernames and names.



### 4. Mask Attacks

A **mask attack** is a smarter type of brute-force attack. Instead of trying **every possible combination**, we tell Hashcat the exact pattern the password is likely to follow.


For example, if we know the password looks like: ``Summer2026!``

We know the pattern is:
- ``1`` uppercase letter
- ``5`` lowercase letters
- ``4`` digits
- ``1`` special character

So Hashcat can focus only on passwords matching that structure.



Hashcat mask syntax uses placeholders for character sets:

| Mask | Meaning             | Example                    |
| ---- | ------------------- | -------------------------- |
| `?l` | Lowercase `a-z`     | `a`                        |
| `?u` | Uppercase `A-Z`     | `S`                        |
| `?d` | Digit `0-9`         | `2`                        |
| `?s` | Special character   | `!`                        |
| `?a` | All printable ASCII | letters + digits + symbols |


Example: `Summer2026!`

Mask: ``?u?l?l?l?l?l?d?d?d?d?s``

| Character | Mask | Meaning   |
| --------- | ---- | --------- |
| `S`       | `?u` | Uppercase |
| `u`       | `?l` | Lowercase |
| `m`       | `?l` | Lowercase |
| `m`       | `?l` | Lowercase |
| `e`       | `?l` | Lowercase |
| `r`       | `?l` | Lowercase |
| `2`       | `?d` | Digit     |
| `0`       | `?d` | Digit     |
| `2`       | `?d` | Digit     |
| `6`       | `?d` | Digit     |
| `!`       | `?s` | Special   |




### Choosing the Right Approach

Choose the attack method based on **what we know about the password**.

| Scenario                                      | Best Approach                                |
| --------------------------------------------- | -------------------------------------------- |
| No information about the password             | **Dictionary attack** with `rockyou.txt`     |
| Dictionary fails, password is likely modified | **Dictionary + rules** such as `best64.rule` |
| Password pattern is known                     | **Mask attack**                              |
| Short password + small character set          | **Brute force**                              |
| Company-specific terms are likely             | **Custom wordlist + rules**                  |


#### Summary:

| Attack                 | How It Works                                 | Best Used When                               | Example                   |
| ---------------------- | -------------------------------------------- | -------------------------------------------- | ------------------------- |
| **Dictionary Attack**  | Tries passwords from a wordlist              | No information about password                | `rockyou.txt`             |
| **Rule-Based Attack**  | Modifies words from a wordlist               | Password is likely a variation               | `password` → `Password1!` |
| **Mask Attack**        | Generates passwords matching a known pattern | Password structure is known                  | `?u?l?l?d?d?d`            |
| **Brute-Force Attack** | Tries every possible combination             | Password is short and character set is small | `aaaa`, `aaab`, `aaac`... |

### Performance notes

| Topic                    | Explanation                                                                                                        |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------ |
| **CPU fallback**         | If no GPU is available, Hashcat uses the CPU. MD5/SHA-256 can still be fast, but **bcrypt is intentionally slow**. |
| **Potfile**              | John and Hashcat save cracked passwords. If you run the same hash again, they can skip already-cracked hashes.     |
| **Session**              | Gives a long-running Hashcat attack a name so you can continue it later.                                           |
| `--session=bcrypt_crack` | Names the Hashcat session `bcrypt_crack`.                                                                          |
| `--restore`              | Resumes an interrupted Hashcat session.                                                                            |

#### Comparison (John vs Hashcat)
| Feature               | John the Ripper               | Hashcat                    |
| --------------------- | ----------------------------- | -------------------------- |
| **Main acceleration** | CPU                           | GPU + CPU fallback         |
| **MD5/SHA speed**     | Fast                          | Very fast                  |
| **Hash detection**    | Good auto-detection           | Usually requires `-m`      |
| **Unusual formats**   | Excellent                     | Good                       |
| **Rules**             | Built-in + extensible         | Large rule library         |
| **Best for**          | Quick attempts & many formats | Fast, long-running attacks |

| Step                 | What you learned                                               | Main tools/commands            |
| -------------------- | -------------------------------------------------------------- | ------------------------------ |
| 1. Identify the hash | Determine which algorithm produced the hash                    | `hashid`, `hashcat --identify` |

| 7. Compare tools     | Understand when to use John vs Hashcat                         | John / Hashcat                 |
