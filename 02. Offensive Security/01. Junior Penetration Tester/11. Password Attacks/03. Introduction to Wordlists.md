## Task 2: Wordlists

what wordlists are, where they are used, which tools use them, and where we can get or create them.

#### What is Wordlists?
A **wordlist** is a text file where each line contains a possible word, password, username, filename, directory, or other value.

Example:
````
admin
administrator
guest
test
backup
login
````
Security tools can read these entries one by one and use them during security testing.



### Where Are Wordlists Used?

#### 1. Password Guessing and Cracking

**Wordlists** can contain commonly used passwords.

Example:
````
password
password123
admin123
welcome
qwerty
````

Tools such as ``John the Ripper`` and ``Hashcat`` can use these lists to test password hashes.

Simple flow:

``Password Wordlist`` -> ``John / Hashcat`` -> ``Password Hash`` -> ``Test candidates``.



> **Purpose**: Find weak passwords during an authorized password audit.

#### 2. Service Login Brute-Forcing

Wordlists can contain:
- Usernames
- Passwords

Tools such as ``Hydra`` and ``Medusa`` can test username/password combinations against network services.

Example:
````
Username List       Password List
     ↓                   ↓
   admin              password
   user               admin123
   test               welcome
          \             /
           \           /
             Hydra
                ↓
          Login Testing
````

Common services include:
- SSH
- FTP
- HTTP

**Purpose**: Test whether a service is protected against weak or guessable credentials.

#### 3. Directory Brute-Forcing

Websites can contain directories that are not visible through normal navigation.

For example: ``https://example.com/``

might contain:
````
/admin
/backup
/uploads
/test
/dev
````

A directory wordlist might look like:
````
admin
backup
uploads
test
dev
````

Tools such as ``DirBuster``, ``Gobuster``, and ``ffuf`` test these names against the web server.

Flow: ``Directory Wordlist``-> ``Gobuster / ffuf`` -> ``Web Server`` -> ``Found / Not Found``

Seclist: https://github.com/danielmiessler/SecLists

**Purpose**: Discover hidden or unlinked web directories and files during an authorized assessment.


#### 4. Subdomain Discovery

Organizations often have multiple subdomains.

example like:
````
example.com
dev.example.com
mail.example.com
vpn.example.com
api.example.com
````
A subdomain wordlist might contain:
````
dev
mail
vpn
api
test
staging
````
Tools such as DNSRecon, Sublist3r, and ffuf can use these names during enumeration.

Flow:
````
Subdomain Wordlist
        ↓
 DNS Enumeration Tool
        ↓
   example.com
        ↓
dev.example.com
mail.example.com
vpn.example.com
````

**Purpose**: Discover additional hosts and services belonging to the authorized target.



### Common Tools That Use Wordlists

| Tool                | Purpose                         | How It Uses Wordlists                                                  |
| ------------------- | ------------------------------- | ---------------------------------------------------------------------- |
| **John the Ripper** | Password cracking               | Uses password lists to test candidates against password hashes         |
| **Hashcat**         | Password cracking               | Uses wordlists and rules to generate/test password candidates          |
| **Hydra**           | Network login testing           | Uses username and password lists to test supported login services      |
| **Medusa**          | Network login testing           | Uses username/password lists against network services                  |
| **Gobuster**        | Directory/subdomain enumeration | Uses directory or subdomain names to discover resources                |
| **ffuf**            | Web fuzzing                     | Uses wordlists to test URLs, parameters, directories, and other inputs |
| **DirBuster**       | Directory enumeration           | Tests possible directory and file names                                |
| **Burp Suite**      | Web security testing            | Uses wordlists for fuzzing parameters and other inputs                 |
| **OWASP ZAP**       | Web security testing            | Can use wordlists during fuzzing                                       |
| **Aircrack-ng**     | Wireless security auditing      | Can use password lists when auditing WPA/WPA2 networks                 |

### Building a Custom Wordlist

A good custom wordlist should contain three main categories.

#### 1. Company-Specific Keywords

These are words related specifically to the organization.

Examples:
````
product names
project names
internal features
company terminology
````
Example:
````
tryfinance
payroll
finance
portal
````


#### 2. Technology-Specific Keywords

These are terms related to technologies used by the target.

For example, if the target uses WordPress:
````
wordpress
wp-admin
wp-content
plugins
````
If it uses Laravel:
````
laravel
api
routes
storage
````

The idea is: ``Technology`` -> ``Technology-specific terms`` -> ``Custom wordlist``



#### 3. Generic Keywords

These are common words frequently found in websites and applications.

Examples:
````
api
assets
admin
dev
login
settings
````

Combining the categories: ``Company Terms`` + ``Technology Terms`` -> ``Generic Terms`` -> ``Custom Wordlist``

This can help discover directories, files, parameters, or subdomains that a generic wordlist might miss.

## Task 4: Creating and Cleaning Wordlists

This task teaches us how to take the raw information collected in Task 3, clean it, remove duplicates, and create smaller, more useful wordlists.

The overall process is: ``Raw Wordlists`` -> ``Merge`` -> ``Remove duplicates`` -> ``Lowercase`` -> ``Remove unwanted entries`` -> ``Clean Wordlists``



### Why Cleaning Matters

Raw wordlists can contain:

Duplicate words
Uppercase/lowercase variations
Very short words
Symbols
Broken or meaningless strings

For example:
````
Helios
helios
HELIOS
admin
admin
!@#
ab
````
A cleaned list could become:
````
admin
helios
````

A clean list:
- Reduces unnecessary testing
- Makes enumeration faster
- Removes duplicate entries
- Produces more realistic results



### Merging and Normalising Password Words

First, combine:
````
cewl_words.txt
raw_words.txt
````
using:
````
cat cewl_words.txt raw_words.txt | sort -u > words_raw.txt
````

#### Normalising and Filtering

The next command cleans the combined list:
````
cat words_raw.txt | tr '[:upper:]' '[:lower:]' | tr -d '\r' | grep -P '^[a-z0-9][a-z0-9._-]{4,}$' | sort -u > words_clean.txt
````
<img width="1195" height="1009" alt="image" src="https://github.com/user-attachments/assets/0fbf1475-ab72-4a96-84d4-0294de2f7c02" />


This looks complicated, but each part has one job.
| Command                      | Purpose                                       |
| ---------------------------- | --------------------------------------------- |
| `tr '[:upper:]' '[:lower:]'` | Convert uppercase to lowercase                |
| `tr -d '\r'`                 | Remove Windows carriage returns               |
| `grep -P ...`                | Keep only entries matching the desired format |
| `sort -u`                    | Sort and remove duplicates                    |
| `words_clean.txt`            | Final cleaned wordlist                        |


What Does the grep Pattern Mean?

The pattern is:

^[a-z0-9][a-z0-9._-]{4,}$

Simply understand it as: ``Start`` -> ``Letter or number`` -> ``Allowed characters`` -> ``At least 5 characters total`` -> ``End``

Allowed characters include:
````
a-z
0-9
.
_
-
````
This removes many malformed or useless entries.

### Directory and File Discovery With ffuf

**ffuf** is used to discover hidden directories and files on a web server.

For example, a website might have:
````
http://tryfinanceme.local/
````
but also contain hidden paths such as:
````
/helios/
/admin/
/backup/
````
These may not be linked from the homepage.

Our target:
````
http://tryfinanceme.local/
````
<img width="1919" height="919" alt="image" src="https://github.com/user-attachments/assets/57df64cb-5b51-442d-a022-48d5c3d9330d" />



````
ffuf -w words_clean.txt -u http://tryfinanceme.local/FUZZ -e .php,.html,/ -mc 200,301,302
````
<img width="897" height="478" alt="image" src="https://github.com/user-attachments/assets/e16bcce1-3b2a-4aba-83eb-cefa78e145ec" />


| Flag                 | Meaning                                     |
| -------------------- | ------------------------------------------- |
| `-w words_clean.txt` | Use `words_clean.txt` as the wordlist       |
| `-u`                 | Specify the target URL                      |
| `FUZZ`               | Position where ffuf inserts each word       |
| `-e .php,.html,/`    | Test different extensions                   |
| `-mc 200,301,302`    | Show responses with these HTTP status codes |


##### Understanding HTTP Status Codes

The command filters for:
````
200
301
302
````

| Status | Meaning                |
| ------ | ---------------------- |
| `200`  | Page/resource exists   |
| `301`  | Permanently redirected |
| `302`  | Temporarily redirected |

that is interesting because the ``/helios`` path returned a valid response.


#### Filtering False Positives

Sometimes a web server returns a response even when the page doesn't really exist.

For example, many nonexistent paths might return: ``404``

with the same response size.

We can compare the response size or number of lines and filter false positives.

The lesson mentions options such as:
````
-fs <bytes>
````
or:
````
-fl <lines>
````
These help remove responses that match the typical ``not found`` response.



### Brute-Forcing the Login Page With Hydra

After discovering the hidden directory, the lab tells us that the login page is:
````
http://tryfinanceme.local/helios/login.php
````
Now we use the username and password lists created earlier.
````
users.txt
     +
pass_helios.txt
     ↓
   Hydra
     ↓
Login credentials
````


#### Understanding http-post-form

The important part of the Hydra command is:
````
/helios/login.php:username=^USER^&password=^PASS^:S=THM{
````
It has three sections: ``PATH : POST DATA : SUCCESS CONDITION``


##### Login path
````
/helios/login.php
````
The location of the login handler.


##### POST data
````
username=^USER^&password=^PASS^
````

Hydra replaces: ``^USER^``

with usernames from users.txt.

And: ``^PASS^``

with passwords from pass_helios.txt.


##### Success condition
````
S=THM{
````
In this lab, a successful login contains THM{, so Hydra uses that as the success indicator.


````
hydra -L users.txt -P pass_helios.txt -f -v -t 4 tryfinanceme.local http-post-form "/helios/login.php:username=^USER^&password=^PASS^:S=THM{"
````
