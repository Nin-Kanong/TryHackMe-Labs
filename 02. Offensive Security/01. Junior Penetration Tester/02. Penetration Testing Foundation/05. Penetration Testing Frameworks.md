## Task 1: Introduction


A **penetration testing framework** is a structured methodology that tells a pentester what to do, when to do it, and how to organize the assessment.

> Framework = A roadmap for conducting a penetration test properly.

<img width="1536" height="1024" alt="image" src="https://github.com/user-attachments/assets/8d18e4d4-5f67-4f73-9237-61416ddf8a6b" />



### Why Use a Framework?
| Benefit              | Meaning                                            |
| -------------------- | -------------------------------------------------- |
| **Thoroughness**  | Important areas aren't overlooked                  |
| **Consistency**   | Different testers follow comparable processes      |
| **Compliance**    | Helps align testing with standards/regulations     |
| **Communication** | Clients understand the testing process and results |


### Major Pentesting Frameworks
| Framework                | Full Name                                                                        | Main Focus                                   | Easy Meaning                                |
| ------------------------ | -------------------------------------------------------------------------------- | -------------------------------------------- | ------------------------------------------- |
|  **OSSTMM**            | **Open Source Security Testing Methodology Manual**                              | Scientific & metrics-driven security testing | Measure security systematically             |
|  **OWASP WSTG**        | **Open Worldwide Application Security Project – Web Security Testing Guide**     | Web application security                     | Test websites/web apps                      |
| 🇺🇸 **NIST SP 800-115** | **National Institute of Standards and Technology – Special Publication 800-115** | Technical security testing                   | Government technical security testing guide |
|  **PTES**              | **Penetration Testing Execution Standard**                                       | Full penetration testing engagement          | Practical pentest lifecycle                 |
|  **ISSAF**             | **Information Systems Security Assessment Framework**                            | Detailed security assessment                 | Detailed assessment methodology             |
|  **MITRE ATT&CK**      | **MITRE Adversarial Tactics, Techniques, and Common Knowledge**                  | Adversary tactics & techniques               | Understand how real attackers operate       |

## Task 2: OSSTMM

**OSSTMM = Open Source Security Testing Methodology Manual**

It was developed by **ISECOM: Institute for Security and Open Methodologies**.

> **Metrics over opinions:**: Security should be measured, producing results that are quantifiable, repeatable, and verifiable.


### 5 Security Channels
| Channel        | Full Name               | What is Tested                                            |
| -------------- | ----------------------- | --------------------------------------------------------- |
| 👤 **HUMSEC**  | Human Security          | Social engineering & human vulnerabilities                |
| 🏢 **PHYSSEC** | Physical Security       | Doors, badges, physical access, tailgating                |
| 📡 **SPECSEC** | Wireless Communications | Wi-Fi, Bluetooth, RFID, electromagnetic signals           |
| ☎️ **COMSEC**  | Telecommunications      | Phone systems, VoIP, fax, modem infrastructure            |
| 🌐 **DATASEC** | Data Networks           | Networks, firewalls, servers, application-layer protocols |


### 4 OSSTMM Phases

<img width="1536" height="1024" alt="image" src="https://github.com/user-attachments/assets/7add89fd-7ade-468b-8005-bb4bca6eec55" />

| Phase                   | Easy Meaning       | Main Activity                                           |
| ----------------------- | ------------------ | ------------------------------------------------------- |
| 🔍 **1. Induction**     | Find & verify      | Discover assets and confirm they exist                  |
| 🔎 **2. Interaction**   | Probe & measure    | Test services and quantify exposure                     |
| 💥 **3. Inquiry**       | Test access        | Determine whether exposure leads to unauthorized access |
| 🛡️ **4. Intervention** | Address & validate | Quarantine, audit, and test controls                    |




### Risk Assessment Values (RAVs)

**RAV = Risk Assessment Value**

It measures the balance between:

<img width="1536" height="1024" alt="image" src="https://github.com/user-attachments/assets/60e4ebb0-07f7-4f4c-9357-c4ac5b1bc7b9" />

The goal is to provide a numeric, comparable security measurement rather than simply saying:

> This system looks risky.


### Reporting

OSSTMM uses:

**STAR = Security Test Audit Report**

It helps make security-testing results ``consistent``, ``auditable``, and ``comparable``.

## Task 3: OWASP WSTG

**OWASP WSTG = Open Worldwide Application Security Project – Web Security Testing Guide**

> A structured guide for testing web application security.

It contains ``90+ test cases`` covering the major attack surfaces of modern web applications.



### What WSTG Tests

| Area                         | What is Tested                                      |
| ---------------------------- | --------------------------------------------------- |
| 🔎 **Information Gathering** | Discover application information and attack surface |
| ⚙️ **Configuration**         | Server/application configuration                    |
| 👤 **Identity Management**   | User identities and accounts                        |
| 🔑 **Authentication**        | Login, passwords, password reset                    |
| 🛂 **Authorization**         | Permissions and access control                      |
| 🍪 **Session Management**    | Sessions, cookies, logout                           |
| 📥 **Input Validation**      | SQLi, XSS and other input-related issues            |
| ⚠️ **Error Handling**        | Information leakage through errors                  |
| 🔐 **Cryptography**          | Encryption and sensitive-data protection            |
| 💼 **Business Logic**        | Abuse of application workflows                      |
| 💻 **Client-Side**           | Browser/client-side vulnerabilities                 |
| 🔌 **API Testing**           | API endpoints and security controls                 |


### WSTG Across the SDLC

WSTG integrates security throughout the **Software Development Life Cycle (SDLC)**.

<img width="650" height="800" alt="image" src="https://github.com/user-attachments/assets/7b045404-3dc0-46fa-b93c-bdfbb2c32650" />


| Phase                           | Main Activity                               |
| ------------------------------- | ------------------------------------------- |
| **1. Before development**       | Define security requirements and compliance |
| **2. Definition & design**      | Architecture review and threat modeling     |
| **3. During development**       | Code reviews and security testing           |
| **4. During deployment**        | Pentest and verify production configuration |
| **5. Maintenance & operations** | Retest after updates and monitor security   |



### Risk-Based Approach
WSTG doesn't treat every vulnerability equally.

<img width="650" height="800" alt="image" src="https://github.com/user-attachments/assets/be377017-0611-49a8-b641-374e39adba08" />



### Strengths vs Limitations

| Strengths                     | Limitations                                    |
| ------------------------------- | ------------------------------------------------- |
| 90+ detailed test cases         | Full testing can take significant time            |
| Practical step-by-step guidance | Some areas require specialized expertise          |
| Excellent web-app coverage      | Easy to fall into a checklist mentality           |
| Community maintained            | Not every test is necessary for every application |
| Covers modern APIs/apps         | Tester still needs creativity and context         |

## Task 4: NIST SP 800-115

**NIST SP 800-115 = National Institute of Standards and Technology Special Publication 800-115**

**Title**: Technical Guide to Information Security Testing and Assessment

> A structured guide for testing security controls, finding vulnerabilities, and assessing exploitability.

### 3 Main Objectives

| Objective                          | Easy Meaning                                                |
| ---------------------------------- | ----------------------------------------------------------- |
| 🔍 **Identify Vulnerabilities**    | Find weaknesses                                             |
| 🛡️ **Validate Security Controls** | Check whether defenses actually work                        |
| 💥 **Assess Exploitability**       | Determine whether weaknesses can realistically be exploited |


### 3 Main Phases
````
1️⃣ PLANNING
      ↓
2️⃣ EXECUTION
      ↓
3️⃣ POST-TESTING
````
| Phase                  | What Happens                                              | Easy Meaning     |
| ---------------------- | --------------------------------------------------------- | ---------------- |
| **1. Planning**     | Define scope, objectives, rules, timing and communication | **Prepare**      |
| **2. Execution**    | Review, discover, validate vulnerabilities and pentest    | **Test**         |
| **3. Post-Testing** | Analyze results, prioritize risks and recommend fixes     | **Report & Fix** |


### Phase 2: Execution has 4 Techniques
| Technique                               | Purpose                                                  |
| --------------------------------------- | -------------------------------------------------------- |
| 📄 **Review Techniques**                | Review documentation, configurations, policies and rules |
| 🔍 **Target Identification & Analysis** | Discover hosts, ports, services and technologies         |
| 🧪 **Target Vulnerability Validation**  | Confirm vulnerabilities are real, not false positives    |
| 💥 **Penetration Testing**              | Simulate attacks to determine actual impact              |


Easy progression:

<img width="650" height="800" alt="image" src="https://github.com/user-attachments/assets/3d87e9a7-b1e3-43ce-8bc6-32a2b694a7d3" />


Not every assessment needs to reach the final penetration-testing step.


> **NIST 800-115 = Plan → Test → Report**.

## Task 5: PTES

**PTES = Penetration Testing Execution Standard**

> A practical end-to-end methodology showing how a real penetration testing engagement should be performed.

### 7 PTES Phases
| #     | Phase                              | What Happens                                        | Easy Meaning       |
| ----- | ---------------------------------- | --------------------------------------------------- | ------------------ |
| **1** | 🤝 **Pre-Engagement Interactions** | Define scope, authorization, rules, testing windows | **Plan**           |
| **2** | 🔍 **Intelligence Gathering**      | Passive & active reconnaissance                     | **Collect Info**   |
| **3** | 🎯 **Threat Modeling**             | Identify valuable targets and likely attack paths   | **Choose Targets** |
| **4** | 🔎 **Vulnerability Analysis**      | Find and verify weaknesses                          | **Find Vulns**     |
| **5** | 💥 **Exploitation**                | Exploit confirmed vulnerabilities                   | **Get Access**     |
| **6** | 🔓 **Post-Exploitation**           | Determine impact, pivot, access valuable resources  | **Show Impact**    |
| **7** | 📝 **Reporting**                   | Document findings, risk, evidence and remediation   | **Report**         |

## Task 6: ISSAF

**ISSAF = Information Systems Security Assessment Framework**

Developed by **OISSG: Open Information Systems Security Group**.

> A detailed penetration-testing methodology that models how an attacker progresses from **reconnaissance → compromise → persistence → covering tracks**.


### 3 Main Phases

| #     | Phase                           | Easy Meaning                                  |
| ----- | ------------------------------- | --------------------------------------------- |
| **1** | 📋 **Planning and Preparation** | Define scope, rules, contacts and constraints |
| **2** | ⚔️ **Assessment**               | Perform the **9-step security assessment**    |
| **3** | 📝 **Reporting and Cleanup**    | Report findings and remove testing artifacts  |

### Phase 2 — 9 Assessment Steps

| #     | Step                                         | Easy Meaning                                    |
| ----- | -------------------------------------------- | ----------------------------------------------- |
| **1** | 🔍 **Information Gathering**                 | Collect information about the target            |
| **2** | 🗺️ **Network Mapping**                      | Find hosts, ports and services                  |
| **3** | 🔎 **Vulnerability Identification**          | Find weaknesses                                 |
| **4** | 💥 **Penetration**                           | Exploit a vulnerability and gain initial access |
| **5** | ⬆️ **Gaining Access & Privilege Escalation** | Increase privileges                             |
| **6** | 📂 **Enumerating Further**                   | Explore deeper after gaining access             |
| **7** | ↔️ **Compromise Remote Users/Sites**         | Move laterally to other systems                 |
| **8** | 🔗 **Maintaining Access**                    | Establish persistence                           |
| **9** | 👣 **Covering Tracks**                       | Understand how an attacker could hide evidence  |

### Flow

ISSAF's methodology is still useful for learning, but the framework is no longer actively maintained, so its old tool-specific guidance should not be relied upon for current engagements.

> **ISSAF = Plan → 9-step Assessment → Report & Cleanup**

## Task 7: MITRE ATT&CK

**ATT&CK = Adversarial Tactics, Techniques, and Common Knowledge**

> MITRE ATT&CK describes how real-world attackers behave.

Unlike ``PTES``, it does not tell you how to perform a pentest from start to finish. It helps you categorize and describe attacker behavior.

Official: https://attack.mitre.org/

### ATT&CK Structure
| Level                | Meaning              | Easy Meaning    | Example                                |
| -------------------- | -------------------- | --------------- | -------------------------------------- |
| 🎯 **Tactic**        | Attacker's objective | **WHY**         | Initial Access                         |
| ⚔️ **Technique**     | Method used          | **HOW**         | Phishing — `T1566`                     |
| 🔹 **Sub-Technique** | Specific variation   | **Exactly HOW** | Spearphishing Attachment — `T1566.001` |


Example:
````
🎯 Tactic
Initial Access
     ↓
⚔️ Technique
Phishing (T1566)
     ↓
🔹 Sub-Technique
Spearphishing Attachment (T1566.001)
````


### Enterprise ATT&CK Tactics
| #      | Tactic                       | Easy Meaning                         |
| ------ | ---------------------------- | ------------------------------------ |
| **1**  | 🚪 **Initial Access**        | Get into the target                  |
| **2**  | ▶️ **Execution**             | Run malicious code                   |
| **3**  | 🔗 **Persistence**           | Maintain access                      |
| **4**  | ⬆️ **Privilege Escalation**  | Gain higher permissions              |
| **5**  | 🥷 **Defense Evasion**       | Avoid detection                      |
| **6**  | 🔑 **Credential Access**     | Steal credentials                    |
| **7**  | 🔍 **Discovery**             | Learn about the environment          |
| **8**  | ↔️ **Lateral Movement**      | Move to other systems                |
| **9**  | 📦 **Collection**            | Gather target data                   |
| **10** | 🎮 **Command and Control**   | Communicate with compromised systems |
| **11** | 📤 **Exfiltration**          | Steal/send data out                  |
| **12** | 💥 **Impact**                | Damage or disrupt systems            |
| **13** | 🔎 **Reconnaissance**        | Gather information before attack     |
| **14** | 🛠️ **Resource Development** | Prepare infrastructure/resources     |



### Mapping Pentest Findings to ATT&CK
| Finding                           | Tactic            | Technique                                         |
| --------------------------------- | ----------------- | ------------------------------------------------- |
| 📧 Phishing attachment            | Initial Access    | **Spearphishing Attachment — T1566.001**          |
| 🌐 Exploit public web application | Initial Access    | **Exploit Public-Facing Application — T1190**     |
| 🔑 Dump credentials               | Credential Access | **OS Credential Dumping — T1003**                 |
| ↔️ Move using stolen credentials  | Lateral Movement  | **Use Alternate Authentication Material — T1550** |
| 📂 Access data repository         | Collection        | **Data from Information Repositories — T1213**    |



### PTES vs MITRE ATT&CK
| PTES                                  | MITRE ATT&CK                          |
| ------------------------------------- | ------------------------------------- |
| 📋 Tells you **how to run a pentest** | ⚔️ Describes **attacker behavior**    |
| Has engagement phases                 | Has tactics & techniques              |
| Scope → Test → Report                 | Tactic → Technique → Sub-technique    |
| Testing methodology                   | Knowledge base                        |
| **How to conduct the assessment**     | **How to describe what attackers do** |

> ATT&CK complements PTES — it does not replace it.

## Other Notable Frameworks
These are more specialized frameworks. we choose them depending on the application, industry, cloud environment, or regulatory requirements.

| Framework          | Full Name                                                                         | Main Focus                | Easy Meaning                                     |
| ------------------ | --------------------------------------------------------------------------------- | ------------------------- | ------------------------------------------------ |
| 🌐 **WASC**        | **Web Application Security Consortium Threat Classification**                     | Web applications          | Classify web threats/vulnerabilities             |
| ☁️ **CSA CCM**     | **Cloud Security Alliance – Cloud Controls Matrix**                               | Cloud environments        | Assess cloud security controls                   |
| 📱 **OWASP MASTG** | **OWASP Mobile Application Security Testing Guide**                               | Android & iOS             | Test mobile app security                         |
| 💳 **PCI DSS**     | **Payment Card Industry Data Security Standard – Penetration Testing Guidelines** | Payment/card environments | Pentest systems handling cardholder data         |
| 🏦 **CBEST**       | **CBEST Threat Intelligence-Led Assessments**                                     | UK financial institutions | Simulate realistic threats against banks/finance |



### When Should I Use Which?
````
🌐 Web threat classification
        → WASC

☁️ Cloud environment
        → CSA CCM

📱 Android / iOS App
        → OWASP MASTG

💳 Payment / Cardholder Data
        → PCI DSS

🏦 UK Bank / Financial Institution
        → CBEST
````


### MASTG + MASVS

These two often work together:

**MASTG** = tells we **HOW to test** a mobile application.

**MASVS** = **Mobile Application Security Verification Standard**, defining WHAT security requirements the app should meet.
````
MASVS → 📋 What should be secure?
              +
MASTG → 🔍 How do we test it?
````


### PCI DSS

For environments that **process, store, or transmit cardholder data**, PCI DSS requirements can shape the pentest.

> **External + Internal testing → Network segmentation testing → Regular/required testing**


### CBEST

CBEST differs from a normal generic pentest because it is threat-intelligence-led.
````
🕵️ Threat Intelligence
        ↓
🎯 Identify realistic threats
        ↓
⚔️ Simulate those threats
        ↓
🏦 Test financial institution
````


#### Summary:
| Need                                   | Framework                |
| -------------------------------------- | ------------------------ |
| General pentest lifecycle              | 🎯 **PTES**              |
| Web application pentest                | 🌐 **OWASP WSTG**        |
| Mobile application pentest             | 📱 **OWASP MASTG**       |
| Cloud security controls                | ☁️ **CSA CCM**           |
| Payment/card environment               | 💳 **PCI DSS**           |
| UK financial-sector threat-led testing | 🏦 **CBEST**             |
| Real attacker behavior                 | ⚔️ **MITRE ATT&CK**      |
| Scientific security measurement        | 🔬 **OSSTMM**            |
| Government-style security assessment   | 🇺🇸 **NIST SP 800-115** |

## Task 9: 

**There is no single “best” penetration-testing framework. Choose based on the engagement.**


### 4 Selection Criteria
| # | Criteria                       | Easy Meaning                              | Example                              |
| - | ------------------------------ | ----------------------------------------- | ------------------------------------ |
| 1 | 🎯 **Scope & Target Type**     | **What are you testing?**                 | Web → OWASP WSTG, Mobile → MASTG     |
| 2 | ⚖️ **Regulatory & Compliance** | **What rules must you follow?**           | Card data → PCI DSS, UK bank → CBEST |
| 3 | 📊 **Repeatable Results**      | **Need measurable comparison?**           | OSSTMM → RAV metrics                 |
| 4 | 👥 **Team & Resources**        | **What can your team realistically use?** | General pentest → PTES               |


### Scenario

| Scenario                               | Best Framework(s)                    | Why                                                                         |
| -------------------------------------- | ------------------------------------ | --------------------------------------------------------------------------- |
| 🏥 Hospital web + internal network     | **PTES + OWASP WSTG + MITRE ATT&CK** | PTES structures the pentest; WSTG covers web; ATT&CK maps attacker behavior |
| 🏦 UK bank                             | **CBEST**                            | Designed for UK financial institutions                                      |
| 🌐 SaaS web platform + compare results | **OSSTMM + OWASP WSTG**              | OSSTMM measures results; WSTG tests the web app                             |
| 📱 Mobile banking + credit cards       | **OWASP MASTG + PCI DSS**            | Mobile testing + payment-card compliance                                    |
