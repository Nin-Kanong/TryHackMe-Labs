## Task 1: Introduction 

#### What is mobile application security?

We use mobile applications every day, such as banking apps, Facebook, Telegram, and shopping apps. These applications may store sensitive information, including passwords, personal details, payment information, and messages.

**Mobile application penetration testing** is the process of testing an application's security to find weaknesses that attackers could exploit.

For example, a tester might check whether a banking app stores passwords insecurely or allows someone to access another user's information.


#### Why is mobile security important?

Mobile applications often handle sensitive information. If an application has security weaknesses, attackers might be able to:
- Steal usernames, passwords, or personal information.
- Access data belonging to other users.
- Exploit insecure communication between an app and its server.
- Abuse excessive permissions to access device features.
- Modify or manipulate application behavior.

> The goal of a penetration tester is to identify these problems and help developers fix them before attackers exploit them.

#### How are mobile applications built?
To test a mobile application properly, we need to understand its basic structure.

| Component | Easy explanation | Example |
|---|---|---|
| Application package | The file used to distribute and install an app. | Android uses `.apk` files; iOS commonly uses `.ipa` packages. |
| Application code | Instructions that tell the app what to do. | Code that handles login and payments. |
| Permissions | Access rights an app requests from the operating system. | Camera, contacts, or location access. |
| Local storage | Data saved directly on the device. | Settings, cached data, or saved tokens. |
| Backend server | A remote system that processes requests and stores data. | A bank's server checking your login. |
| Network communication | How the app sends and receives information. | HTTPS requests between the app and server. |



### Learning Objectives
- Understand what mobile application penetration testing is and why it matters from a red team perspective
- Know how mobile applications are structured and what is inside a package
- Follow a clear methodology when approaching a mobile application test
- Perform static analysis on a mobile application package to find vulnerabilities
- Understand how dynamic analysis works and what techniques it involves
- Recognise the most common vulnerability categories found in mobile applications
- Apply static analysis skills in a practical CTF-style challenge

## Task 2: How Mobile Applications work 

A mobile application is not just one file. It is a package containing everything needed for the app to work.

It usually contains:
- **Code**: Instructions that make the app function.
- **Configuration files**: Settings that control how the app behaves.
- **Resources**: Things like images, text, and layouts.
- **Assets**: Additional files the app uses.



### The Application Package
A **mobile application package** is a file that contains everything needed to install and run a mobile app.

It includes:
- **Application code**: Instructions that make the app work.
- **Configuration files**: Settings that tell the operating system how the app should behave.
- **Supporting files**: Images, fonts, text, and local databases.


### The Manifest and Configuration File

The **manifest** is a file that tells the operating system how a mobile application should work.

It contains:
- **App name and version**: Identifies the application.
- **Permissions**: Specifies what the app can access, such as the camera or location.
- **App components**: Defines parts of the app and how they work.
- **Accessibility settings**: Determines whether other applications can access certain components.



### The Sandbox Model

A **sandbox** is a security feature that keeps each mobile application isolated from other apps.
- **App isolation**: Each app runs in its own protected environment.
- **File protection**: Apps generally cannot access other apps' private files.
- **Process protection**: Apps are restricted from directly interacting with other apps' processes.
- **Security testing**: Testers look for vulnerabilities or misconfigurations that weaken this protection.


### Application Components

Mobile applications contain different components, and each component has a specific job.

#### Common Android components include:
- **Activity**: Displays the app's user interface, such as a login screen.
- **Service**: Performs tasks in the background.
- **Broadcast Receiver**: Responds to system-wide or app events.
- **Content Provider**: Manages and shares app data with other components or apps.

#### Internal vs. Exported
- **Internal**: Only accessible within the application under normal conditions.
- **Exported**: Can be accessed by other applications, subject to applicable permissions and security controls.


> **Example**: If a banking app accidentally exposes a sensitive component, another app might be able to trigger it without proper authorization.




### Why Package Structure Matters
Understanding a mobile app's package structure helps penetration testers know where to look for security **vulnerabilities**.
- **Manifest**: Contains app configuration and permission information.
- **Compiled code**: Contains the app's logic and functionality.
- **Resource files**: May contain strings, API keys, or other hardcoded values.

## Task 3: The mobile Pentesting Methodology

**Mobile penetration testing** follows a **systematic**, **repeatable process** to make sure the application is checked thoroughly instead of just running tools randomly.
- **Four phases**: Testing is divided into four stages to organize the work.
- **Repeatable process**: Follow the same structured approach so important areas are not missed.
- **OWASP Mobile Top 10**: A security guide used to help classify and understand common mobile application risks.


### The Phases of a Mobile Penetration Test

A mobile application penetration test typically follows four phases:

<img width="1200" height="382" alt="image" src="https://github.com/user-attachments/assets/8c0beaa8-b526-461b-bc14-f2b5952872df" />

| Phase | What does it mean? | What does the tester do? | Example | Goal |
|---|---|---|---|---|
| 1. Reconnaissance | Collect information about the mobile application before testing. | Identify the app's purpose, users, features, backend services, platform, and application package. | Identify an Android app's login page and the server it communicates with. | Understand the application and identify areas to test. |
| 2. Static Analysis | Examine the application without running it. | Unpack the application package, inspect configuration files, review compiled code, check permissions, and search for hardcoded secrets. | Find an unnecessary permission or an API key stored in the app's files. | Identify potential vulnerabilities in the app's code and configuration. |
| 3. Dynamic Analysis | Run the application and observe its behavior in real time. | Inspect network traffic, monitor data handling, test application components, and check authentication and authorization. | Check whether sensitive data is transmitted securely or whether a user can access another user's information. | Investigate and verify vulnerabilities by observing the app in operation. |
| 4. Reporting | Document the vulnerabilities and explain how to fix them. | Record the issue, reproduction steps, evidence, severity, potential impact, and recommended remediation. | Report insecure data storage and recommend a secure storage method. | Help developers understand, prioritize, and fix security weaknesses. |


### The OWASP Mobile Top 10

**[OWASP Mobile Top 10](https://owasp.github.io/www-project-mobile-top-10/)** is a security guideline that lists 10 major categories of risks in mobile applications. Penetration testers use it to identify, classify, and report vulnerabilities. The current published list is the **2024 edition**.

> **Open Web Application Security Project (OWASP)**

#### The 10 mobile security risks:
| Code | Risk category | explanation | Example |
|---|---|---|---|
| M1 | Improper Credential Usage | Handles passwords, API keys, or tokens insecurely. | An API key is exposed in the app. |
| M2 | Inadequate Supply Chain Security | Uses insecure or compromised third-party components. | An app includes a vulnerable library. |
| M3 | Insecure Authentication/Authorization | Does not properly verify users or their access rights. | A user accesses another person's account data. |
| M4 | Insufficient Input/Output Validation | Fails to properly validate data entering or leaving the app. | Malicious input causes unexpected behavior. |
| M5 | Insecure Communication | Does not adequately protect data transferred over a network. | Sensitive information is sent over unprotected HTTP. |
| M6 | Inadequate Privacy Controls | Fails to sufficiently protect users' privacy. | The app collects unnecessary personal information. |
| M7 | Insufficient Binary Protections | Lacks protections against reverse engineering or unauthorized modification. | An attacker modifies the app's behavior. |
| M8 | Security Misconfiguration | Security settings are configured incorrectly. | An unnecessary component is exposed to other apps. |
| M9 | Insecure Data Storage | Stores sensitive information insecurely on the device. | Passwords are saved in a plain-text file. |
| M10 | Insufficient Cryptography | Uses weak or incorrectly implemented encryption. | Sensitive data is encrypted using an outdated algorithm. |



### Testing Approaches

Mobile penetration testing has three main approaches. The difference is how much information and access the tester has before testing begins.

| Approach | Explanation | What does the tester have? | Example | Advantage |
|---|---|---|---|---|
| Black-box Testing | Test the app without prior internal knowledge, like an external attacker. | The application itself, with little or no internal documentation or source code. | Install a banking app and test its login and accessible features without seeing its code. | Simulates an external attacker's perspective. |
| Grey-box Testing | Test with some knowledge or access, but not complete access. | Perhaps test credentials, API documentation, or limited source code. | Log in using a test account and check whether you can access another user's data. | Balances realistic testing with better coverage. |
| White-box Testing | Test with full internal knowledge of the application. | Source code, documentation, architecture details, and other relevant information. | Review the app's source code to identify insecure password handling or access controls. | Enables deeper and more thorough analysis. |


### Scope and Reporting

**Mobile application penetration testing** must have a clearly defined scope and a proper report to ensure testing is authorized, safe, and useful.

#### Testing Scope
The scope defines what the penetration tester is allowed to test.
| Item | Explanation | Example |
|---|---|---|
| Application version | Specifies which version of the app can be tested. | Android app version 2.0. |
| Backend environment | Defines which servers or APIs are included. | A staging API, not the production server. |
| Permitted actions | Lists what testing activities are allowed. | Test login security but do not perform destructive actions. |
| Authorization | Confirms permission to conduct the assessment. | Written approval from the application owner. |


#### Vulnerability Severity

After finding vulnerabilities, testers classify them by severity to help developers decide which issues to fix first.

| Severity | Meaning | Example |
|---|---|---|
| Critical | Extremely serious issue that could cause major damage. | An exploitable flaw allows an attacker to take over many user accounts. |
| High | Serious weakness with significant security impact. | Unauthorized access to sensitive customer information. |
| Medium | A vulnerability with a meaningful but more limited impact. | Sensitive information is exposed under specific conditions. |
| Low | A weakness with limited security impact. | An application reveals unnecessary technical information. |

**Static analysis** is the process of examining a mobile application's files and code without running the application. Testers inspect the app package, configuration, permissions, and code to find potential security weaknesses.

> **Static Analysis**: The process of analyzing malware without executing it, but in a controlled environment.



### Obtaining and Unpacking the Package

First, obtain the mobile app package from an authorized source, such as the developer, a device, or an app store. Then, use a **decompiler** to unpack the app and make its compiled code easier to read.

The recovered code may not be identical to the original source code, but it can help testers understand how the app works and find potential security vulnerabilities.


### Reading the Manifest: Android

The **Android Manifest** (``AndroidManifest.xml``) contains the app's configuration and security settings. During static analysis, testers check for:
- **Over-requested permissions**: The app requests more permissions than it needs.
- **Exported components**: Activities, services, or content providers may be accessible to other apps without proper protection.
- **Insecure configuration flags**: Settings may weaken the app's security.


### Reading the Manifest: iOS

On iOS, ``Info.plist`` is a configuration file that defines important app settings and behavior.

During static analysis, testers check for:
- **Permissions and configuration**: Does the app request unnecessary access or have insecure settings?
- ``NSAllowsArbitraryLoads``: If set to true under ``NSAppTransportSecurity``, it relaxes Apple's App Transport Security protections and may allow insecure HTTP connections.
- **Security risks**: Unencrypted communication can expose sensitive data.


#### OWASP mapping:
- **M5**: Insecure Communication
- **M8**: Security Misconfiguration




### Hunting for Hardcoded Secrets

**Hardcoded secrets** are sensitive values written directly into an application's code or files.

Examples include:
- **API keys**: Used to access services.
- **Passwords**: Login credentials.
- **Encryption keys**: Used to protect or decrypt data.
- **Access tokens**: Used to authenticate requests.
- **Internal URLs**: Addresses of internal servers or APIs.

Where do testers look?
- Decompiled application code.
- String resources and configuration files.
- Local database files included in the package.
- iOS ``Info.plist`` and other ``.plist`` files.


##### Why is this dangerous?

An attacker who obtains the application package may extract these secrets and misuse them, potentially gaining unauthorized access to services or data.




### Using MobSF for Automated Scanning
**MobSF (Mobile Security Framework)** is a free, open-source tool that automatically analyzes mobile applications to find potential security vulnerabilities.

What can MobSF detect?
- **Permissions**: Identifies potentially unnecessary permissions.
- **Hardcoded secrets**: Finds exposed API keys, passwords, or tokens.
- **Insecure configurations**: Detects potentially unsafe app settings.
- **Security weaknesses**: Highlights other possible vulnerabilities in the application.


How do testers use it?
1. Upload the mobile app package to MobSF.
2. Run an automated security scan.
3. Review the generated security report.
4. Investigate findings manually to confirm issues and identify problems automated tools might miss.



### Mapping to OWASP Mobile Top 10

Static analysis findings can be classified using the OWASP Mobile Top 10 to help testers describe security risks.

| OWASP Category | Meaning | Example |
|---|---|---|
| M1: Improper Credential Usage | Sensitive credentials are handled insecurely. | An API key or password is hardcoded in the app's code. |
| M8: Security Misconfiguration | App settings or security controls are configured incorrectly. | An unnecessary component is exposed to other apps. |

## Task 5: Dynamic Analysis

**Dynamic analysis** means testing a mobile application while it is running to observe its actual behavior.

Testers check:
- **Network traffic**: What data the app sends and receives.
- **Data storage**: How the app stores sensitive information on the device.
- **Application logs**: Whether sensitive information appears in logs.
- **App components**: How the app responds when its components are tested.

#### Static vs. Dynamic Analysis

| Analysis Type | Explanation | Purpose | Example |
|---|---|---|---|
| Static Analysis | Examines code and files without running the app. | Finds potential security weaknesses in code and configuration. | Find a hardcoded API key. |
| Dynamic Analysis | Tests the app while it is running. | Identifies weaknesses in the app's actual behavior. | Observe whether sensitive data is sent insecurely. |


> **Static Analysis**: The process of analyzing malware without executing it, but in a controlled environment.

> **Dynamic Analysis**: The process of analyzing malware by running it in a controlled environment like a sandbox.



### Traffic Interception

**Traffic interception** means monitoring the network communication between a mobile app and its server while the app is running.

Testers use a **proxy tool**, such as Burp Suite, to inspect requests sent by the app and responses received from the server.


They check:
- **Data protection**: Is sensitive data transmitted securely using HTTPS/TLS?
- **Authentication tokens**: Are login tokens handled securely?
- **Data exposure**: Is sensitive information sent in plain text?
- **Third-party connections**: Does the app communicate with unexpected external services?

> **Example**: If a banking app sends a password over unencrypted HTTP, an attacker monitoring the network might be able to read it.

> **Transport Layer Security (TLS)** is a cryptographic protocol that secures communications over a network. It provides authentication through the use of certificates, integrity by detecting tampering and confidentiality by encrypting the data.



### SSL Pinning
**SSL pinning** is a security mechanism that makes a mobile app trust only a specific certificate or set of certificates when connecting to a server.

How it works:
1. A tester configures a proxy, such as Burp Suite, to inspect network traffic.
2. The proxy presents its own certificate to the app.
3. If SSL pinning detects that the certificate does not match the expected certificate, the app may block the connection.

#### Why is it important?
**SSL pinning** helps prevent attackers from intercepting and reading an application's network traffic.

**[Objection](https://github.com/sensepost/objection)**: is a mobile runtime exploration tool that can help authorized testers bypass SSL pinning during testing. It can also inspect app data and interact with application components at runtime.



### Runtime Instrumentation
**Runtime instrumentation** means observing or changing an application's behavior while it is running, without needing to modify its original source code.


#### What is Frida?
**[Frida](https://frida.re/)** is a tool that allows penetration testers to inspect and interact with a running application.

Testers can use Frida to:
- **Inspect functions**: Find classes and methods used by the app.
- **Hook functions**: Monitor or modify what a function does.
- **Inspect memory**: Examine data handled by the app while it runs.
- **Test security controls**: Check whether authentication or other protections can be bypassed.



### Insecure Logging

**Insecure logging** happens when a mobile app writes sensitive information into system logs, where it may be exposed to unauthorized access.

#### What do testers check?
- **Usernames and passwords**: Are login details written to logs?
- **Authentication tokens**: Are session tokens exposed?
- **API responses**: Do logs contain private user data?
- **Debug messages**: Is unnecessary sensitive information recorded in the production app?

> **Example**: A banking app writes a user's authentication token to system logs. If another app can access those logs, the token could be exposed.

## Task 6: Common Mobile Vulnerabilities

The **common security vulnerabilities found in mobile applications**, based on the OWASP Mobile Top 10.


### Insecure Data Storage
**Insecure data storage** happens when a mobile app saves sensitive information in an unsafe location or format, allowing unauthorized people or apps to access it.

Common examples:
- **Plain-text files**: Passwords or tokens are saved without protection.
- **Local databases**: Sensitive information is stored without appropriate encryption.
- **Shared storage**: Private data is saved somewhere other apps may access.
- **Cached data**: Sensitive API responses remain stored insecurely on the device.

#### How do testers check?
Examine the app's files, local databases, and storage locations while using the application to identify exposed sensitive information.

> **OWASP mapping: M9 - Insecure Data Storage.**



### Insecure Authentication and Session Management

**Insecure authentication and session management** happen when a mobile app does not properly verify a user's identity or protect their login session.

Common examples:
- **Weak session tokens**: Tokens do not expire properly or can be reused after logout.
- **Insecure token storage**: Login tokens are saved in unprotected files.
- **Missing re-authentication**: The app allows sensitive actions without asking the user to verify their identity again.
- **Biometric bypass**: Fingerprint or face recognition checks can be bypassed if implemented incorrectly.

> **Example**: A banking app checks fingerprint authentication only on the device. If an attacker can bypass that local check, they might access protected features.


> **OWASP mapping: M3 - Insecure Authentication/Authorization**.



### Exposed Application Components

**Exposed application components** happen when parts of a mobile app are accessible to other apps without proper security protection.

Common examples:
- **Exposed activities**: Other apps can open sensitive screens.
- **Exposed services**: Other apps can trigger sensitive functions.
- **Exposed content providers**: Other apps may access private data.


> **Example**: A banking app exposes a component that displays account details. Another app might access that component and retrieve private information if proper access controls are missing.

> **OWASP mapping: M8 - Security Misconfiguration.**


### Insufficient Binary Protections

**Insufficient binary protections** mean a mobile app lacks adequate security measures to prevent attackers from reverse-engineering, modifying, or repackaging it.

Three important protections:
- **Code Obfuscation**: Makes the app's code harder to understand after decompilation.
- **Tamper Detection**: Detects whether someone has modified the application.
- **Root/Jailbreak Detection**: Checks whether the device has elevated privileges that could make the app easier to attack.

> **Example**: An attacker modifies a banking app to bypass a security check and then installs the modified version.

> **OWASP mapping: M7 - Insufficient Binary Protections.**
