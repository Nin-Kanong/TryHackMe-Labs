## Task 1: Introduction 

When a penetration tester attacks a system, a Security Operations Center (SOC) analyst may detect and investigate that activity.

- **Detection**: Security tools detect suspicious activity, such as repeated failed logins or directory brute-force requests.
- **Logging**: Systems record events, including source IP addresses, login attempts, and requests.
- **Alerting**: A SIEM tool analyzes logs and generates alerts for suspicious behavior.
- **Investigation**: The SOC analyst checks whether the activity is a real threat or a false positive.
- **Response**: The security team may block an IP, disable a compromised account, or isolate an affected system.
- **Blind spots**: Some attacks may go undetected because of missing logs, misconfigured tools, or detection rules that are too weak.

> A pentester tests how systems can be attacked; a SOC analyst detects, investigates, and responds to those attacks. Understanding both sides helps us identify weaknesses in security monitoring.

### Why the Blue Team Matters to us
- **Stealth**: Understand how security tools detect attacks and how monitoring thresholds affect detection during authorized tests.
- **Better Reporting**: Explain not only the vulnerability but also whether the client's security tools detected it and what needs improvement.
- **Realistic Testing**: Simulate realistic attacker behavior to test how effectively a security team detects and responds to threats.

> Understanding both offensive and defensive security helps pentesters test defenses, identify detection gaps, and provide more valuable recommendations.

## Task 2: Inside the SOC: How Defenders Operate

### Key Lesson: The Target Data Breach

In 2013, Target's security system detected malware, but the alert was not properly escalated. The attack continued for 18 days.

#### Why did it happen?

- **Detection worked**: FireEye detected suspicious malware.
- **Human failure**: The alert was not escalated appropriately.
- **Process failure**: Automatic threat deletion was disabled.
- **Impact**: Millions of payment card and customer records were compromised.

#### What Is a SOC?

A **Security Operations Center (SOC)** is a team responsible for monitoring, detecting, investigating, and responding to security threats.

> Detecting an attack is not enough. Security teams must investigate alerts, escalate serious threats, and respond quickly. As a pentester, we should test both the security technology and the organization's ability to respond.

---

### The SOC Tier Structure

A **SOC (Security Operations Center)** uses different levels to investigate security alerts.

| Tier          | Role                           | Main Responsibilities                                                                           |
| ------------- | ------------------------------ | ----------------------------------------------------------------------------------------------- |
| L1            | Triage Analyst                 | Monitor alerts, identify false positives, and escalate suspicious activity.                     |
| L2            | Incident Handler               | Investigate incidents, identify affected systems, collect evidence, and coordinate containment. |
| L3            | Threat Hunter / Senior Analyst | Hunt for hidden threats, perform advanced forensics, and create detection rules.                |
| L4 (optional) | SOC Management / Engineering   | Manage the SOC team and maintain security platforms and infrastructure.                         |

> Example: Detecting a Brute-Force Attack
>
> 1. L1: Receives an alert about repeated failed logins and checks whether it is suspicious.
> 
> 2. L2: Investigates the source IP, affected accounts, and possible compromise.
>  
> 3. L3: Hunts for related activity that the existing detection rules may have missed.

---


### The Analyst Workflow

An **L1** analyst follows four main steps when handling security alerts.

| Step           | Action            | What It Means                                                        |
| -------------- | ----------------- | -------------------------------------------------------------------- |
| 1. Monitor     | Review alerts     | Check new and unassigned alerts on the dashboard.                    |
| 2. Triage      | Classify alerts   | Decide whether an alert may be a real threat or a false positive.    |
| 3. Investigate | Check evidence    | Review logs, source IPs, and related events for suspicious patterns. |
| 4. Decide      | Close or escalate | Document false positives or escalate suspicious incidents to L2.     |

> Example: If many failed logins trigger an alert, the analyst checks the logs and source IP. If the activity looks malicious, they escalate it to L2 for deeper investigation.

---


### Measuring SOC Performance: MTTD and MTTR

Two important metrics measure how quickly a SOC detects and handles attacks.

| Metric | Meaning              | Key Point                                                  |
| ------ | -------------------- | ---------------------------------------------------------- |
| MTTD   | Mean Time to Detect  | Average time taken to detect an attack or breach.          |
| MTTR   | Mean Time to Respond | Average time from detection until the threat is contained. |

> Examples from the Provided Text
- **[MTTD: 181 days (IBM 2025)](https://www.ibm.com/think/x-force/2025-cost-of-a-data-breach-navigating-ai)**: The reported average time to identify a breach.
- **[MTTR: 60 days (IBM 2025)](https://cloud.google.com/blog/topics/threat-intelligence/m-trends-2026)**: The reported average time to contain a breach after detection.
- **Mandiant median dwell time: 14 days (2026)**: The median time attackers remained undetected in the cases studied.

These reports measure different populations, so their figures are not directly interchangeable.

> Lower MTTD means detecting attacks faster. Lower MTTR means containing threats faster. Both reduce the time attackers have to cause damage.


---


### Alert Fatigue: The Human Bottleneck

> **Alert fatigue** happens when SOC analysts receive too many alerts, especially false positives, causing them to overlook real threats.

- **Too many alerts**: Analysts receive hundreds of security alerts.
- **False positives**: Many alerts are harmless, creating unnecessary workload.
- **Reduced attention**: Analysts may ignore or underestimate genuine threats.
- **Missed incidents**: Real attacks can go unnoticed or remain uninvestigated.


> **Example**: FireEye detected malware, but the legitimate alert was not properly escalated, allowing the attack to continue.


How to Reduce Alert Fatigue
- Tune detection rules to reduce false positives.
- Prioritize critical alerts.
- Automate repetitive triage tasks.
- Follow clear escalation procedures.

> Security tools can detect threats correctly, but human and process failures can still allow attacks to succeed.

### Looking Ahead

A **SIEM (Security Information and Event Management)** is a platform that collects and analyzes security logs from multiple systems in one central location to detect suspicious activity.

| Function    | Purpose                                                           |
| ----------- | ----------------------------------------------------------------- |
| Collect     | Gather logs from servers, firewalls, endpoints, and applications. |
| Normalize   | Convert different log formats into a consistent structure.        |
| Correlate   | Connect related events to identify suspicious patterns.           |
| Detect      | Generate alerts when potential threats are identified.            |
| Investigate | Search logs to understand what happened during an incident.       |

> A SIEM detects repeated failed logins across multiple accounts and generates an alert for the SOC analyst.

> SIEM centralizes logs and helps security teams detect and investigate threats. Splunk is one example of a SIEM platform.

### What a SIEM Does (and What It Does Not)

A **SIEM (Security Information and Event Management)** collects and analyzes security logs in one central platform.

| Function         | Meaning                                                          |
| ---------------- | ---------------------------------------------------------------- |
| 1. Aggregation   | Collect logs from different systems and devices.                 |
| 2. Normalization | Convert logs into a consistent format.                           |
| 3. Indexing      | Store and organize events for fast searching.                    |
| 4. Correlation   | Connect related events to identify suspicious patterns.          |
| 5. Alerting      | Notify analysts when detection rules identify potential threats. |

##### What a SIEM Cannot Do

A SIEM cannot automatically understand and resolve every threat. It needs properly configured detection rules, accurate log data, and skilled analysts to investigate alerts and respond.

> Example: A user has repeated failed logins, then successfully logs in and accesses sensitive files. A SIEM can correlate these events and generate an alert.

> SIEM collects, organizes, searches, connects, and alerts on security events. The tool supports security analysts; it does not replace them.

### The Splunk Data Model

Splunk uses fields to organize, identify, and search security events.

| Field        | Meaning                                           | Example                  |
| ------------ | ------------------------------------------------- | ------------------------ |
| `index`      | Container that stores data                        | `botsv1`                 |
| `source`     | Input or file that generated the event            | `WinEventLog://Security` |
| `sourcetype` | Defines the event's data format and parsing rules | `WinEventLog:Security`   |
| `host`       | Device that generated the event                   | `WIN-PC01`               |
| `_time`      | Timestamp of the event                            | `2026-10-28 10:30:00`    |
| `_raw`       | Original, unparsed event text                     | Raw log message          |

#### Important Differences

- `index` = Where the data is stored.
- `source` = Where the data came from.
- `sourcetype` = What format the data uses.
- `host` = Which device generated the data.


Example Splunk search:
```
index=botsv1 sourcetype=suricata
```
This searches the `botsv1` index for events classified as `suricata`.

> These fields help SOC analysts filter logs and investigate suspicious activity efficiently.

### Normal vs. Suspicious: Reading the Timechart
When we look at event volume over time, not every spike is an attack. Knowing what normal looks like is half the job.


| Pattern               | Normal Activity                                      | Suspicious Activity                                                                   |
| --------------------- | ---------------------------------------------------- | ------------------------------------------------------------------------------------- |
| Security Event Volume | Steady activity with normal business-hour increases. | Sudden spikes, especially outside business hours.                                     |
| Failed Logons         | Occasional mistakes across different users.          | Hundreds of failures from one IP targeting one account.                               |
| HTTP 404 Errors       | Occasional broken links.                             | Thousands of rapid 404s with sequential URLs, possibly indicating directory scanning. |
| New Service Installs  | During scheduled maintenance or updates.             | Unexpected installations with random names outside maintenance windows.               |

> Suspicious activity does not automatically mean an attack. Analysts must investigate and confirm the evidence before deciding.

## Task 4: Reading the logs: Attack Patterns in Event Data

Attack Signatures and Windows Event IDs.

Security analysts look for specific log events and patterns that may indicate an attack:

| Activity                         | Evidence to Monitor             | Possible Threat                                       |
| -------------------------------- | ------------------------------- | ----------------------------------------------------- |
| Brute-force attack (Hydra)       | Repeated failed logins          | Password guessing                                     |
| Directory scanning (Gobuster)    | Many HTTP 404 responses         | Web directory enumeration                             |
| New Windows service installation | Event ID 7045 in the System log | Possible malware or unauthorized service installation |

##### Example: WannaCry (2017)

**WannaCry ransomware** spread across many systems. Installing a new Windows service could generate Event ID 7045, giving defenders a potential warning signal.

> Event ID 7045 means a service was installed. It does not automatically mean malware; analysts must investigate the service name, path, timing, and related events.


---


### The Event IDs That Matter

These Windows Event IDs help analysts identify suspicious activity and investigate attacks.


#### Authentication Events (sourcetype: WinEventLog:Security):

sourcetype: ``WinEventLog:Security``:

| Event ID | What It Records                            | Why It Matters                                                                                                                              |
| -------- | ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------- |
| 4624     | Successful logon                           | Confirms access. Logon Type 2 = interactive/console, Type 3 = network/SMB, Type 10 = Remote Desktop (RDP).                                  |
| 4625     | Failed logon                               | Repeated failures from one IP or against one account may indicate a brute-force attack.                                                     |
| 4672     | Special privileges assigned to a new logon | Common for administrator accounts. Unexpected privileged logons, especially involving service accounts or unusual hours, may be suspicious. |



#### Account Management (sourcetype: WinEventLog:Security):

sourcetype: ``WinEventLog:Security``:

| Event ID | What It Records                        | Why It Matters                                                                                                                         |
| -------- | -------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| 4720     | User account created                   | May indicate an unauthorized account created to maintain persistent access, especially outside normal account-provisioning procedures. |
| 4732     | Member added to a local security group | Adding an account to the Administrators group may indicate privilege escalation or unauthorized access.                                |


#### Process and Service Events:
| Event ID | Sourcetype             | What It Records       | Why It Matters                                                                                                                               |
| -------- | ---------------------- | --------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| 4688     | `WinEventLog:Security` | New process created   | Helps analysts identify suspicious programs or commands. Command-line auditing can provide additional details about the commands executed.   |
| 7045     | `WinEventLog:System`   | New service installed | May indicate malware installation or unauthorized remote execution. Investigate unexpected services, especially outside maintenance windows. |


#### Defense Evasion:

| Event ID | What It Records            | Why It Matters                                                                                                                                             |
| -------- | -------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1102     | Security audit log cleared | May indicate an attempt to hide evidence of suspicious activity. Investigate who cleared the log, when it happened, and whether the action was authorized. |

### Know Normal to See Abnormal

## Know Normal to See Abnormal

A **behavioral baseline** is a record of what normal activity looks like. SOC analysts compare current events against that baseline to identify suspicious behavior.

| Event / Pattern             | Normal Activity                                       | Suspicious Activity                                                                  |
| --------------------------- | ----------------------------------------------------- | ------------------------------------------------------------------------------------ |
| 4625 - Failed logon         | Occasional failures from different users or IPs.      | Hundreds of failures from one IP in minutes, followed by a successful login (4624).  |
| 4672 - Special privileges   | Known administrators logging in at expected times.    | Unexpected privileged logons from unusual accounts, times, or machines.              |
| 7045 - New service          | Service installed during scheduled maintenance.       | Unexpected service with a random name or executable stored in a temporary folder.    |
| HTTP 404 - Not found        | Occasional errors from broken links or mistyped URLs. | Hundreds of rapid 404 responses from one IP, possibly indicating directory scanning. |
| 1102 - Security log cleared | Rarely occurs during documented maintenance.          | Log cleared unexpectedly, potentially to hide evidence.                              |

### Important Takeaway

> **Baseline** → **Identify deviations** → **Investigate** → **Confirm**.

> Suspicious activity is not automatically malicious. Check the event details, timestamps, accounts, source IPs, and related logs before drawing conclusions.

### Hunting in the Logs: Three SPL Exercises


#### Exercise 1: Detecting Automated Attack Tools via Network IPS

A **flood of network-layer attack** signatures from a single IP is one of the clearest brute-force and scanning indicators a defender can detect. 

The FortiGate UTM's IPS engine logs every blocked or detected attack signature with the source IP. Run this query in the Splunk search bar:

````spl
index=botsv1 sourcetype=fgt_utm subtype=ips | stats count by srcip | sort -count | head 1
````
<img width="1918" height="660" alt="image" src="https://github.com/user-attachments/assets/ac790224-e55a-4183-acf0-2bd3a3875149" />


This query identifies which IP address generated the most IPS security alerts against Wayne Corp's network.

After running the query in Splunk, open the Statistics tab. You will see the source IP address (srcip) and the number of events (count).

If one IP triggers thousands of IPS events, it may indicate automated scanning or attack activity.


#### Detecting Brute-Force Attacks

SOC analysts can detect brute-force attacks by counting failed login attempts from each source IP address.

Example SPL query:
````spl
index=botsv1 sourcetype=WinEventLog:Security EventCode=4625 | stats count by src_ip | sort -count
````

- ``EventCode=4625``: Finds failed Windows logon events.
- ``stats count by src_ip``: Counts failed logons from each source IP.
- ``sort -count``: Sorts the results from highest to lowest.

> The Wayne Corp BOTSv1 scenario focuses on web application attacks, so the FortiGate IPS query is more relevant to that exercise.

### Exercise 3: Spotting New Service Installations

The WannaCry dropper installed itself as a Windows service. PsExec does the same thing during lateral movement. Let's look for service installations in the BOTSv1 data:

````
index=botsv1 sourcetype=WinEventLog:System EventCode=7045 | table _time, Service_Name, Service_File_Name
````

Investigating New Windows Services

- Suspicious indicators: Executables in temporary folders, user profile folders, randomized filenames, or multiple installations within minutes.
- `%SystemRoot%`: A Windows environment variable that usually points to `C:\Windows`.
- Verification: Check the service path, installation time, and change management records.

Example: `tenable_mw_scan` is associated with the Nessus vulnerability scanner and may be legitimate.

> A suspicious-looking service is not automatically malware. Investigate its location and context before deciding.

### Connecting the Dots

Across the three exercises, the detection logic is the same:

1. **Collect**: Search the relevant logs (authentication, web, or system logs).
2. **Aggregate**: Count events by source IP or another relevant field.
3. **Detect**: Identify unusual activity that exceeds the normal baseline.
4. **Investigate**: Check whether the activity is malicious or legitimate.

Example:
- **Authentication logs** → Detect brute-force attacks.
- **Web logs** → Detect directory scanning.
- **System logs** → Detect suspicious service installations.

> Count events, compare against a baseline, and investigate outliers.

## Task 5: When Thing Go Wrong: The Incident Response Lifecycle

The **Incident Response Lifecycle** is a structured process that helps security teams manage security incidents from detection to recovery.

| Phase                   | Purpose                                                |
| ----------------------- | ------------------------------------------------------ |
| 1. Preparation          | Prepare tools, playbooks, and response teams.          |
| 2. Detection & Analysis | Identify suspicious activity and confirm the incident. |
| 3. Containment          | Limit the attack and prevent further damage.           |
| 4. Eradication          | Remove malware and fix the root cause.                 |
| 5. Recovery             | Restore systems and monitor for further attacks.       |

#### Example: Brute-Force Attack

1. **Detect**: SIEM alerts on repeated failed logins.
2. **Contain**: Block malicious activity or restrict the affected account.
3. **Eradicate**: Remove any unauthorized access or persistence.
4. **Recover**: Restore normal access and monitor the account.

> Detect → Contain → Eradicate → Recover → Improve. Preparation supports every stage, helping the team respond quickly and consistently.

---

### The NIST SP 800-61 Rev 2 Lifecycle

The most widely adopted framework for incident response comes from [NIST Special Publication 800-61 Revision 2](https://csrc.nist.gov/pubs/sp/800/61/r2/final), NIST defines four phases for handling security incidents.

| Phase                                     | Main Purpose                                                          |
| ----------------------------------------- | --------------------------------------------------------------------- |
| 1. Preparation                            | Prepare tools, policies, playbooks, and trained staff.                |
| 2. Detection and Analysis                 | Detect suspicious activity, investigate logs, and confirm incidents.  |
| 3. Containment, Eradication, and Recovery | Stop the attack, remove the threat, and restore systems safely.       |
| 4. Post-Incident Activity                 | Review what happened, document lessons learned, and improve defenses. |

NIST SP 800-61 Rev 2 also establishes three key definitions worth knowing:

| Term              | Meaning                                                             |
| ----------------- | ------------------------------------------------------------------- |
| Event             | Any observable activity in a system or network.                     |
| Adverse Event     | An event that causes a negative consequence.                        |
| Security Incident | An event that violates or threatens security policies or practices. |

#### Example: Brute-Force Attack

1. **Preparation**: Configure SIEM detection rules.
2. **Detection and Analysis**: Identify repeated failed logins and investigate the source.
3. **Containment, Eradication, and Recovery**: Block malicious activity, remove unauthorized access, and restore safe operations.
4. **Post-Incident Activity**: Improve detection rules and update the response playbook.

> The lifecycle is a continuous cycle. Lessons learned from each incident improve preparation for future incidents.


---


### The SANS PICERL Model

We will encounter a second framework in the field: the SANS **PICERL** model. It breaks the response into six phases:

| SANS Phase      | Maps to NIST Rev. 2 Phase              |
| --------------- | -------------------------------------- |
| Preparation     | Preparation                            |
| Identification  | Detection and Analysis                 |
| Containment     | Containment, Eradication, and Recovery |
| Eradication     | Containment, Eradication, and Recovery |
| Recovery        | Containment, Eradication, and Recovery |
| Lessons Learned | Post-Incident Activity                 |


#### SANS vs. NIST

- **SANS**: Uses six phases, separating Containment, Eradication, and Recovery into distinct operational steps.
- **NIST Rev. 2**: Uses four phases, grouping Containment, Eradication, and Recovery into one phase.

> Both frameworks describe the same incident response process but organize it differently. Organizations may use NIST for policies and SANS for detailed operational playbooks.

### Case Study: When Frameworks Fail

#### Target Breach (2013)
- **What happened**: FireEye detected BlackPOS malware, but the alert was not properly escalated.
- **Failure**: The detection system worked, but the response process failed.
- **Impact**: 40 million payment card records were stolen.
- **Lesson**: Critical alerts need clear escalation procedures and timely action.

### SolarWinds SUNBURST (2020)

- **What happened**: Attackers inserted a backdoor into SolarWinds Orion software updates.
- **Failure**: The backdoor remained undetected for months.
- **Impact**: Approximately 18,000 organizations received the compromised update.
- **Lesson**: Organizations need strong monitoring, long enough log retention, and supply-chain security.

### Key Comparison

| Breach     | Main Failure                  | Key Lesson                                                        |
| ---------- | ----------------------------- | ----------------------------------------------------------------- |
| Target     | Alert escalation and response | Act on critical alerts quickly.                                   |
| SolarWinds | Detection and monitoring      | Detect hidden threats and retain logs long enough to investigate. |

> Security tools alone are not enough. Organizations need effective processes, trained analysts, rapid escalation, and continuous improvement.

## Task 6: Know Your Enemy: Threat Intelligence Basic

**MITRE ATT&CK** is a knowledge base that describes real-world attacker behaviors using a common language.

- **NIST Incident Response Lifecycle**: Explains how to manage and respond to incidents.
- **MITRE ATT&CK**: Explains what attackers do, including their tactics and techniques.
- **Threat Intelligence**: Helps security teams share information about attackers and identify useful indicators to investigate or block.

> Example: A pentester uses credential brute-forcing. A defender can map that behavior to a known MITRE ATT&CK technique and use it to improve detection rules.

> MITRE ATT&CK helps pentesters and defenders describe attacker behavior consistently and improve security detection.


---


### MITRE ATT&CK: A Shared Dictionary for Adversary Behavior

**MITRE ATT&CK** is a knowledge base that helps security professionals describe and understand real-world attacker behavior.

| Level         | Meaning                                                 | Example                                                     |
| ------------- | ------------------------------------------------------- | ----------------------------------------------------------- |
| Tactic        | Why the attacker acts (goal)                            | Credential Access                                           |
| Technique     | How the attacker achieves the goal                      | Brute Force (T1110)                                         |
| Sub-technique | A specific method                                       | Password Guessing (T1110.001)                               |
| Procedure     | How a real attacker or malware implements the technique | A threat group using a particular method to steal passwords |

- **Cyber Kill Chain**: Describes an attack as seven general stages.
- **MITRE ATT&CK**: Describes attacker tactics and techniques in a flexible, non-linear model.

> Tactic = why, technique = how, sub-technique = specific method, procedure = real-world implementation.

---


### The Pyramid of Pain: Not All Indicators Are Equal

The **Pyramid of Pain** explains how difficult it is for attackers to adapt when defenders detect and block different types of indicators.

| Level      | Indicator              | Pain Level  | Example                                     |
| ---------- | ---------------------- | ----------- | ------------------------------------------- |
| 6 - Top    | TTPs                   | Tough       | Detecting brute-force behavior (T1110).     |
| 5          | Tools                  | Challenging | Identifying a specific attack tool.         |
| 4          | Network/Host Artifacts | Annoying    | Detecting suspicious URL patterns.          |
| 3          | Domain Names           | Simple      | Blocking a command-and-control (C2) domain. |
| 2          | IP Addresses           | Easy        | Blocking an attacker's source IP.           |
| 1 - Bottom | Hash Values            | Trivial     | Blocking a malware file by its MD5 hash.    |

- **Low-level indicators**: Attackers can change a file hash or IP address relatively easily.
- **High-level indicators**: Changing their behavior or TTPs requires more effort and may force them to redesign their attack methods.

> Example: Blocking one malicious IP may stop current traffic, but detecting the behavior of repeated suspicious connections can help identify the attacker even after the IP changes.

> The higher up the Pyramid of Pain you detect, the harder it generally is for an attacker to adapt.

Detecting Suspicious Process Execution

- **Event ID 4688**: Records when a new process is created in Windows.
- **Parent process**: The process that launches another process.
- **Suspicious behavior**: A web server or service unexpectedly launching `cmd.exe` or `powershell.exe` may indicate command execution by an attacker.
- **MITRE ATT&CK**: Maps to T1059 - Command and Scripting Interpreter.

> Investigate unexpected parent-child process relationships. A web server launching a command interpreter is suspicious, but not automatic proof of an attack.



Establish a Process Baseline

- **BOTSv1 lab**: Unusual parent-child process relationships are easier to identify because there are fewer events.
- **Production environment**: Many legitimate processes launch `cmd.exe` or `powershell.exe`.
- **Baseline**: Learn which parent-child process relationships are normal for each system.
- **Detection**: Alert on unusual relationships that deviate from normal behavior.

> Example: A web server unexpectedly launching `powershell.exe` may indicate an attacker executing commands.

> Do not alert on every command interpreter. Establish a baseline and investigate unusual process behavior.

### The Purple Team Feedback Loop

Purple Teaming means Red Team and Blue Team work together to improve security.

1. **Red Team**: Performs an authorized attack technique.
2. **Blue Team**: Checks whether security tools detect the activity.
3. **Analyze**: Identify detection gaps.
4. **Improve**: Update detection rules and security controls.
5. **Retest**: Repeat the technique to verify the improvement.

> Red Team simulates a brute-force attack → Blue Team checks SIEM alerts → both improve detection rules → retest.

> Purple teaming combines offensive and defensive skills to make security detection and response stronger.
