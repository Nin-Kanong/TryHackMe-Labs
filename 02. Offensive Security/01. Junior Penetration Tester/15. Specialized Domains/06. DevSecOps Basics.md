## Task 2: DevOps: A New Era

Since its inception, Developer Operations (DevOps) has become a significant influence in modern Software Development, Deployment and Operations. But where did the term come from?

### The Story of DevOps

A long time ago, we used waterfalls.

### Waterfall Model
### Traditional Software Development — Summary

This is the **traditional**, **hierarchical approach** to software development, where each team has separate responsibilities.

| Team                  | Responsibility                                 |
| --------------------- | ---------------------------------------------- |
| System Administrators | Maintain servers, systems, and infrastructure. |
| Developers            | Build software and add new features.           |
| QA Engineers          | Test software to make sure it works correctly. |

> Each team works separately and passes work to the next team. This can create communication delays and cause security issues to be discovered late in development.


<img width="1751" height="1750" alt="image" src="https://github.com/user-attachments/assets/04f02d1a-8282-4593-9868-b51a6a977837" />


In traditional development, teams worked separately, which often caused delays, communication problems, and blame when something went wrong.

| Problem            | Easy Explanation                                                              |
| ------------------ | ----------------------------------------------------------------------------- |
| Blame Game         | Teams blamed each other when bugs or problems occurred.                       |
| Communication Gaps | Developers, sysadmins, and QA did not communicate effectively.                |
| Backlog            | Bugs and security issues accumulated without being fixed.                     |
| Delayed Releases   | Separate teams slowed down development and deployment.                        |
| Security Issues    | Vulnerabilities were often discovered late and left unresolved.               |
| Poor Scalability   | The process became difficult to manage as projects and customer demands grew. |

> Traditional development created separate teams, slow communication, and delayed fixes. This led to the need for a better approach, such as DevOps, where teams collaborate throughout the software development process.


---



### Agile Model

### Agile Methodology — Summary

**Agile** is a flexible software development approach introduced to solve problems with traditional Waterfall development. It focuses on teamwork, customer feedback, and adapting to changes.


##### Four Values of the Agile Manifesto

| Value                        | Easy Explanation                                                             |
| ---------------------------- | ---------------------------------------------------------------------------- |
| Individuals and Interactions | People and teamwork are more important than tools and processes.             |
| Working Software             | Focus on delivering software that works rather than excessive documentation. |
| Customer Collaboration       | Work closely with customers to understand their needs.                       |
| Responding to Change         | Adapt to changes instead of strictly following the original plan.            |

> Agile makes software development more flexible through teamwork, continuous feedback, frequent releases, and adapting to change.


<img width="3084" height="1750" alt="image" src="https://github.com/user-attachments/assets/bca4c8cc-b816-4a95-af13-2d2d6f687e42" />

> Companies now value team collaboration and rely on self-organising teams, focusing on clients and plenty of room for change and flexibility.


DevOps combines Development (Dev) and Operations (Ops) to improve teamwork, communication, and software delivery through automation and integration.

| Concept                     | Easy Explanation                                                     |
| --------------------------- | -------------------------------------------------------------------- |
| Collaboration               | Developers, system administrators, and QA teams work together.       |
| Automation                  | Automate repetitive tasks such as testing, building, and deployment. |
| Integration                 | Connect tools and processes so teams can work together.              |
| Continuous Integration (CI) | Frequently combine and test code changes.                            |
| Continuous Delivery (CD)    | Prepare software changes for reliable release and deployment.        |
| Shared Responsibility       | Everyone contributes to software quality, reliability, and security. |

##### Why is DevOps important?

- Reduces communication problems between teams.
- Finds and fixes bugs faster.
- Speeds up software development and releases.
- Improves software quality and security.

> DevOps brings developers, operations, and QA together through collaboration, automation, and continuous delivery to build and release software faster and more reliably.

### Why is DevOps Important?

### DevOps Philosophy

**DevOps** focuses on building trust and improving communication between developers, system administrators, and QA teams.

| Concept            | Easy Explanation                                          |
| ------------------ | --------------------------------------------------------- |
| Teamwork           | Different teams work together instead of separately.      |
| Trust              | Teams share responsibility and support each other.        |
| Business Alignment | Software projects focus on business needs and priorities. |
| Small Changes      | Changes are released in small, manageable steps.          |
| Reversible Changes | Changes can be rolled back if something goes wrong.       |
| Visibility         | All teams can see project progress and updates.           |
| Efficiency         | Better communication helps deliver work faster.           |

> DevOps improves teamwork, trust, and visibility so organizations can deliver software faster, more reliably, and with fewer problems.


---


### In Summary

DevOps uses automation and integration to make software development, testing, and deployment faster and more reliable.

| Concept                      | Easy Explanation                                                             | Example                                     |
| ---------------------------- | ---------------------------------------------------------------------------- | ------------------------------------------- |
| Cloud Provisioning           | Developers can create cloud resources without waiting for IT administrators. | Create a virtual machine on AWS.            |
| CI/CD                        | Automatically builds, tests, and deploys software.                           | Automatically test new code before release. |
| Infrastructure as Code (IaC) | Manage and deploy infrastructure using code.                                 | Terraform and Vagrant.                      |
| Containers                   | Package applications with their dependencies for easier deployment.          | Docker containers.                          |
| Automation                   | Reduce repetitive manual work.                                               | Automatically create testing environments.  |

#### Declarative vs. Imperative Approach

| Approach                | Meaning                                                    | Example                                                                |
| ----------------------- | ---------------------------------------------------------- | ---------------------------------------------------------------------- |
| Declarative             | Specify the desired final state, and the tool creates it.  | "Create three running virtual machines."                               |
| Imperative / Procedural | Specify the exact steps needed to reach the desired state. | Create a VM, install software, configure settings, and start services. |


> **Note**: DevOps helps organizations release software faster, reduce manual work, and improve collaboration between development and operations teams.

## Task 4: Shifting Left

### Introduction

**Shift Left** means adding security checks early in the software development process instead of waiting until the software is finished.

| Concept              | Easy Explanation                                                  |
| -------------------- | ----------------------------------------------------------------- |
| Shift Left           | Find and fix security problems early during development.          |
| Security Integration | Developers and security teams work together.                      |
| Code Analysis        | Automatically scan code for security weaknesses.                  |
| Automated Testing    | Test software regularly to detect bugs and vulnerabilities early. |

> Find and fix security vulnerabilities early to reduce risks, costs, and problems in production.


### Shifting Left

**Shifting Left** means performing security testing at the beginning of software development instead of waiting until the end.

| Traditional Security                 | Shift Left Security                              |
| ------------------------------------ | ------------------------------------------------ |
| Security testing happens at the end. | Security testing happens throughout development. |
| Vulnerabilities are found late.      | Vulnerabilities are found early.                 |
| Fixing issues can be expensive.      | Fixing issues is cheaper and faster.             |
| Can cause deployment delays.         | Reduces delays and production problems.          |

> Find and fix security problems early in development to reduce costs, save time, and build more secure software.



### Why are we shifting left

**Cloud infrastructure** can now be created automatically instead of waiting weeks or months for IT teams to provide servers.

| Benefit                           | Security Concern                           |
| --------------------------------- | ------------------------------------------ |
| Faster infrastructure deployment. | Misconfigurations may go unnoticed.        |
| Improved developer productivity.  | Security checks may be skipped.            |
| Automated resource creation.      | Vulnerabilities can be introduced quickly. |

> Cloud automation makes development faster, but security checks must also be automated to prevent misconfigurations and vulnerabilities.

<img width="1402" height="594" alt="image" src="https://github.com/user-attachments/assets/4332cb12-f7cf-4ce2-a3d3-1baad52e522b" />


**DevSecOps (Development + Security + Operations)** means integrating security into every stage of software development instead of checking security only at the end.

| Concept                    | Easy Explanation                                                |
| -------------------------- | --------------------------------------------------------------- |
| DevSecOps                  | Combines development, security, and operations.                 |
| Shift Left                 | Introduces security checks early in development.                |
| Code Analysis              | Scans source code to find security weaknesses.                  |
| Automated Security Testing | Automatically checks applications for vulnerabilities.          |
| Continuous Security        | Performs security checks throughout development and deployment. |

> DevSecOps = DevOps + Security. Security is built into the entire development process, not added at the end.

## Task 5: DevSecOps: Security AShifts Left


> **DevSecOps** is an approach that relies heavily on automation and platform design that integrates security as a shared responsibility. It is a culture-driven development style that normalises security as a day-to-day operation. 


### What is the value?

**DevSecOps** helps organizations improve security while developing and releasing software faster.

| Value                   | Benefit                                       |
| ----------------------- | --------------------------------------------- |
| Reduced Vulnerabilities | Find and fix security problems early.         |
| Better Test Coverage    | Identify more potential security issues.      |
| Automation              | Reduce manual security testing.               |
| Risk Reduction          | Prevent security incidents and data breaches. |
| Cost Savings            | Reduce financial losses from security flaws.  |
| Brand Protection        | Protect the organization's reputation.        |
| Auditing & Monitoring   | Make security reviews and tracking easier.    |

> DevSecOps reduces security risks, saves money, improves software quality, and makes security part of everyday development.


### How to implement this efficiently? 

### How to Implement DevSecOps Efficiently — Summary

**Culture is the foundation of DevSecOps**. Teams must communicate, trust each other, share security knowledge, and take responsibility for security.

| Implementation           | Easy Explanation                                                            |
| ------------------------ | --------------------------------------------------------------------------- |
| 1. Open Communication    | Developers, security teams, and operations teams share information.         |
| 2. Build Trust           | Teams support each other instead of blaming each other when problems occur. |
| 3. Security Training     | Teach everyone basic security knowledge and best practices.                 |
| 4. Shared Responsibility | Everyone is responsible for identifying and preventing security issues.     |
| 5. Provide Tools         | Give teams automated security tools to find vulnerabilities.                |
| 6. Knowledge Sharing     | Share security guidelines, documentation, and lessons learned.              |

> DevSecOps works efficiently when everyone understands security, communicates openly, has the right tools, and takes shared responsibility for protecting software.


### DevSecOps Challenges

#### Security Silos
**Security Silos** happen when security teams work separately from developers and operations teams instead of working together.

| Problem                    | Easy Explanation                                                 |
| -------------------------- | ---------------------------------------------------------------- |
| Separate Teams             | Security is handled only by specialized security staff.          |
| Poor Communication         | Developers and security teams do not share enough information.   |
| Lack of Security Awareness | Developers may not understand or apply security practices early. |
| Security Becomes a Blocker | Security teams slow down development instead of supporting it.   |


#### Lack of Visibility & Prioritisation

**Lack of Visibility & Prioritisation** happens when teams do not clearly understand security risks or which problems should be fixed first.

| Problem             | Easy Explanation                                                |
| ------------------- | --------------------------------------------------------------- |
| Lack of Visibility  | Teams do not have a clear view of security issues.              |
| Poor Prioritisation | Security vulnerabilities are not fixed according to their risk. |
| Blame Game          | Teams blame each other instead of solving problems together.    |
| Lack of Trust       | Developers and security teams do not work together effectively. |

> Make security visible to everyone, prioritize risks, and encourage teams to work together instead of blaming each other.




### Stringent Processes — Summary

Stringent Processes happen when security rules and approval procedures are too complicated, slowing down software development.

| Problem                   | Easy Explanation                                                             |
| ------------------------- | ---------------------------------------------------------------------------- |
| Too Many Approvals        | Developers must go through many security checks before testing new software. |
| Development Delays        | Complicated procedures slow down development.                                |
| Inflexible Security Rules | Low-risk tasks and high-risk changes are treated the same way.               |

### Solution

- Use risk-based security checks: Apply stricter checks to high-risk changes.
- Keep procedures flexible for low-risk development tasks.
- Provide Sandbox environments for safe software testing.

### What is a Sandbox?

A Sandbox is a temporary, isolated environment where developers can test software safely.

| Sandbox Feature                | Purpose                                             |
| ------------------------------ | --------------------------------------------------- |
| Isolated environment           | Prevents testing from affecting production systems. |
| No internal network connection | Reduces access to company infrastructure.           |
| No real customer data          | Protects sensitive information.                     |
| Temporary environment          | Can be removed after testing.                       |

Key takeaway: Use flexible, risk-based security processes and isolated Sandbox environments to allow developers to test software safely without unnecessary delays.

## Task 6: DevSecOps Culture

### Promote autonomy of teams

**Promoting autonomy** means giving teams the knowledge, tools, and responsibility to handle security issues independently without always depending on security specialists.

| Concept                | Easy Explanation                                                      |
| ---------------------- | --------------------------------------------------------------------- |
| Automation             | Integrate security tests into the development pipeline.               |
| Security Education     | Teach developers how to identify and fix vulnerabilities.             |
| Playbooks / Runbooks   | Provide step-by-step guides for handling security issues.             |
| Team Autonomy          | Allow teams to make secure decisions independently.                   |
| Security Collaboration | Security teams support and guide developers instead of blocking them. |
| Knowledge Sharing      | Share security knowledge across all teams.                            |

> Automate security testing, educate developers, and provide useful guides so everyone can take responsibility for security without depending on security specialists for every decision.



### Visibility and Transparency

**Visibility and Transparency** mean making security information and tools accessible to all teams so they can understand and fix security problems.

| Concept              | Easy Explanation                                                                              |
| -------------------- | --------------------------------------------------------------------------------------------- |
| Visibility           | Give teams a clear view of their application's security status.                               |
| Security Dashboard   | Shows vulnerabilities based on severity, such as Critical, High, Medium, and Low.             |
| Prioritisation       | Helps teams decide which vulnerabilities to fix first.                                        |
| Transparency         | Allow developers to access security tools and understand why issues are detected.             |
| Remediation Guidance | Provide explanations and step-by-step instructions to fix vulnerabilities.                    |
| Team Access          | Give developers access to security reports instead of limiting information to security teams. |

> Example: A developer pushes code, and an automated security check detects a possible code injection vulnerability. The tool shows the affected code, explains the issue, and recommends how to fix it.

> Make security findings, dashboards, and tools accessible to everyone so teams can understand risks, prioritize fixes, and solve security problems independently.



### Account for flexibility thanks to understanding and empathy

**Understanding and empathy** mean considering how other teams work, what they prioritize, and what risks matter to them before introducing security processes.

| Concept                | Easy Explanation                                                             |
| ---------------------- | ---------------------------------------------------------------------------- |
| Understand Other Teams | Learn how developers and engineers work and what challenges they face.       |
| Different Priorities   | Different teams may consider different issues more important.                |
| Flexibility            | Adjust security processes according to deadlines, risks, and team resources. |
| Risk-Based Security    | Focus on vulnerabilities that create the greatest risk to each service.      |
| Scanner Customization  | Configure security tools to reduce unnecessary alerts.                       |
| Build Trust            | Work with teams instead of forcing complicated security processes on them.   |

#### Example

A platform team manages an important internal service.
- A bug that causes the service to stop working is a high priority.
- A potential injection vulnerability behind multiple security controls may have lower immediate priority.

Security teams should understand the situation and prioritize findings based on actual risk.

> DevSecOps should be flexible. Understand each team's priorities, adjust security processes to their needs, and focus on real risks instead of creating unnecessary work.
