## Task 1: Introduction

**Cloud computing** means renting computing resources, such as servers, storage, and networking delivered through an API, from providers like AWS, Microsoft Azure, or Google Cloud instead of buying and managing physical servers.

> **Amazon Web Services (AWS)** is a comprehensive cloud computing platform offered by Amazon. It provides a wide range of services such as computing power, storage, databases, networking, analytics, and more, delivered over the internet on a pay-as-you-go basis.

> **Application Programming Interface (API)** is a set of rules and protocols for building software and applications. An API allows different software programs to communicate with each other. It defines methods of communication between various components, including the kinds of requests that can be made, how they're made, the data formats that should be used, and conventions to follow.

#### Concepts

| Topic | Easy Explanation | Example |
|---|---|---|
| Cloud Computing | Rent IT resources over the internet. | Rent a virtual server instead of buying a physical server. |
| Compute | Resources that run applications and programs. | Virtual machines and cloud instances. |
| Storage | Services that store files and data. | Cloud storage buckets. |
| Networking | Connects cloud servers and controls network traffic. | Virtual networks, firewalls, and security groups. |
| Identity and Access | Controls who can access cloud resources and what they can do. | User accounts, roles, and permissions. |
| Service Deployment Models | Different ways cloud services are provided and managed. | Public cloud, private cloud, and hybrid cloud. |


#### Why Is Cloud Security Important?

Companies often host their applications, files, servers, and user accounts in the cloud. Misconfigurations or excessive permissions can expose these resources to attackers.


### Learning Objectives

- Describe cloud networking primitives and common exposed-service and lateral-movement patterns
- Explain the Instance Metadata Service and the SSRF-to-credentials attack chain
- Walk a guided, cloud-agnostic attack against a simulated cloud environment

## Task 2: Cloud Services and Deployment Models

Before testing cloud security, understand what cloud services the company rents and which security responsibilities belong to the company versus the provider.



### Service Models

Cloud service models explain what the cloud provider manages and what we manage ourself.

| Model | Full Name | Easy Explanation | Example | Analogy |
|---|---|---|---|---|
| IaaS | Infrastructure as a Service | Rent virtual servers, storage, and networks. We manage the operating system and applications. | AWS EC2 virtual machine | Empty apartment - we set up everything inside. |
| PaaS | Platform as a Service | The provider manages the infrastructure and platform. We focus on building and deploying our application. | Google App Engine, Azure App Service | Semi-furnished apartment - the basics are ready. |
| SaaS | Software as a Service | Use ready-made software managed by the provider. We mainly configure and use it. | Gmail, Microsoft 365 | Hotel room - everything is ready to use. |


> IaaS = Rent infrastructure.
> 
> PaaS = Build and deploy applications.
>
> SaaS = Use ready-made software.


> **IaaS** stands for **Infrastructue as a Service** and means renting raw compute, storage, and networking over the internet.
> 
> **PaaS** stands for **Platform as a Service** and provides an on-demand environment for developing, testing, and managing software applications.
>
> **Software as a Service (SaaS)** is a method of providing software to users. This software/application will run in the cloud and users will pay to use it via subscription (as a service) rather than buying it.



### Deployment Models

Deployment models describe where cloud infrastructure is hosted, who uses it, and how it is shared.

| Model | Easy Explanation | Example | Analogy |
|---|---|---|---|
| Public Cloud | A cloud provider offers infrastructure used by multiple customers, with workloads isolated from one another. | AWS, Microsoft Azure, Google Cloud | Renting an apartment in a large apartment building. |
| Private Cloud | Cloud infrastructure dedicated to one organization. It can be hosted on-site or by a provider. | A company's own private cloud. | Owning a private house. |
| Hybrid Cloud | Combines public cloud services with private infrastructure, connected through a network or VPN. | A company keeps sensitive data on-site but hosts its website in AWS. | Using your own house and renting another place when needed. |
| Community Cloud | Infrastructure shared by organizations with similar needs, such as security or regulatory requirements. | A cloud shared by government agencies. | Several organizations sharing a facility built for their common needs. |


> **Public** = Used by multiple customers.
> 
> **Private** = Dedicated to one organization.
> 
> **Hybrid** = Combination of public and private environments.
> 
> **Community** = Shared by organizations with common requirements.


> A **Virtual Private Network** is a way to create a secure "tunnel" between two networks. For example, we use a VPN on TryHackMe to access the private network on which the machines operate. VPNs are also commonly used for an employee to log into their workplace when they are not on site (such as working from home or travelling for business matters).
>
> VPNs are also used where networks (such as coffee shops) do not provide encryption, and are a great way of preventing others from reading Our network traffic.




### The Shared Responsibility Model

**Cloud security** is shared between the cloud provider and the customer. Each is responsible for protecting different parts of the environment.

| Layer | IaaS | PaaS | SaaS |
|---|---|---|---|
| Physical datacentre | Provider | Provider | Provider |
| Hardware and hypervisor | Provider | Provider | Provider |
| Network Configuration | Customer | Shared | Provider |
| Operating system | Customer | Provider | Provider |
| Runtime and middleware | Customer | Provider | Provider |
| Application code | Customer | Customer | Provider |
| Data | Customer | Customer | Customer |
| Identities and access | Customer | Customer | Customer |

Cloud penetration testers usually focus on customer-side misconfigurations, rather than the cloud provider's physical infrastructure.

| Misconfiguration | Security Risk |
|---|---|
| Virtual machine has a default password | Unauthorized access to the server. |
| Storage bucket is public | Sensitive files may be exposed. |
| IAM policy uses wildcard actions (`*`) | Users or services may receive excessive permissions. |

Every provider has their own names for the same ideas. Here are a few examples we will most often meet:

| Model | AWS example | Azure example | Google Cloud example |
|---|---|---|---|

| PaaS | RDS, Elastic Beanstalk | Azure SQL Database, App Service | Cloud SQL, App Engine |
| SaaS | Amazon WorkMail | Microsoft 365 | Google Workspace |


> **Elastic Compute Cloud (EC2)** is a service provided by Amazon Web Services (AWS) that allows you to rent virtual PCs on the cloud. The machines can be used just as any regular PC, and their specs can be dimensioned according to our specific needs.

> **Structured query language (SQL)** is a programming language for storing and processing information in a relational database. A relational database stores information in tabular form, with rows and columns representing different data attributes and the various relationships between the data values. We can use SQL statements to store, update, remove, search, and retrieve information from the database. We can also use SQL to maintain and optimize database performance.

## Task 3: Identity and Access Management (IAM)

Cloud security often starts with Identity and Access Management (IAM) because stolen credentials or excessive permissions can let attackers access cloud resources.

- **Credentials**: Keys, passwords, or tokens used to authenticate.
- **Policies**: Rules defining what actions a user or service can perform.
- **Roles**: Sets of permissions assigned to users or services.
- **Least privilege**: Give each identity only the permissions it needs.



### Policies Are Just Documents

A cloud IAM policy is a JSON document that specifies who can do what to which resources. Three fields carry most of the meaning:
- **Effect**: ``Allow`` or ``Deny``
- **Action**: the operations the policy covers, such as ``storage:GetObject`` or ``iam:CreateUser``
- **Resource**: the specific resource the action applies to, usually expressed as a provider-specific identifier

Here is a small example of a well-scoped policy:
````json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "storage:GetObject",
      "Resource": "bucket/reports/*"
    }
  ]
}
````


This grants a single action on a single bucket prefix. Compare it to this one:
````json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "*",
      "Resource": "*"
    }
  ]
}
````


The ``*`` wildcard means all.
- ``Effect``: Defines whether an action is allowed or denied.
- ``Action: "*"``: Allows all actions.
- ``Resource: "*"``: Applies to all resources.

**Security risk**: If both fields use ``*`` with ``Allow``, the identity may have excessive permissions across all resources covered by the policy.




### Roles and Role Assumption

A **role** is a set of permissions that a user, application, or virtual machine can temporarily assume.
- **Role assumption**: An identity takes on a role and receives temporary credentials.
- **Privilege escalation**: An attacker with compromised credentials may assume a more privileged role if permitted.
- **Instance Metadata Service (IMDS)**: A virtual machine can obtain temporary credentials for its attached role through metadata services.

> **Example**: A VM has a role that can read cloud storage. If someone obtains its temporary credentials, they may be able to access that storage.






### IAM Enumeration Mindset

Whenever we land a set of cloud credentials, whether from a leaked ``.aws/credentials`` file, an SSRF response, or a compromised service, the first question should be "What can I do with these?".

When we obtain cloud credentials during an authorized security test, determine what access they provide.

| Step         | What to Check                                                  |
| ------------ | -------------------------------------------------------------- |
| 1. Identity  | Who do the credentials belong to?                              |
| 2. Policies  | What permissions are attached directly or through groups?      |
| 3. Roles     | Which roles can the identity assume?                           |
| 4. Wildcards | Do policies use `*` for actions or resources?                  |
| 5. Resources | Is access limited to specific resources or the entire account? |

> Identify the user, understand their permissions, check assumable roles, and look for excessive access.

> **Server Side Request Forgery (SSRF)** is a web vulnerability where an attacker manipulates a vulnerable application to make requests to internal or external resources on behalf of the server. This can lead to data exposure, unauthorised access to internal systems, or service disruptions.



### The One Weakness Pattern Worth Knowing

If we only remember one IAM attack pattern, it is this: **over-permissive policies combined with exposed keys**.

Access keys end up in the wrong place constantly and attackers scrape all of these: 
- Committed to public code repositories.
- Embedded in container images pushed to a public registry.
- Written in a config file that got backed up to a public bucket.
- Printed in a screenshot posted on a ticket.


Cloud breaches often happen when exposed access keys have too many permissions.
- **Exposed keys**: Credentials are leaked or made public.
- **Wildcard permissions (*)**: Allow broad access to actions or resources.
- **Security risk**: Attackers may use the keys to access, modify, or steal company data.

> Example: A developer's leaked cloud key can access every file in the company's storage bucket.

> **Containers** are packages of software that bundles up code, and all its dependencies so it can be run reliably in any environment.

## Task 4: Cloud Storage and Data Exposure

A **public storage bucket** is a cloud storage location that allows people without proper authorization to access its contents.

> **Example**: A company uploads a database backup to a cloud bucket and accidentally allows anyone to download it.



### Object Storage Basics

**Object storage** stores files as objects inside containers. These containers are called **buckets** in AWS and Google Cloud, and **containers** in Azure.

Every object is accessible by a URL shaped like 
````https
https://<provider-endpoint>/<bucket-name>/<object-key>
````

Three access-control primitives show up on every platform:
| Concept | Easy Explanation | Security Risk |
|---|---|---|
| Object Storage | Stores files and their metadata in buckets or containers. | Sensitive files may be exposed. |
| Bucket Policy | Rules that control who can access stored objects. | A policy using `"Principal": "*"` may allow public access if not restricted by other controls. |
| ACL (Access Control List) | Defines access permissions for individual objects or buckets. | Incorrect permissions may allow unauthorized users to read files. |
| Signed URL | A link that grants temporary access to a file without requiring the recipient to log in. | Leaked links or excessively long expiry times may expose files. |


### How Buckets End Up Public

Four patterns cover most real incidents:
| Cause | Easy Explanation |
|---|---|
| 1. Forgotten Defaults | Developers make a bucket public for testing and forget to secure it before adding real data. |
| 2. Block Public Access Disabled | Turning off public-access protections may allow public policies to expose data. |
| 3. Wildcard Principals (`"Principal": "*"`) | A policy may allow anyone on the internet to access the specified resources. |
| 4. Leaked or Long-Lived Signed URLs | Long-validity links may be exposed or indexed by search engines, allowing unauthorized access. |



### Attacker Workflow

Our approach to discovering exposed storage is methodical:
| Step | Action | Purpose |
|---|---|---|
| 1. Identify Bucket Names | Find likely storage bucket names within the authorized scope. | Identify possible storage locations. |
| 2. Check Public Access | Check whether the bucket allows unauthenticated access. | Detect misconfigured permissions. |
| 3. Review Object Listings | Check whether stored filenames are publicly visible. | Identify potential data exposure. |
| 4. Verify Exposure | Safely confirm access using approved test objects. | Gather evidence without accessing sensitive data. |

> **Tools**: ``s3scanner``, ``cloud_enum``, and ``curl`` can assist with cloud storage assessments.


### What Ends Up In Open Buckets

The artefacts we prioritise, in rough order of value:

| Artifact | What It May Contain | Security Risk |
|---|---|---|
| 1. Backups | Database dumps, disk snapshots, configuration backups. | May expose large amounts of sensitive data. |
| 2. Source Code | Hardcoded secrets, API documentation, unreleased features. | May reveal credentials and application weaknesses. |
| 3. Configuration Files | `.env`, `credentials.json`, Kubernetes and CI/CD secrets. | May expose credentials and internal services. |
| 4. Logs | Emails, session tokens, internal IP addresses, passwords. | May leak sensitive information. |
| 5. Customer Data | Email addresses, payment identifiers, personal documents. | Privacy breaches and data exposure. |

A single publicly listable backup file is often more impactful than every other technique combined.


### Provider Callouts

| Concept | AWS | Azure | Google Cloud |
|---|---|---|---|
| Storage service | Amazon S3 | Azure Blob Storage | Google Cloud Storage |
| Unit of storage | Bucket | Container | Bucket |
| Public URL shape | `https://<bucket>.s3.amazonaws.com/<key>` | `https://<account>.blob.core.windows.net/<container>/<blob>` | `https://storage.googleapis.com/<bucket>/<object>` |
| Access document | Bucket Policy, IAM policy, ACL | Shared Access Signature, RBAC, public access level | IAM policy, ACL, signed URL |


> An **Access Control List (ACL)** is a list of permissions that determine who can access a specific resource in a computer network. It is used to grant or deny access to files, folders, printers, and other network resources.

> **RBAC** refers to **access to resources being restricted on a role** basis in an organisation. Can be used in (but not limited to) Kubernetes to restrict access to cluster resources.

## Task 5: Cloud Networking

**Cloud networking** helps us understand which cloud resources are reachable and what access is possible once inside the environment.

> During an authorized cloud security assessment, map the network, identify reachable resources, and review firewall rules to understand the environment's exposure.


### The Building Blocks

A **virtual network (sometimes called a VPC, for Virtual Private Cloud)** is the private network a customer carves out within the provider's network. 
| Key Concept | Easy Explanation |
|---|---|
| VPC | A private network in the cloud. |
| IP Address Range | The range of IP addresses assigned to the network, such as `10.0.0.0/16`. |
| Isolation | Keeps your virtual network separate from other customers' networks by default. |
| Connections | Networks can be connected through configured routing or networking services. |


A **subnet** is a smaller section of a VPC used to organize cloud resources into different networks.

| Type                   | Easy Explanation                                                         | Example                                             |
| ---------------------- | ------------------------------------------------------------------------ | --------------------------------------------------- |
| Public Subnet          | Has a route to the internet through an Internet Gateway (IGW).           | A public-facing web server.                         |
| Private Subnet         | Has no direct route from the internet through an IGW.                    | A database server.                                  |
| Internet Gateway (IGW) | Connects a VPC to the internet when routing and security rules allow it. | Enables internet connectivity for public resources. |

> **Example**: A company places its web server in a public subnet and its database in a private subnet to reduce direct internet exposure.


Two firewall primitives sit on top of that structure:
| Feature | Security Group (SG) | Network ACL (NACL) |
|---|---|---|
| Level | Resource / network interface | Subnet |
| Type | Stateful | Stateless |
| Rules | Allow rules only | Allow and deny rules |
| Traffic response | Return traffic is automatically allowed for an established permitted connection. | Return traffic must be explicitly allowed by the rules. |
| Default behavior | Unmatched traffic is denied. | Depends on the default or configured rules. |
| Main purpose | Protect individual resources, such as virtual machines. | Filter traffic entering or leaving a subnet. |


> A **virtual private cloud (VPC)** is an isolated, private cloud inside of a public cloud environment. VPCs are granted to users of cloud providers so that their resources aren't accessible by other users in the same public cloud.


> **Firewall**: A security tool, hardware or software that is used to filter network traffic by stopping unauthorized incoming and outgoing traffic.

> **(IGW) Internet Gateway** a component in cloud computing that acts as a bridge between a virtual private cloud (VPC) and the public internet. 



### Attacker Focus 1: Exposed Ports

A security group that exposes sensitive ports to ``0.0.0.0/0`` allows traffic from any IPv4 address, subject to other network controls.

Typical examples that appear on reports:
| Port / Service | Common Port | Security Risk |
|---|---:|---|
| SSH | 22 | Attackers may attempt unauthorized remote access. |
| MySQL | 3306 | Database may be exposed to internet-based attacks. |
| PostgreSQL | 5432 | Unauthorized users may attempt database access. |
| MongoDB | 27017 | Database data may be exposed if access controls are weak. |
| Admin Panels | 8080, 9000 | Administrative interfaces may be accessible without a VPN. |
| RDP | 3389 | Windows remote access may be exposed to unauthorized connections. |

We find these with ordinary port scans and HTTP probes. The cloud does not change the tooling; it changes how easy it is to introduce the mistake.



### Attacker Focus 2: Lateral Movement

**Lateral movement** means moving from one compromised system to other systems within the same network.

> **Example**: An attacker compromises a public-facing web server and then discovers it can connect to an internal database.


| Potential Target              | Security Risk                                                                    |
| ----------------------------- | -------------------------------------------------------------------------------- |
| Internal databases and caches | Sensitive data may be accessed.                                                  |
| Application servers           | Other systems may be compromised.                                                |
| Internal admin panels         | Unauthorized administrative access.                                              |
| Service metadata endpoints    | Temporary cloud credentials may be exposed if access is not properly restricted. |



### Provider Callouts

| Concept           | AWS                    | Azure                        | Google Cloud                                                                     |
| ----------------- | ---------------------- | ---------------------------- | -------------------------------------------------------------------------------- |
| Virtual Network   | VPC                    | Virtual Network (VNet)       | VPC                                                                              |
| Subnet            | Subnet                 | Subnet                       | Subnet                                                                           |
| Internet Access   | Internet Gateway (IGW) | Public IP or NAT Gateway     | Default route + external IP; Cloud NAT for outbound-only access from private VMs |
| Instance Firewall | Security Group (SG)    | Network Security Group (NSG) | VPC Firewall Rule                                                                |
| Subnet Firewall   | Network ACL (NACL)     | NSG applied at subnet scope  | VPC Firewall Rules, optionally targeting network tags or service accounts        |

## Task 6: Compute and Metadata Services

Cloud computing is where our familiar skills meet new primitives. Cloud VMs run like normal servers, but IMDS provides instance identity and temporary credentials. If an attacker exploits SSRF to access IMDS, they may gain access to cloud resources.


### Instances and Images

A **cloud instance** is a virtual machine rented from a cloud provider. An **image** is a template containing an operating system and sometimes preinstalled software, used to create the instance.

| Concept       | Easy Explanation                                    | Example                       |
| ------------- | --------------------------------------------------- | ----------------------------- |
| Instance      | A running virtual machine in the cloud.             | A Linux server hosted on AWS. |
| Image         | A template used to create a virtual machine.        | Ubuntu Server image.          |
| Instance Size | Determines available CPU, RAM, and computing power. | 2 vCPUs and 4 GB RAM.         |
| IP Address    | Allows the instance to communicate over a network.  | Public IP or private IP.      |

#### Security Risks to Check

| Risk                       | Example                                               |
| -------------------------- | ----------------------------------------------------- |
| Weak Passwords             | A server uses a default or easily guessed password.   |
| Open Ports                 | Unnecessary services are accessible over the network. |
| Outdated Software          | The operating system has unpatched vulnerabilities.   |
| Misconfigured Applications | A service exposes sensitive information.              |




### The Instance Metadata Service

**Instance Metadata Service (IMDS)** is an HTTP service that allows a cloud virtual machine to retrieve information about itself, including its identity, configuration, and sometimes temporary access credentials.

| Concept               | Easy Explanation                                                                                                    |
| --------------------- | ------------------------------------------------------------------------------------------------------------------- |
| IMDS                  | A service that provides information about a cloud instance.                                                         |
| Endpoint              | Usually accessible from inside the instance at `169.254.169.254`.                                                   |
| Instance Information  | Provides details such as instance ID and region.                                                                    |
| Temporary Credentials | May provide credentials associated with an attached cloud role.                                                     |
| Security Risk         | If an attacker exploits a vulnerable application, such as SSRF, they may be able to access metadata or credentials. |

> **IMDS** helps cloud applications obtain information and temporary credentials without hardcoding them. However, if access is not properly protected, attackers may exploit it to gain access to cloud resources.

> From an attacker's point of view, IMDS is a small HTTP server that hands out credentials to anyone who requests them.




### IMDSv1 Is What Lands On Reports

AWS Instance Metadata Service has two versions. The main difference is how they control access to instance metadata and temporary credentials.

| Feature        | IMDSv1                                                       | IMDSv2                                                                  |
| -------------- | ------------------------------------------------------------ | ----------------------------------------------------------------------- |
| Request        | Simple HTTP GET request.                                     | Requires a session token obtained through a PUT request.                |
| Authentication | No session token required.                                   | Session token required.                                                 |
| Security       | More vulnerable to certain SSRF attacks.                     | Adds protection against many common SSRF attacks.                       |
| Risk           | An SSRF vulnerability may allow access to instance metadata. | Token requirements make metadata access harder to exploit through SSRF. |

IMDSv1 is less protected because it does not require a session token. IMDSv2 adds an extra security step. Cloud penetration testers check whether IMDSv1 is enabled because it can increase the risk of exposing temporary cloud credentials.


### The SSRF-To-Credentials Chain

This is the attack chain we see on almost every cloud engagement that has a web application in scope:

1. Find SSRF: Find a feature that fetches URLs provided by users.
2. Target IMDS: Check whether the server can access its internal metadata service, typically ``http://169.254.169.254/latest/meta-data/iam/security-credentials/<role-name>``, he role name is discoverable by first querying the parent path ``/latest/meta-data/iam/security-credentials/``, which returns it.
3. Request Metadata: The server requests information from the cloud instance.
4. Expose Credentials: Weak protections may expose temporary cloud credentials.
5. Access Cloud Resources: Exposed credentials may allow access to resources permitted by the instance's role.

**Capital One Breach (2019)**: An SSRF vulnerability allowed an attacker to obtain cloud credentials through AWS metadata and access data belonging to over 100 million customers.


### Other Compute Forms Worth Knowing

Three more compute forms have their own identity and metadata stories. We touch them briefly here and go deeper on each in later rooms.

| Compute Form         | Easy Explanation                                                    | Security Risk                                                                |
| -------------------- | ------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| Disk Snapshots       | Copies of a virtual machine's disk at a specific time.              | Public snapshots may expose sensitive files and credentials.                 |
| Serverless Functions | Run code on demand without managing a permanent server.             | Misconfigurations or SSRF may expose sensitive data or function credentials. |
| Containers           | Run applications in isolated environments using container services. | Weak permissions or SSRF may expose application data or cloud credentials.   |

> Disk snapshots can expose stored data, while serverless functions and containers can introduce identity and metadata security risks.



### Provider Callouts
| Concept             | AWS                                              | Azure                                                      | Google Cloud                                   |
| ------------------- | ------------------------------------------------ | ---------------------------------------------------------- | ---------------------------------------------- |
| Instance            | EC2                                              | Virtual Machine                                            | Compute Engine VM                              |
| Metadata Endpoint   | `http://169.254.169.254/latest/meta-data/`       | `http://169.254.169.254/metadata/instance?api-version=...` | `http://metadata.google.internal/`             |
| Metadata Protection | IMDSv2 requires a PUT request and session token. | Requires the `Metadata: true` header.                      | Requires the `Metadata-Flavor: Google` header. |
| Serverless          | AWS Lambda                                       | Azure Functions                                            | Cloud Functions, Cloud Run                     |
| Managed Containers  | ECS, EKS, Fargate                                | ACI, AKS                                                   | Cloud Run, GKE                                 |


> **AWS Lambda** is a compute service that runs code without the need to manage servers.

> The **Elastic Common Schema (ECS)** is an open-source standard that defines consistent field names for data in Elasticsearch. It normalises logs from different sources so analysts can correlate events without rewriting queries.

> **Elastic Kubernetes Service (AKS)** is a managed Kubernetes service from the Amazon Web Services Cloud Service Provider. 

> **AWS Fargate** is a serverless compute engine for containers. It allows you to run Docker containers without having to provision, configure, or manage your own virtual servers or container clusters.

> **ACI (Agent-Computer Interface)**: The tools, parameters and documentation an AI agent uses to interact with external systems, designed for an agent the way a UI is designed for a person.

> **Azure Kubernetes Service (AKS)** is a managed Kubernetes service from the Azure Cloud Service Provider.
