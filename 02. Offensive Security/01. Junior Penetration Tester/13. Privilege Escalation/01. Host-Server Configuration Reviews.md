## Task 1: Introduction

**Privilege escalation** is the process of moving from a **low-privileged account** to a **higher-privileged account**, such as ``root`` on Linux or ``SYSTEM/Administrator`` on Windows.


### Two main types

<img width="900" height="420" alt="image" src="https://github.com/user-attachments/assets/9904d5f6-c95a-48ad-b978-fcdd1cf30b77" />


| Type                    | Meaning                                  | Example              |
| ----------------------- | ---------------------------------------- | -------------------- |
| **Vulnerability-based** | Exploit a software bug                   | Kernel CVE           |
| **Configuration-based** | Exploit an insecure system configuration | Writable root script |



#### Configuration-based escalation

Even a fully patched system can be vulnerable when administrators configure it poorly.

Common examples:
- Weak file permissions
- Insecure services
- Misconfigured scheduled tasks
- Exposed credentials
- Excessive user/group privileges

#### Secure configuration

Security frameworks such as:
- **CIS Benchmarks**: secure configuration recommendations
- **DISA STIGs**: detailed security configuration requirements


#### Auditing tools

| Tool         | Main use                                   |
| ------------ | ------------------------------------------ |
| **Nessus**   | Vulnerability and configuration assessment |
| **Lynis**    | Linux security auditing                    |
| **OpenSCAP** | Compliance and configuration checking      |


#### methodology

When we get a low-privileged shell: ``Who am I?`` -> ``What can I access?`` -> ``What is running?`` -> ``What can I modify?`` -> ``What runs with higher privileges?`` -> ``Can these weaknesses lead to escalation?``

## Task2: What is a Configuration Review


#### What is a Configuration Review?

A **configuration review** checks a host's **settings**, **permissions**, **services**, and **policies** against a secure baseline to find misconfigurations.


#### Configuration Review vs Vulnerability Scan
| Type                     | Focus                                                        |
| ------------------------ | ------------------------------------------------------------ |
| **Vulnerability Scan**   | Finds known software flaws, missing patches, and CVEs        |
| **Configuration Review** | Finds insecure settings, permissions, services, and policies |


A system can have **no known vulnerabilities** but still have insecure configurations.

#### Configuration Review vs Exploitation
- **Exploitation**: What is broken in this software?
- **Configuration Review**: What is configured incorrectly on this system?



### When Configuration Reviews Happen

During a pentest, configuration review usually happens after initial access.

``Initial Access`` -> ``Low-Privileged Shell`` -> ``Configuration Review`` -> ``Find Misconfiguration`` -> ``Privilege Escalation``

It can also be performed as a standalone security audit for hardening and compliance.


### The Offensive Perspective

| Defensive       | Offensive               |
| --------------- | ----------------------- |
| Find deviations | Find weaknesses         |
| Assess risk     | Prioritise weaknesses   |
| Fix them        | Use them for escalation |

<img width="900" height="420" alt="image" src="https://github.com/user-attachments/assets/6184f1ab-690f-47a2-9177-0235f0033973" />


The same configuration checklist can help both administrators and penetration testers.



### What Systems Can Be Reviewed?


Configuration reviews can apply to:
- Linux Servers
- Windows Workstations
- Domain Controllers
- Web Servers
- Database Servers
- File Servers
- Network Appliances
- Cloud Instances

Common areas include:
- Users
- Permissions
- Services
- Policies
- Credentials

## Task 3: Security Baselines and Frameworks


#### Security Baseline

A **security baseline** is a documented standard that defines how a system should be configured securely.

It covers things like:
- Passwords
- File permissions
- Services
- Network settings
- Security policies




### CIS Benchmarks

**CIS Benchmarks** provide secure configuration recommendations for operating systems, applications, cloud platforms, and devices.

| Level       | Meaning                                          |
| ----------- | ------------------------------------------------ |
| **Level 1** | Basic, practical hardening with limited impact   |
| **Level 2** | Stronger hardening, but may affect functionality |


Each recommendation usually includes: ``Recommendation`` -> ``Why it matters`` -> ``How to audit it`` -> ``How to fix it``

Example: ``SSH PermitRootLogin = no``

This prevents direct remote root login through SSH.


### DISA STIGs

**Defense Information Systems Agency (DISA) STIGs**:  are detailed security hardening requirements, mainly used in U.S. government and military environments.


They classify findings by severity:
| Category    | Risk   |
| ----------- | ------ |
| **CAT I**   | High   |
| **CAT II**  | Medium |
| **CAT III** | Low    |



### Relationship to Compliance Standards

- **PCI-DSS (Payment Card Industry Data Security Standard)**: Security requirements for organizations that handle payment card data.
- **ISO 27001 (International Organization for Standardization/International Electrotechnical Commission 27001)**: A framework for managing and protecting information security.
- **NIST 800-53 (National Institute of Standards and Technology Special Publication 800-53)**: A catalog of security and privacy controls for federal information systems and organizations.
- **CIS (Center for Internet Security) Benchmarks / DISA STIGs (Defense Information Systems Agency Security Technical Implementation Guides)**: Detailed system-hardening guidance used to configure systems securely and support compliance requirements.

## Task 4: Automated Compliance Tools

Manually checking a host against hundreds of security rules takes a lot of time. **Automated compliance tools** scan the system against a security baseline and show which settings **pass** or **fail**.


### Nessus

**Nessus** is a commercial scanner from Tenable. It is mainly used for vulnerability scanning, but it can also perform compliance audits against:

Go to: https://www.tenable.com/products/nessus

- CIS Benchmarks
- DISA STIGs
- Custom Policies

It produces reports showing failed checks and recommended fixes.



### Lynis

Lynis is an open-source security auditing tool mainly used on Linux, macOS, and Unix systems.

Go to: https://github.com/CISOfy/lynis

It runs locally on the host and checks:

System Configuration
Permissions
Services
Authentication
Hardening

It produces a hardening index and security findings.


### OpenSCAP

**OpenSCAP** is an open-source framework based on the Security Content Automation Protocol (SCAP).

Go to: https://github.com/OpenSCAP/openscap


It checks a system against security profiles such as:

- CIS
- STIG
- Other SCAP Policies

It produces detailed pass/fail compliance results.



### CIS-CAT

**CIS-CAT (Center for Internet Security Configuration Assessment Tool)** is designed specifically to check systems against **CIS Benchmarks**.

Go to: https://www.cisecurity.org/cybersecurity-tools/cis-cat-pro

It reports:
- Pass
- Fail
- Benchmark Recommendation



### Offensive Enumeration Tools
These tools are designed for **privilege-escalation enumeration** after gaining access to a host.

| Tool        | Platform | Purpose                                       |
| ----------- | -------- | --------------------------------------------- |
| **LinPEAS** | Linux    | Find possible privilege-escalation weaknesses |
| **WinPEAS** | Windows  | Find Windows privilege-escalation weaknesses  |
| **PowerUp** | Windows  | Find insecure Windows configurations          |

## Task 5: Categories of Misconfiguration

<img width="900" height="430" alt="image" src="https://github.com/user-attachments/assets/ddd3199a-3162-46ac-9934-78212e9d7802" />

**Host misconfigurations** are usually grouped into six main categories. These categories help us systematically look for possible privilege-escalation paths.

- **Users and Groups**: Check accounts, group memberships, and excessive privileges.
- **File Permissions**: Look for files or directories with permissions that are too broad or incorrectly assigned.
- **Services**: Check services that run with high privileges and may be insecurely configured.
- **Scheduled Tasks**: Examine tasks or jobs that automatically run and may be controlled by lower-privileged users.
- **Credential Storage**: Look for passwords, keys, or other credentials stored in accessible locations.
- **Network Configuration**: Review network settings, interfaces, ports, and services for insecure configurations.



### User and Group Configuration

Check whether users have **more privileges than they need**.

Common issues:
- Unnecessary administrator group membership
- Overprivileged service accounts
- Default accounts not disabled
- Weak password policies

Excessive user privileges can allow direct escalation.


### File and Directory Permissions

Check who can **read**, **write**, or **execute** files and directories.

#### Linux:
- Unsafe SUID binaries
- World-writable scripts or binaries
- Sensitive files with excessive read permissions

#### Windows:
- Weak ACLs (Access Control Lists)
- Writable directories
- Weak registry permissions

A low-privileged user should not be able to modify resources controlled by higher-privileged users.



### Service Configurations

Check services that run with high privileges.

Common issues:
- Service runs as ``root`` or ``LocalSystem`` unnecessarily
- Service files or binaries are writable
- Incorrect or ambiguous executable paths
- Unquoted service paths on Windows


Flow: ``Low-privileged user`` -> ``Modify service resource`` -> ``Privileged service executes it`` -> ``Higher privileges``.


### Scheduled Tasks and Cron Jobs

Check tasks that automatically execute scripts or programs.

- Linux: ``cron``
- Windows: Task Scheduler

Common issue: ``Privileged scheduled task`` -> ``Runs a writable script`` -> ``Low-privileged user modifies it`` -> ``Privilege escalation``

Other issues can include unsafe handling of filenames, such as **wildcard injection**.



### Credential Storage

Look for **passwords**, **keys**, and **tokens** stored where other users can access them.

#### Linux:
- ``~/.bash_history``
- Environment variables
- Configuration files
- SSH private keys

#### Windows:
- Windows Credential Manager
- ``runas /savecred``
- Registry
- ``Unattend.xml``
- PowerShell history
- ``web.config``

> Finding credentials for a privileged account can provide direct access to higher privileges.



### Network Configuration

Check whether services and ports are exposed more widely than necessary.

Common issues:
- Unnecessary open ports
- Services listening on all interfaces
- Weak firewall rules
- Insecure remote-management protocols
- Database services unnecessarily exposed

Example:
````
127.0.0.1  → Local access only
0.0.0.0    → All network interfaces
````

Poor network configuration increases the host's attack surface and can expose services to attackers.

## Task 6: Structured Enumeration Methodology


### Phase 1: Situational Awareness

First understand the host and our current access.

Check:
- User → Who am I?
- Groups → What privileges do I have?
- OS → Which OS/version/architecture?
- Hostname → What is the machine called?
- Role → Server, workstation, DC, etc.
- Domain → Is it domain-joined?

Main idea: Understand the environment before looking for weaknesses.



### Phase 2: Category-Based Enumeration

<img width="900" height="520" alt="image" src="https://github.com/user-attachments/assets/7f104134-6166-4ee1-8065-a8775c7acda2" />


Check the six categories systematically:
- **Users and Groups**: Find accounts, groups, and administrative privileges.
- **File Permissions**: Find writable files, SUID/SGID binaries, weak ACLs, and sensitive files.
- **Services**: Identify privileged services and check whether their files/configurations can be modified.
- **Scheduled Tasks**: Find privileged cron jobs or scheduled tasks and check referenced scripts/files.
- **Credential Storage**: Search accessible locations for passwords, keys, tokens, and configuration credentials.
- **Network Configuration**: Check listening ports, interfaces, and firewall rules. 



### Phase 3: Prioritisation and Exploitation

After enumeration, you may find many **weaknesses**. Prioritise the ones that provide the most direct and reliable path to higher privileges.

Prioritise Findings

``Many Findings`` -> ``Compare Exploitability`` -> ``Find Most Direct Path`` -> ``Privilege Escalation``

For example:
- **Stored administrator password** → direct access
- **Writable hourly cron script** → requires waiting and additional steps

So the stored credential would generally be investigated first.


####Combine Findings

Sometimes one finding is not enough.

Example:

``Root cron job`` + ``World-writable script`` -> ``Modify script`` -> ``Cron runs as root`` -> ``Elevated privileges``

Individually:
- Cron job → not necessarily insecure
- Writable file → not necessarily useful

Together:
- They create a privilege-escalation path.

This is called chaining findings.



### The Role of Automated Tools

Tools such as:
- LinPEAS
- WinPEAS
- PowerUp

automatically check many privilege-escalation categories.

But they are a **supplement**, **not a replacement**.

We should understand:

``What was checked?`` -> ``Why is it a weakness?`` -> ``Is it actually exploitable?`` -> ``Are there false positives?`` -> ``What did the tool miss?``


Results from **Nessus** or **Lynis can also help identify which categories deserve investigation.

## Task 7: Reading a CIS Benchmark


### Structure of a Recommendation

A CIS Benchmark recommendation tells you what a secure setting should look like, why it matters, how to check it, and how to fix it.

- **Title**: What is being checked.
- **Profile**: Level 1 or Level 2.
- **Description**: What the secure configuration should be.
- **Rationale**: Why the setting is important.
- **Audit**: How to check it.
- **Remediation**: How to fix it.


``/etc/shadow permissions`` -> ``Check ownership & permissions`` -> ``Secure → Pass, Insecure → Fail``


### Reading from an Offensive Perspective

A pentester looks at a failed recommendation and asks:

> Can this weakness help me gain higher privileges?

Example: ``/etc/shadow is readable`` -> ``Obtain password hashes`` -> ``Attempt offline cracking`` -> ``Possible privileged account access``

Not every failed check is directly exploitable. Some need to be **combined with other findings**.



### Mapping to Automated Tool Output

Security tools can report the same weaknesses described in CIS Benchmarks.

For example: ``CIS Check`` -> ``FAILED`` -> ``/etc/shadow permissions are too broad``

A tool such as Nessus or Lynis may detect this from a compliance perspective, while LinPEAS may identify it from an offensive perspective.

> Understanding the CIS recommendation behind a tool finding helps us understand what the problem means and whether it may be exploitable.

## Task 8=9: Conclusion

| Topic                     | Remember This                                                                                   |
| ------------------------- | ----------------------------------------------------------------------------------------------- |
| **Privilege Escalation**  | Move from **low privilege → higher privilege** such as `root`, `Administrator`, or `SYSTEM`.    |
| **Two Types**             | **Vulnerability-based** = software bugs/CVEs. **Configuration-based** = insecure settings.      |
| **Configuration Review**  | Check **settings, permissions, services, and policies** against a secure baseline.              |
| **Security Baseline**     | Defines what a **secure system should look like**.                                              |
| **CIS Benchmarks**        | Security configuration recommendations from the **Center for Internet Security**.               |
| **DISA STIGs**            | Detailed **security-hardening requirements**.                                                   |
| **Audit Tools**           | **Nessus, Lynis, OpenSCAP, CIS-CAT** check configuration and compliance.                        |
| **Offensive Tools**       | **LinPEAS, WinPEAS, PowerUp** look for possible privilege-escalation weaknesses.                |
| **Users & Groups**        | Look for **unnecessary or excessive privileges**.                                               |
| **File Permissions**      | Check **writable privileged files, SUID/SGID, and weak ACLs**.                                  |
| **Services**              | Check **privileged services** and whether their files/configurations can be modified.           |
| **Scheduled Tasks/Cron**  | Check privileged tasks that execute **modifiable scripts or files**.                            |
| **Credentials**           | Look for **passwords, keys, and tokens** stored in accessible locations.                        |
| **Network**               | Check **open ports, exposed services, interfaces, and firewall rules**.                         |
| **Situational Awareness** | Identify **user, groups, OS, version, architecture, hostname, role, and domain**.               |
| **Prioritisation**        | Focus on the **most direct and reliable escalation path**.                                      |
| **Finding Chains**        | Multiple findings can combine to create an escalation path.                                     |
| **CIS Recommendation**    | **Title → Profile → Description → Rationale → Audit → Remediation**.                            |
| **Failed CIS Check**      | Ask: **What risk does this create? Can it lead to privilege escalation?**                       |
| **Main Method**           | **Understand → Enumerate → Connect findings → Prioritise → Investigate**.                       |
| **Main Mindset**          | Don't just ask **“What exploit can I run?”** Ask **“What can my account access or influence?”** |


### Six Categories to Memorize

| Category                 | Ask Yourself                                  |
| ------------------------ | --------------------------------------------- |
| **Users & Groups**       | Who has extra privileges?                     |
| **File Permissions**     | What can I read, write, or execute?           |
| **Services**             | What privileged services can I influence?     |
| **Scheduled Tasks/Cron** | What runs automatically with high privileges? |
| **Credentials**          | Where are passwords, keys, or tokens stored?  |
| **Network**              | What services and ports are exposed?          |
