## Task 1: Introduction

### What Is Command Injection?

**Command Injection** happens when a web application takes user input and puts it directly into an OS command.

``User input`` -> ``Web Application`` -> ``OS Command`` -> ``Operating System``

If the application doesn't properly validate the input, an attacker may add an extra command.


### Simple Example

Suppose the application runs:

ping USER_INPUT

Normal input:

8.8.8.8

The server runs:

ping 8.8.8.8

If user input is improperly handled, additional shell syntax can cause another command to execute.

The important idea is:

> ``Expected input`` -> ``OS command``
> 
> ``Malicious input`` -> ``OS command + attacker command``



### Why Is It Dangerous?

The injected command runs with the **same permissions as the web application**.

For example: ``Web server`` -> ``runs as "www-data"`` -> ``injected command`` -> ``runs as "www-data"``

If the application has higher privileges, the impact can be much greater.



### Command Injection vs RCE

These terms are related but not exactly the same.

| Term                        | Meaning                                                    |
| --------------------------- | ---------------------------------------------------------- |
| **Command Injection**       | Injecting OS commands through vulnerable application input |
| **RCE**                     | An attacker can execute code remotely                      |
| **Command Injection → RCE** | Command injection can result in RCE                        |


Think like: ``Command Injection`` ->  ``Attacker executes OS command`` -> ``Possible RCE``

## Task 2: Discovering Command Injection

What is Command Injection?

**Command Injection** happens when an application takes user input and puts it directly into an operating system command.

The attacker can add another command that the developer did not intend.

Flow: ``User input`` -> ``Web application`` -> ``OS command`` -> ``Server executes it``

If user input is not checked:

``Normal input`` → ``normal command``

``Malicious input`` → ``original command`` + ``attacker command``


#### Common Functions
| Language | Functions that can execute commands                |
| -------- | -------------------------------------------------- |
| PHP      | `exec()`, `system()`, `shell_exec()`, `passthru()` |
| Python   | `subprocess`                                       |
| Node.js  | `child_process.exec()`                             |

These functions are **not automatically vulnerable**. The problem happens when **untrusted user input** reaches them without proper validation.


### PHP Example
The following PHP application allows a user to search for a song title within a text file stored on the server.
````php
<?php
$songs = "/var/www/html/songs";                                    // 1

if (isset($_GET["title"])) {
    $title = $_GET["title"];                                       // 2

    $command = "grep $title /var/www/html/songtitle.txt";          // 3

    $search = exec($command);                                      // 4
    if ($search == "") {
        $return = "<p>The requested song</p><p> $title does </p><b>not</b><p> exist!</p>";
    } else {
        $return = "<p>The requested song</p><p> $title does </p><b>exist!</b>";
    }

    echo $return;
}
?>
````



#### The application uses:
````
$command = "grep $title /var/www/html/songtitle.txt";
$search = exec($command);
````
The important part is: ``User input`` → ``$title`` → ``$command`` → ``exec()``

For example: ``title=Yesterday``

becomes: ``grep Yesterday /var/www/html/songtitle.txt``

This is normal.


#### Where is the Vulnerability?

The application directly places ``$title`` inside the command:
````
$command = "grep $title /var/www/html/songtitle.txt";
````


There is **no sanitisation or validation**.

Therefore, special shell characters can change how the command is interpreted.

For example, in the lab:
````
title=; cat /etc/passwd
````
can result in:
````
grep ; cat /etc/passwd /var/www/html/songtitle.txt
````

The ``;`` tells the shell:

- Command 1 → ``grep``
- Command 2 → ``cat /etc/passwd``


So the second command can read the file.



#### Important Pattern

Remember this: ``User Input`` -> ``Command Construction`` -> ``exec()`` -> ``Operating System``

If there is no proper validation between the user and the command: ``User Input`` -> ``Command Injection`` -> ``OS Command Execution``



### Python Example

This problem is not specific to PHP. It can occur in any language that allows applications to make system calls. The following example uses the Python Flask web framework.
````py
import subprocess
from flask import Flask                                            # 1
app = Flask(__name__)

def execute_command(shell):                                        # 2
    return subprocess.Popen(shell, shell=True, stdout=subprocess.PIPE).stdout.read()

@app.route('/<shell>')                                             # 3
def command_server(shell):
    return execute_command(shell)
````


````
def execute_command(shell):
    return subprocess.Popen(
        shell,
        shell=True
    )
````


The important part is:
````
shell=True
````
If the application passes user-controlled input directly into this function, the input can become an OS command.

For example, the lab demonstrates a route like:
````
http://flaskapp.thm/whoami
````
The application passes whoami to the command execution function.

Result: ``whoami`` -> ``Server executes command`` -> ``Returns the result``


You are not expected to fully understand every line of this code. What matters is the overall behaviour.

- At (``1``), the ``flask`` package sets up a web server.
- At (``2``), the ``execute_command`` function uses the ``subprocess`` module to run whatever string is passed to it as a system command.
- At (``3``), a route is defined so that whatever value appears in the URL path is handed directly to that function and executed. Visiting http://flaskapp.thm/whoami would run the whoami command on the server and return the result.



### PHP vs Python
| PHP                  | Python                      |
| -------------------- | --------------------------- |
| `exec()`             | `subprocess`                |
| `system()`           | `subprocess.Popen()`        |
| `shell_exec()`       | `subprocess.run()`          |
| `passthru()`         | Can execute system commands |
| User input → command | User input → command        |

## Task 3: Exploiting Command Injection


- **Command injection** happens when user input is used to build system commands without proper sanitization.
- Attackers exploit shell operators like ``;``, ``&``, ``&&`` to chain extra commands.
- **Verbose injection**: output is shown directly (e.g., ``; whoami``).
- **Blind injection**: command runs but no output is returned, requiring indirect confirmation (like time delays or side effects).
- **Risk**: can lead to full system compromise if attackers execute arbitrary commands.


### Detecting Blind Command Injection

**Blind command injection** means the command executes, but the application does not show the command's output.


#### Use a Time Delay

A common way to test this is with ``ping`` or ``sleep``.
````
; ping -c 10 127.0.0.1
````
If the page takes about 10 seconds longer to respond, this is a strong sign that command injection worked.

``Input`` -> ``; ping -c 10 127.0.0.1`` -> ``Server executes command`` -> ``Output is hidden`` -> ``Response is delayed``


#### Write Output to a File

We can redirect the command's output into a file using ``>``.
````
; whoami > /var/www/html/output.txt
````

Then access: ``http://target.thm/output.txt``

If it shows: ``www-data``

the command executed successfully.




#### Test with curl

We can send the payload using curl:
````
curl 'http://vulnerable.app/process.php?search=The%20Beatles%3B%20whoami'
````
Important URL encoding:
| Encoded | Meaning |
| ------- | ------- |
| `%20`   | Space   |
| `%3B`   | `;`     |

So: `The%20Beatles%3B%20whoami`


becomes: `The Beatles; whoami`


In this if we want to `Decode` and `Encode` go to: https://www.urldecoder.org/

### Detecting Verbose Command Injection

**Verbose injection**: the application shows the output of the injected command directly in its response.

Example: adding ``; whoami`` to a vulnerable input in a ping tool → the server runs whoami and displays the username right below the ping results.

Easy to detect because the command’s output is immediately visible.

Common starter commands: ``ping`` and ``whoami`` since their output is recognizable.

#### Useful Payloads

Once command injection is confirmed, these commands help you learn about the target.

##### Linux
| Payload  | What it does                                               |
| -------- | ---------------------------------------------------------- |
| `whoami` | Shows which user the application runs as                   |
| `ls`     | Lists files/directories                                    |
| `ping`   | Creates a delay; useful for **blind injection**            |
| `sleep`  | Creates a time delay; alternative to `ping`                |
| `nc`     | Netcat; can be used for network connections/reverse shells |


##### Windows

| Payload   | What it does                                    |
| --------- | ----------------------------------------------- |
| `whoami`  | Shows which user the application runs as        |
| `dir`     | Lists files/directories                         |
| `ping`    | Creates a delay; useful for **blind injection** |
| `timeout` | Creates a time delay; alternative to `ping`     |

### Blind vs Verbose Command Injection
| Type                          | Meaning                                                               | What happens                                                          | How to detect                                                      | Example                                        |
| ----------------------------- | --------------------------------------------------------------------- | --------------------------------------------------------------------- | ------------------------------------------------------------------ | ---------------------------------------------- |
| **Verbose Command Injection** | The application **shows the output** of your injected command         | You inject a command and its result appears in the HTTP response/page | Look for command output directly in the response                   | `; whoami` → page shows `www-data`             |
| **Blind Command Injection**   | The application **executes the command but does not show its output** | The command runs on the server, but the webpage looks normal          | Use **time delays**, file output, or other observable side effects | `; sleep 5` → response takes ~5 seconds longer |
| **Verbose**                   | Output is visible                                                     | Easy to confirm                                                       | Read the response                                                  | `whoami` → `apache`                            |
| **Blind**                     | Output is hidden                                                      | Harder to confirm                                                     | Measure response time or create/read a file                        | `sleep 5` → noticeable delay                   |

## Task 5: Remediating

**Command injection** happens when an application takes user-controlled input and places it directly into an operating-system command.

> Do not allow untrusted input to become part of a system command.


#### Vulnerable Functions
| PHP Function | Purpose                                   | Risk                          |
| ------------ | ----------------------------------------- | ----------------------------- |
| `exec()`     | Executes a command                        | High if user input reaches it |
| `passthru()` | Executes a command and outputs the result | High if input is uncontrolled |
| `system()`   | Executes a command and returns output     | High if input is uncontrolled |




#### Example from the Lesson


Restrict the input
````
<input type="text" id="ping" name="ping" pattern="[0-9]+">
````
The important part is: ``pattern="[0-9]+"``

It means: ``0 → 9``

Only digits are allowed by the browser.

So: ``127001``

is allowed.

But something like:
````
127.0.0.1; whoami
````
doesn't match the pattern.



#### The server executes the value
````
echo passthru("/bin/ping -c 4 " . $_GET['ping']);
````
The application intends to create:
````
/bin/ping -c 4 127.0.0.1
````
The problem is that ``$_GET['ping']`` comes from the user.


#### Why Client-Side Validation Is Not Enough

The HTML pattern is useful, but an attacker doesn't have to use the browser form.

For example: ``Browser`` -> ``HTML pattern`` -> ``Server``

An attacker can instead send a request directly: ``curl`` -> ``Server``

Therefore:

> Client-side validation can be bypassed.

We need server-side validation as well.

Defense
| Defense                    | What it does                          | Importance                                    |
| -------------------------- | ------------------------------------- | --------------------------------------------- |
| **Allowlist input**        | Accept only expected values           | Very important                                |
| **Server-side validation** | Validates input on the server         | Very important                                |
| **Client-side validation** | Provides basic browser-side filtering | Helpful, but bypassable                       |
| **Avoid shell commands**   | Use safe APIs instead                 | Best when possible                            |
| **Escape input**           | Reduces shell interpretation          | Useful, but not the preferred primary defense |




### Input Sanitisation

Input sanitisation means checking and cleaning user input on the server before using it.

> Only accept the type of input the application actually expects.



#### Server-Side Input Validation

The lesson uses PHP's filter_input():
````
if (!filter_input(INPUT_GET, "number", FILTER_VALIDATE_NUMBER)) {
    // Invalid input
}
````
Conceptually: ``User input`` -> ``Server receives input`` -> ``Validate input`` -> ``Valid? ── No ──→ Reject`` ->  ``Yes`` -> ``Process input``



#### Input Sanitisation vs Validation
| Technique                  | Meaning                                      | Example                     |
| -------------------------- | -------------------------------------------- | --------------------------- |
| **Validation**             | Check whether input matches what is expected | Only accept numbers         |
| **Sanitisation**           | Clean/remove unwanted characters             | Remove dangerous characters |
| **Allowlist**              | Define exactly what is permitted             | `en`, `fr`, `de` only       |
| **Blocklist**              | Define what is forbidden                     | Block `;`, `&&`, `\|`       |
| **Server-side validation** | Validation performed by the server           | `filter_input()`            |
| **Client-side validation** | Validation performed by browser              | HTML `pattern`              |


#### Bypassing Filters

Filters are not always perfect.

A weak filter might remove or block particular characters, but an attacker may try to represent the same data differently.


Exalpme like, hexadecimal encoding:
````
$payload = "\x2f\x65\x74\x63\x2f\x70\x61\x73\x73\x77\x64";
````

This represents: ``/etc/passwd``

The important concept is: ``Original input`` -> ``Filter`` -> ``Filter doesn't recognise encoded form`` -> ``Application decodes/interprets it`` -> ``Original meaning``




#### Why this matters
| Filter behavior                | Problem                                                |
| ------------------------------ | ------------------------------------------------------ |
| Blocks only one representation | Alternative encoding may bypass it                     |
| Blocks individual characters   | Other representations may exist                        |
| Only validates in browser      | Direct requests can bypass browser controls            |
| Uses a blocklist               | Difficult to anticipate every dangerous representation |
| Uses an allowlist              | Much harder to provide unexpected input                |




#### Defense in Depth
Don't rely on a single filter.
| Layer                    | Purpose                                              |
| ------------------------ | ---------------------------------------------------- |
| **Input validation**     | Ensure input has the expected format                 |
| **Allowlisting**         | Permit only known-good values                        |
| **Sanitisation**         | Remove/normalise unwanted data where appropriate     |
| **Safe APIs**            | Avoid passing user input to a shell                  |
| **Least privilege**      | Limit damage if something is exploited               |
| **Server-side controls** | Don't rely on browser validation                     |
| **Multiple layers**      | Prevent one bypass from becoming a successful attack |
