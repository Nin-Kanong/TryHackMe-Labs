### Authentication

<img width="1900" height="823" alt="image" src="https://github.com/user-attachments/assets/d80c1651-ef50-4cb8-b087-77de50499522" />


**Authentication** = **proving who you are.**

Example:
````
User
  |
  | username + password
  v
Application Server
  |
  | Check credentials
  v
Credential Store
  |
  | Match?
  v
Application Server
  |
  | Session token
  v
User
````

For example:
````
Username: alice
Password: password123
````

The server checks whether those credentials are correct.

If they are correct: ``Login successful`` -> ``Server creates session`` -> ``Session token/cookie`` -> ``Used with future requests``

The server then uses that session to determine what the user can access.



### Authentication Bypass

**Authentication bypass** = **getting to protected functionality without properly proving your identity**.

Normal flow: ``Valid credentials`` -> ``Authentication`` -> ``Session`` -> ``Protected page`` -> ``ACCESS``.

Bypass:
````
Attacker
   |
   | No valid credentials
   v
Protected functionality
   |
   v
ACCESS
````
The attacker doesn't necessarily need to steal a password or session token.

They might exploit a ``mistake in how the application handles authentication``.

## Task 2: Types of Authentication Bypass


<img width="1569" height="895" alt="image" src="https://github.com/user-attachments/assets/8c6e8b58-9d5c-4d39-b259-e355f1c7303c" />


The lesson is basically saying there are 4 common ways authentication can be bypassed.
| # | Type                       | Easy meaning                                                               | Result                                            |
| - | -------------------------- | -------------------------------------------------------------------------- | ------------------------------------------------- |
| 1 | **Username Enumeration**   | Find out which usernames/accounts actually exist                           | List of valid accounts                            |
| 2 | **Credential Brute Force** | Try many username + password combinations                                  | Find a working login                              |
| 3 | **Logic Flaws**            | Abuse a mistake in the login/password-reset process                        | Access an account without the correct credentials |
| 4 | **Cookie Manipulation**    | Change a session cookie so the server thinks you have different privileges | Elevated access                                   |


### 1. Username Enumeration
The application may respond **differently** when a username exists versus when it doesn't.


Example:
````
Username: alice
Response: "Account exists"

Username: xyz123
Response: "Account does not exist"
````
An attacker can use this difference to build:
````
Valid usernames:
- alice
- bob
- charlie
````

> We aren't finding the password yet. We're first finding which accounts exist.


### 2. Credential Brute Force

Once you have usernames, you can test passwords against them.

``Username list + Password list`` -> ``Login attempts`` -> ``Working username + password``

For example:
````
alice : password1 → No
alice : welcome1  → No
alice : admin123  → Yes
````

> Try many credential combinations until a valid one is found.
> 
> In a real assessment, this should only be done with authorization and appropriate rate limits.
 


### 3. Logic Flaws

This is different from brute forcing.

A **logic flaw** means the developer made a mistake in how the authentication process works.

For example, imagine:
````
Password Reset

Step 1 → Enter username
Step 2 → Receive reset code
Step 3 → Set new password
````
If the application incorrectly trusts something controlled by the client, an attacker might manipulate the workflow.

Expected: ``User`` → ``Step 1`` → ``Step 2`` → ``Step 3`` → ``Reset password``

Flawed: ``User`` → ``manipulate request`` → ``Step 3`` -> ``Password changed``

> We exploit a mistake in the application's logic, rather than guessing the password.


### 4. Cookie Manipulation

After login, a server may give the browser a cookie representing the session.

Example: ``Set-Cookie: role=user``

If the application blindly trusts an editable cookie, changing its value could cause an authorization problem.

Conceptually:

Normal: ``role=user`` -> ``Server`` -> ``Normal privileges``

Potentially vulnerable: ``role=admin`` -> ``Server`` -> ``Admin privileges``

A secure application should **not blindly trust client-controlled session data**.




### Use Cases and Impact

The second image explains what happens if an authentication bypass succeeds.

#### Normal user account
An attacker might gain access to:
- Personal information
- Transaction history
- User records

#### Administrator account
The impact can be much greater:
- View other users' data
- Change application settings
- Access administrative functions
- Potentially reach server-side functionality


````
Authentication bypass
        ↓
Compromised account
        ↓
What privileges does it have?
        ↓
Low privilege ──→ Limited impact
        |
        └── Admin ──→ Much higher impact
````


A bypass can also be the **first step** of a larger attack: ``Authentication bypass`` -> ``Get valid session`` -> ``Access privileged functionality`` -> ``Discover more weaknesses`` -> ``Potentially compromise more of the system``

## Task 3: Username Enumeration

### What is Username Enumeration?

**Username enumeration** means finding out which usernames/accounts ``actually exist`` on a website.

Example:
````
admin     → Account already exists
john      → Account already exists
random123 → Account does not exist
````
The attacker can then use the valid usernames for attacks such as:
- Brute force
- Password spraying
- Targeted phishing



### Where can usernames leak?

Common places include:

| Location       | What happens                                             |
| -------------- | -------------------------------------------------------- |
| Signup         | Website says the username is already registered          |
| Login          | Different message for unknown username vs wrong password |
| Password reset | Website says whether an email exists                     |
| API            | Different response for valid/invalid usernames           |


> If the application responds differently, we may be able to identify valid accounts.


> **Note**: **Phishing** When emails are sent to a target(s) purporting to be from a trusted entity to lure individuals into providing sensitive information.

## Task 4: Brute-Forcing a Login Form

A **brute-force attack** means trying many username and password combinations until the correct credentials are found.

<img width="1759" height="895" alt="image" src="https://github.com/user-attachments/assets/0abfc00a-9537-46dc-8ad2-f28a953ed38d" />

````
200 = Login failed

````
Therefore:
````
steve + letmein
       ↓
    HTTP 302
       ↓
Successful login
````

### Success Conditions

A brute-force tool needs to know:

> How does the website tell us that the login was successful?

#### Failed login

The server returns:
````
HTTP 200
````
and shows the login page again.

#### Why Do We Need a Success Condition?

Imagine ffuf tries 500 combinations.

If every response looks similar, you need a way to identify the correct one.

For example:
````
simon + password → 200
simon + admin    → 200
steve + password → 200
steve + letmein  → 302
mary + admin     → 200
````
We immediately know:
````
steve : letmein
````
is the interesting result.


#### Successful login

The server returns:
````
HTTP 302
````
and redirects the user to the dashboard.

| Response | Meaning          |
| -------- | ---------------- |
| `200`    | Failed login     |
| `302`    | Successful login |

> The **302 redirect is the success signal**.

## Task 5: Login Flaws

<img width="1840" height="895" alt="image" src="https://github.com/user-attachments/assets/bdac8d43-779d-458b-a62c-b6b0375c7286" />


A **logic flaw** happens when an application follows rules that are individually reasonable, but the rules do not work correctly together.

The attacker does not necessarily need to send invalid input. Instead, they find a way to make the application follow an unintended sequence.


### A Case-Sensitive Path Comparison

The application has two components that interpret URLs differently.

For example: ``/admin``

and: ``/adMin``

One component may treat them as different, while another treats them as the same.



**Normal**: ``/admin`` -> ``Authorization check`` -> ``Admin page``.

**Vulnerable**: ``/adMin`` -> ``Router treats it like /admin`` -> ``Admin page`` -> ``Authorization check is skipped``

> The vulnerability occurs because two parts of the application disagree about the same input.

> **Different interpretation → security check bypass**

Consider the following server-side snippet, which decides whether to apply an administrator privilege check before rendering a page:
````
if( url.substr(0,6) === '/admin') {
    # Code to check user is an admin
} else {
    # View Page
}
````
The ``===`` operator performs a strict equality check, so ``/admin`` enters the privileged branch but ``/adMin`` does not. If the routing layer underneath is case-insensitive and maps ``/adMin`` to the same handler as ``/admin``, the request reaches the administrative page with no privilege check performed.

## Task 6: Cookie Manipulation


**HTTP is stateless**: every request is independent.

**Cookies** are used so web apps can remember who you are after login.

If a cookie holds the **session state**, the server trusts its content to decide if you’re authenticated.

**Unsigned cookies** are dangerous → attackers can edit them to impersonate another user.

Vulnerable apps often use cookies in plain text, hashed, or encoded formats without proper signing.

## Task 7: Conclusion

### Authentication Bypass — Mitigation

| **Vulnerability**        | **What is the problem?**                                                 | **How to defend**                                                                  | **Easy way to remember**              |
| ------------------------ | ------------------------------------------------------------------------ | ---------------------------------------------------------------------------------- | ------------------------------------- |
| **Username Enumeration** | Application reveals whether a username/email exists                      | Return identical response body, status code, and timing. Add rate limiting/CAPTCHA | **Don't reveal valid accounts**       |
| **Brute Force**          | Attacker repeatedly guesses passwords                                    | Rate limiting, account lockout, MFA, strong/long passwords                         | **Limit guessing**                    |
| **Logic Flaws**          | Application uses inconsistent or untrusted inputs for security decisions | Use one trusted source for each security decision; avoid `$_REQUEST`               | **One decision → one trusted source** |
| **Cookie Tampering**     | Attacker modifies information stored in a cookie                         | Use signed tokens (HMAC/JWT) or server-side sessions                               | **Don't trust client data**           |
| **Hashing Cookie**       | A plain hash does not prove the server issued the value                  | Use HMAC/signatures or opaque server-side session IDs                              | **Hash ≠ Signature**                  |



### Cookie Security
| **Method**             | **Secure?** | **Why?**                                           |
| ---------------------- | ----------- | -------------------------------------------------- |
| Plain-text cookie      | No          | User can directly modify it                        |
| Base64 cookie          | No          | Base64 is reversible encoding                      |
| Hashed cookie          | Not enough  | Hash alone doesn't authenticate the issuer         |
| HMAC-signed cookie     | Yes         | Modification causes signature verification to fail |
| Server-side session ID | Yes         | Actual session data stays on the server            |
