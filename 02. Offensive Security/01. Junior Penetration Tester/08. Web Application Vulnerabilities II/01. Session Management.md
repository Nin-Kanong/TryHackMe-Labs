## Task 1: Introduction

When we log in to a website, we don't send our username and password with every request. Instead, the website gives our browser a session.

<img width="1024" height="500" alt="image" src="https://github.com/user-attachments/assets/9b653dc5-3f11-41ce-9fb2-e6378ef8bd7d" />

``Login`` -> ``Username + Password`` -> ``Server verifies us`` -> ``Session created`` -> ``Browser stores session information`` -> ``Future requests use the session``.


### Authentication vs Authorisation
| Concept            | Meaning                     | Example                           |
| ------------------ | --------------------------- | --------------------------------- |
| **Authentication** | Who are you?                | You successfully log in as User 1 |
| **Authorisation**  | What are you allowed to do? | User 1 can view their own profile |
| **Session**        | Keeps you logged in         | Browser sends a session cookie    |


### Why session management matters

If a website handles sessions incorrectly, an attacker may be able to:

``Steal/guess session`` -> ``Use another user's session`` -> ``Act as that user`` -> ``Session hijacking``


### Main things this lesson teaches
- What session management is
- Difference between authentication and authorisation
- The two main session-management methods
- The session lifecycle
- How vulnerable session management can be exploited

> **Note**: Authentication proves who you are; the session lets the website remember that you're logged in.

## Task 2: What is Session Management

### What is the lesson trying to teach?

The main problem is:

**HTTP does not remember us.**

Every HTTP request is independent.

For example:
````
Request 1 → "Give me the login page"
Request 2 → "Give me my profile"
Request 3 → "Give me my orders"
````
The server normally doesn't automatically know that all 3 requests came from the same logged-in person.

So websites use ``sessions``.


### Session Management Lifecycle

The best way to learn about session management is to use the session management lifecycle, as shown in the animation below.

<img width="1024" height="400" alt="image" src="https://github.com/user-attachments/assets/d5d28e56-936f-462a-a5fd-ce99fd2ab116" />



#### 1. Session Creation

When we log in:
````
Username: Alice
Password: 123456
        ↓
      Server
        ↓
Session created
        ↓
session_id = ABC123
````
The server creates a session and associates it with our account:
````
ABC123 → Alice
````
our browser receives the session ID, usually through a cookie.

So instead of sending our password every time, òur browser sends:

``Cookie: session_id=ABC123``



#### 2. Session Tracking

Now we visit our profile.
````
Browser
   |
   | Cookie: session_id=ABC123
   ↓
Server
````
The server looks up:
````
ABC123 → Alice
````
Therefore the server knows:

> This request belongs to Alice.

Then you request our orders:
````
Browser
   |
   | session_id=ABC123
   ↓
Server
   |
   ↓
ABC123 = Alice
   |
   ↓
Return Alice's orders
````
**This is session tracking**.




#### 3. Session Expiry

A session shouldn't remain valid forever.

For example:
````
ABC123
   ↓
30 minutes of inactivity
   ↓
Session expires
````

Now if the browser sends:

``Cookie: session_id=ABC123``

the server should respond:

``Session expired`` → ``Login again``

Why?

> Because an old session ID should not give permanent access to an account.



#### 4. Session Termination

This is different from simply waiting for the session to expire.

We explicitly click:
````
Logout
````
The server should destroy/invalidate the session:
````
ABC123 → Alice

Logout
   ↓
ABC123 → INVALID
````
Even if the session hasn't reached its normal expiration time, it should no longer work.

### The important difference
| Concept                 | What happens                                           |
| ----------------------- | ------------------------------------------------------ |
| **Session Creation**    | Server creates a session for the user                  |
| **Session Tracking**    | Server uses the session ID to recognize the user       |
| **Session Expiry**      | Session becomes invalid because its lifetime ended     |
| **Session Termination** | Session is deliberately invalidated, usually by logout |

## Task 3: Authentication vs Authorisation

<img width="1141" height="212" alt="image" src="https://github.com/user-attachments/assets/1d8949fa-7822-4100-95b9-616a3e58b746" />


### 1. Identification

**Who are you?**

We tell the website who you are.

Example:
````
Username: alice
````
We're saying:

> I am Alice.

This doesn't prove that we're Alice yet.


### 2. Authentication

**Prove it**

The website checks our password or another credential.
````
Username: alice
Password: ********
       ↓
     Server
       ↓
   Password correct?
       ↓
      YES
````
Now the website knows:

> This really is Alice.

After successful authentication, the application can create a session for Alice.


### 3. Authorisation

**What are you allowed to do?**

Now that the website knows we're Alice, it needs to decide what Alice is allowed to access.

For example:
````
Alice
  ↓
Authenticated
  ↓
Can view profile?  YES
Can edit profile?  YES
Can delete users?  NO
Can access admin panel?  NO
````
This is **authorisation**.





### 4. Accountability

**What did you do?**

The application records actions.

Example: ``Alice`` -> ``Login`` -> ``Viewed profile`` -> ``Changed email`` -> ``Downloaded document`` -> ``Logout``.

The server can keep logs such as:
````
User: Alice
Action: Changed email
Time: 10:30
Session: ABC123
````
This is useful when investigating a security incident.


---


### IAAA and Session Management

**Login** → **Create session** → **Check permissions** → **Record actions**

The important difference is:

| Concept            | Question                    |
| ------------------ | --------------------------- |
| **Identification** | Who do you claim to be?     |
| **Authentication** | Can you prove it?           |
| **Authorisation**  | What are you allowed to do? |
| **Accountability** | What did you do?            |



Now that we understand the differences between authentication and authorization, let's connect them to session management:
| **IAAA Step**       | **Role in Session Management**                                                                                                                                                   |
| ------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Identification** | The user claims an identity, such as providing a username. This is the first step before a session can be created.                                                               |
| **Authentication** | **Creates the session.** When the user proves their identity, such as with a password, the server starts a new session and issues a session cookie/token.                        |
| **Authorization**  | **Enforces permissions during the session.** For every request with a valid session, the server checks whether the user is allowed to perform the action or access the resource. |
| **Accountability** | **Logs session activity.** Actions performed during the session are recorded with the session ID, creating an audit trail for investigating incidents.                           |

## Task 4: Cookies vs Tokens

> **Cookie = browser manages the session automatically.**
> 
> **Token = JavaScript manages and sends the session token.**


### 1. Cookie-Based Session Management

After login, the server can send:
````
Set-Cookie: session=12345;
````
The browser stores:
````
session = 12345
````
Then when we make another request:
````
Browser
   |
   | Cookie: session=12345
   ↓
Server
````

The browser **automatically sends the cookie** when the cookie matches the request's domain/path rules.

Important cookie protections: 
| Attribute    | Meaning                                               |
| ------------ | ----------------------------------------------------- |
| **Secure**   | Send the cookie only over HTTPS                       |
| **HttpOnly** | JavaScript cannot directly read the cookie            |
| **Expire**   | Defines when the cookie becomes invalid               |
| **SameSite** | Controls when cookies are sent in cross-site requests |



### 2. Token-Based Session Management

With tokens, the application usually gives JavaScript a token after login.

Example: ``Login`` -> ``Server`` -> ``Token`` -> ``JavaScript`` -> ``LocalStorage``.


Then JavaScript gets the token and puts it into a request header:
````
Authorization: Bearer eyJ...
````
So:
````
Browser
   |
   | Authorization: Bearer TOKEN
   ↓
Server
````

Unlike cookies, the browser doesn't automatically attach this token to every request. **The application code has to add it**.



### Benefits and Drawbacks: Cookies vs Tokens
| **Cookie-Based Session** | **Explanation**                                                                               | **Token-Based Session**             | **Explanation**                                                                      |
| ------------------------ | ---------------------------------------------------------------------------------------------------- | ----------------------------------- | ------------------------------------------------------------------------------------------- |
| **Automatically sent**   | Browser automatically sends the cookie with matching requests.                                       | **Manually submitted**              | JavaScript normally reads the token and puts it into the request header.                    |
| **Security attributes**  | Cookies can use `HttpOnly`, `Secure`, `SameSite`, etc.                                               | **No automatic cookie protections** | Tokens don't get those cookie protections automatically; the application must protect them. |
| **CSRF concern**         | Cookies can be affected by traditional CSRF because browsers automatically attach them.              | **Traditional CSRF is reduced**     | A token in a header isn't automatically attached by the browser to a cross-site request.    |
| **Domain-specific**      | Cookies are associated with domains/paths, which can make distributed applications more complicated. | **Good for distributed APIs**       | Tokens can be explicitly sent to different APIs/services by application code.               |

## Task 5: Securing the Sessions Lifecycle

### 1. Session Creation

Session creation happens after a user logs in successfully.

The server gives the user a **session value** (session ID/token). The browser then sends this value with later requests so the server knows which user is making the request.
````
User
  |
  | Username + Password
  v
Server
  |
  | Login successful
  v
Create Session
  |
  | session=ABC123
  v
Browser
````
The important security question is:

> **Is the session value unpredictable?**


#### Weak Session Values

**A weak session value** is a session ID that an attacker can **guess or predict**.

For example, imagine a vulnerable application creates sessions like this:
````
User 1 → session=1001
User 2 → session=1002
User 3 → session=1003
````
The attacker might receive:
````
session=1001
````
and notice the pattern.

They could try:
````
session=1002
session=1003
session=1004
````
If the server accepts one of these as another user's session, the attacker could potentially impersonate that user.



#### Controllable Session Values

This is similar to weak sessions, but the important difference is:

> The attacker can influence or control information used to create or validate the session.

For example, imagine a badly designed token: ``user=alice&role=user``

If the application trusts values supplied by the client, changing something like: ``role=user`` to: ``role=admin``.

could potentially cause an authorization problem.

With JWTs, the server must properly verify things such as: ``Token`` -> ``Signature verification`` -> ``Is it valid?`` -> ``Are the claims trustworthy?``.

Example:
````
Client
  |
  | "I am user=alice, role=admin"
  ↓
Server
  |
  |  Trusts client-controlled information
  ↓
Admin access
````
A secure application should not blindly trust client-controlled session information.



#### Session Fixation

The problem occurs when the application gives a user a session ID **before login** and then fails to change it after login.


Example:
````
1. Attacker gets session ID

session=ABC123

        ↓

2. Victim logs in

        ↓

3. Server keeps:

session=ABC123

        ↓

4. Attacker knows ABC123

        ↓

5. Attacker may be able to use that session
````


The secure behavior is:
````
Before login:

session=ABC123

        ↓
       LOGIN
        ↓
Server creates NEW session

session=XYZ789
````
So:
- ``Old session`` → invalid
- ``New session`` → authenticated




### Insecure Session Transmission

Even if the session ID is strong, it can still be stolen if it is transmitted insecurely.

Bad example:
````
HTTP
 ↓
Session ID
 ↓
Network
 ↓
Attacker may capture it
````

Secure approach:
````
HTTPS
 ↓
Encrypted connection
 ↓
Session ID
 ↓
Server
````

For cookie-based sessions, important protections include: ``Secure``, ``HttpOnly``, ``SameSite``


For example:
````
Set-Cookie: session=ABC123; Secure; HttpOnly; SameSite=Lax
````


| Attribute  | Purpose                                             |
| ---------- | --------------------------------------------------- |
| `Secure`   | Send cookie only over HTTPS                         |
| `HttpOnly` | Prevent JavaScript from directly reading the cookie |
| `SameSite` | Helps reduce cross-site request attacks             |



### 2. Session Tracking

After login, the server needs to know:

``Who is this?`` -> ``Which session?`` -> ``What permissions?`` -> ``What resource are they requesting?``

Example:
````
Browser
   |
   | Cookie: session=ABC123
   ↓
Server
   |
   | ABC123 → Alice
   |
   | Alice = normal user
   ↓
Allow appropriate actions
````

Two major problems are:
- Authorization Bypass
- Insufficient Logging


#### Authorization Bypass

> **Authorization = What are you allowed to do?**

Authentication answers: ``Who are you?``


Authorization answers: ``What are you allowed to access/do?``

Example:
````
Alice logs in
     ↓
Server identifies Alice
     ↓
Alice is a normal user
     ↓
Can view her profile
Can edit her profile
     ↓
Cannot access admin functions
````
An ``authorization bypass`` happens when the server fails to properly check the user's permissions.



It is also worth talking about the two types of authorisation bypasses:
- **Vertical bypass**: We can perform an action that is reserved for a more privileged user
- **Horizontal bypass**: We can perform an action we are allowed to perform, but on a dataset that we should not be allowed to perform the action on.


#### Insufficient Logging

**Insufficient Logging** means the application doesn't record enough information to understand an attack.
- Log ``successful and failed`` actions.
- Record the ``session and user`` associated with actions.
- This helps investigators reconstruct what happened.
- A hijacked session may look legitimate, so logging only rejected actions is not enough.



### 3. Session Expiry

**Session expiry** means deciding how long a session remains valid.
- **Problem**: Session lasts too long → stolen session can be abused for a long time.
- **Banking**: Should use a shorter session lifetime.
- **Webmail**: Can use a longer lifetime, but should detect unusual location/device changes.
- If suspicious activity is detected, the session should be **terminated**.

Flow: ``Session created`` → ``Time passes`` → ``Session expires`` → ``Access denied``



### 4. Session Termination

**Session termination** means properly invalidating a session when the user logs out or when security requires it.
- Logout should **invalidate the session server-side**.
- If an attacker stole the session, termination should remove their access.
- Long-lived tokens may need a **blocklist/revocation mechanism**.
- Users should ideally be able to **view and terminate active sessions**.
- After a **password reset**, terminating existing sessions helps regain control.

Easy idea: ``Logout`` -> ``Server invalidates session`` -> ``Old session no longer works``

Now, we have mapped out the session management lifecycle. Let's take a look:

| **Lifecycle Phase**     | **Observation**                                                                                      |
| ----------------------- | ---------------------------------------------------------------------------------------------------- |
| **Session Creation**    | A combination of **cookie- and token-based session management** is being used.                       |
| **Session Creation**    | A **new session value** is provided for each login attempt.                                          |
| **Session Creation**    | The session value appears to be **sufficiently random**.                                             |
| **Session Tracking**    | **Unauthenticated actions** are not tracked via a session.                                           |
| **Session Tracking**    | The **cookie is sent with each request** for tracking.                                               |
| **Session Tracking**    | Several requests can be made **without a cookie**.                                                   |
| **Session Tracking**    | The initial **token values loaded after authentication** dictate the visible information.            |
| **Session Expiry**      | There is a **mismatch between client-side and server-side expiry times**.                            |
| **Session Expiry**      | The **expiry time is incredibly long**.                                                              |
| **Session Termination** | Users can **forcibly terminate their session**.                                                      |
| **Session Termination** | Sessions are terminated server-side, but reusing an old session causes an **internal server error**. |


Given all of this information, we would already report the following vulnerabilities on a security assessment:
- Excessive Session Lifetimes

We would also need to investigate the following further:
- Access controls on all `API` endpoints
- Web application logs for the accountability of actions


> **Note**: API, which stands for ``Application Programming Interface``, is a set of rules and protocols for building software and applications. An API allows different software programs to communicate with each other. It defines methods of communication between various components, including the kinds of requests that can be made, how they're made, the data formats that should be used, and conventions to follow.

## Task 7: Conclusion 

### Defences
To defend against these attacks, it is important to implement a secure session management lifecycle. While several items were touched on in this room, let's take a look at a recap:

| Defence                                           | Easy meaning                                                                                                                                          |
| ------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| **1. Store session values securely**              | Whether you use a **cookie or token**, protect it properly.                                                                                           |
| **2. Make session values random / non-guessable** | An attacker should not be able to predict another user's session ID. If using a token such as a JWT, use proper **signing** so it cannot be modified. |
| **3. Check authorization**                        | Every request should check: **Who is this user? What are they allowed to do?**                                                                        |
| **4. Set session expiry**                         | Sessions should eventually expire. This reduces the time an attacker can use a stolen session.                                                        |
| **5. Properly terminate sessions**                | When the user logs out, remove the session from the client **and invalidate it on the server**.                                                       |
