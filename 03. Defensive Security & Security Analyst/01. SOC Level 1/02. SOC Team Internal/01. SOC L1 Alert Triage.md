## Task 1: Introduction

A security alert is a notification about suspicious activity or a possible security threat.

#### Main SOC L1 Responsibilities

1. **Receive**: Get alerts from security tools (SIEM, EDR).
2. **Analyse**: Check logs and investigate suspicious activity.
3. **Validate**: Determine whether it is a real threat or a false positive.
4. **Escalate**: Send complex incidents to senior analysts.
5. **Resolve**: Close the alert after appropriate action.

> A SOC L1 Analyst must detect, investigate, and correctly handle alerts to prevent security breaches.

## Task 2: Event and Alerts

A **security alert** is a notification generated when a security tool detects suspicious or potentially malicious activity.

**Example:**
- **Email Marked as Phishing**: A suspicious email is detected.
- **Unusual Gmail Login Location**: A login occurs from an unusual location.
- **Unapproved Mimikatz Usage**: A tool commonly used to extract Windows credentials is detected.

> SOC analysts must understand, investigate, and respond to alerts to prevent security breaches.

---


### From Events to Alerts

An event is any activity happening on a system, such as a login, process launch, or file download.

Key Difference:
- **Event**: Any activity happening on a system.
- **Log**: A record of that activity.
- **Alert**: A notification about suspicious activity that needs investigation.


#### Alert Management Platforms 

These platforms help SOC teams collect, manage, and investigate security alerts.

| Platform  | Purpose                                              | Examples                        |
| --------- | ---------------------------------------------------- | ------------------------------- |
| SIEM      | Collects logs and manages security alerts.           | Splunk ES, Elastic              |
| EDR / NDR | Detects threats on endpoints and networks.           | Microsoft Defender, CrowdStrike |
| SOAR      | Centralises alerts and automates security responses. | Splunk SOAR, Cortex SOAR        |
| ITSM      | Manages security tickets and tasks.                  | Jira, TheHive                   |

### L1 Role in Alert Triage

Alert Triage means reviewing security alerts to decide whether they are real threats or false positives.

#### SOC Team Responsibilities

| Role         | Responsibility                                   |
| ------------ | ------------------------------------------------ |
| SOC L1       | Reviews alerts and escalates real threats to L2. |
| SOC L2       | Performs deeper investigation and remediation.   |
| SOC Engineer | Ensures alerts contain useful information.       |
| SOC Manager  | Monitors alert handling speed and quality.       |

> L1 detects and filters alerts, L2 investigates deeper, engineers maintain tools, and managers oversee the process.

## Task 3: Alert Properties

A **security alert** contains important information that helps SOC analysts investigate suspicious activities.

- Understand alert details.
- Identify affected users and systems.
- Determine threat severity and priority.
- Decide what action to take.

### Alert Properties

Here is the data formatted as a clean Markdown table. Because the "Examples" column contains multi-line text and lists, I used HTML `<br>` tags and bullet points to keep the formatting neat and readable within the table cells.

| № | Property | Description | Examples |
| :--- | :--- | :--- | :--- |
| 1 | **Alert Time** | Shows alert creation time. Alert usually triggers a few minutes after the actual event | • Alert Time: March 21, 15:35<br>• Event Time: March 21, 15:32 |
| 2 | **Alert Name** | Provides a summary of what happened, based on the detection rule's name | • Unusual Login Location<br>• Email Marked as Phishing<br>• Windows RDP Bruteforce<br>• Potential Data Exfiltration |
| 3 | **Alert Severity** | Defines the urgency of the alert, initially set by detection engineers, but can be altered by analysts if needed | • (🟢) Low / Informational<br>• (🟡) Medium / Moderate<br>• (🟠) High / Severe<br>• (🔴) Critical / Urgent |
| 4 | **Alert Status** | Informs if somebody is working on the alert or if the triage is done | • (🆕) New / Unassigned<br>• (🔄) In Progress / Pending<br>• (✅) Closed / Resolved<br>• And often other custom statuses |
| 5 | **Alert Verdict** | Also called alert classification, explains if the alert is a real threat or noise | • (🔴) True Positive / Real Threat<br>• (🟢) False Positive / No Threat<br>• And often other custom verdicts |
| 6 | **Alert Assignee** | Shows the analyst that was assigned or assigned themselves to review the alert | • Assignee can sometimes be called alert owner<br>• Assignee takes responsibility for their alerts |
| 7 | **Alert Description** | Explains what the alert is about, usually in three sections on the right | • The logic of the alert generating rule<br>• Why this activity can indicate an attack<br>• Optionally, how to triage this alert |
| 8 | **Alert Fields** | Provides SOC analysts' comments and values on which the alert was triggered | • Affected Hostname<br>• Entered Commandline<br>• And many more, depending on the alert |

## Task 4: Alert Periodisation

Alert Prioritisation means deciding which security alerts need attention first.

#### How to Prioritise

1. **Critical**: Active attacks or serious security threats.
2. **High**: Suspicious activities that may cause damage.
3. **Medium**: Potential security issues that need investigation.
4. **Low**: Minor or less urgent events.

### ## Picking the Right Alert

SOC analysts prioritise alerts using three steps:

1. **Filter Alerts**: Select new, unresolved alerts that nobody else is investigating.
2. **Sort by Severity**: Handle Critical → High → Medium → Low.
3. **Sort by Time**: Investigate the oldest alerts first.
